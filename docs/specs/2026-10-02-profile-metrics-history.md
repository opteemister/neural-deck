# Метрики профилей: уточнённый проект спецификации

## 1. Решения пользователя

- Сохраняем существующие метрики и их отображение.
- Основные показатели: Decode, Prefill, один средний TTFT, параллельные запросы,
  очередь, время ожидания в очереди, занятость KV cache, текущие и средние
  попадания в KV/prefix cache, процент принятия draft-токенов.
- Отдельно сохраняем историю входных, выходных и кешированных входных токенов
  по запросам, чтобы позднее строить суммы и столбчатые графики.
- Фоновая запись снимков раз в 5 секунд; браузер получает live раз в 2 секунды.
- В браузере ровно ограничение до 120 точек, без ограничения числа минут.
- Bootstrap загружает последние 120 сохранённых точек и продолжает live-буфер.
- Очистка снимков движка в полночь допускает физическое наличие записей возрастом
  почти 48h; чтение истории снимков ограничено последними 24 часами.
- Журнал использования API хранится бессрочно, без автоматической очистки;
  запросы к нему могут охватывать любой сохранённый период.
- Идентификатор запуска в истории: `(profile_name, pid)`, без дополнительного
  Run ID. Допущение: в пределах хранения один профиль не получает повторно
  тот же PID в другом запуске. При нарушении допущения записи могут объединиться;
  дополнительного механизма различения запусков в данной версии нет.
- Бенчмарки являются обычными запросами к профилям, отдельного хранилища нет.
- URL Prometheus опционален; при недоступности используется локальный источник.

Это черновик для обсуждения. Код сбора, хранения и UI пока не реализуется.

## 2. Обязательный набор

### 2.1. Существующие поля сохраняются

`decode_tps`, `prefill_tps`, `ttft_mean_ms`, `active_requests`, `queue_requests`,
`kv_cache_percent`, `prompt_tokens_total`, `completion_tokens_total`,
`inflight_completion_tokens`, `completed_requests`, `uptime_s`, `vram_bytes`,
`power_watts`, `energy_kwh`.

Последние четыре поля остаются в контракте, но ранее убранные из модельной панели
карточки не возвращаются. Для power/energy на отдельный профиль достоверного
источника сейчас нет: NULL, без деления общей мощности GPU между процессами.

### 2.2. Добавляемые колонки снимков

| Колонка | Смысл | Возможный источник |
|---|---|---|
| `queue_time_mean_ms` | Среднее ожидание запросов в очереди в интервале измерения | vLLM/SGLang histogram, если есть |
| `cached_prompt_tokens_total` | Кешированные входные токены с начала запуска | llama.cpp, vLLM, SGLang |
| `prefix_cache_hit_percent` | Текущая доля повторно использованных входных токенов | Приращения hits/queries или cached/input; SGLang native gauge |
| `prefix_cache_hit_mean_percent` | Общая доля повторно использованных токенов с начала текущего запуска | Накопительные совместимые счётчики |
| `spec_acceptance_percent` | Текущий процент принятых draft-токенов | Native ratio либо Δaccepted/Δdraft |

Отдельные TTFT p50/p95/p99, другие процентили, многочисленные стадии, Mamba/SWA,
память весов/graphs, LoRA/MFU/коннекторы не добавляются в обязательный набор.

### 2.3. Семантика кеша

«Попадание в KV cache» в UI уточняется как «повторное использование входного
prefix», чтобы не смешивать это с процентом занятой памяти KV.

- Текущее: 100 × Δcached / Δeligible_input за фактический интервал двух измерений.
- Среднее с начала запуска: 100 × cumulative_cached / cumulative_eligible_input.
- Это доля токенов по всем запросам, взвешенная по их длине, не среднее процентов
  запросов и не среднее процентов 5-секундных снимков.
- При denominator=0: NULL/«—», а не 0%. Реальные cache misses дают 0%.
- llama.cpp prompt_tokens_total исключает кеш: denominator = processed + cached.
- vLLM hits/queries считаются токенами; использовать одну совместимую пару.
  Native input totals и queried tokens не обязаны иметь одинаковую семантику:
  выбранная пара и единица фиксируются в metadata/tooltip.
- SGLang native cache_hit_rate допустим для текущего значения с его native окном;
  общую долю считать по достоверным накопительным cached/input counters.
- Если exporter имеет только текущий ratio, из него не вычислять фиктивное
  общее среднее: без весов mean остаётся NULL.
- Native process lifetime counters могут дать долю с начала процесса даже при
  позднем обнаружении; нельзя объявлять историю лишь наблюдаемого периода
  статистикой всего запуска.
- FreeToken/NInfer не получают показатели кеша из занятости памяти: если
  достоверного источника reuse нет, это прочерк.
- SGLang token_usage — давление нескольких пулов, не только KV. kv_cache_percent
  брать из подтверждённого full KV; если его нет, не подменять общей долей.

### 2.4. Speculative decoding

Один показатель «Draft acceptance, %» для MTP, DFlash, DSpark и иных методов.
Название метода можно показывать как metadata, только если оно достоверно известно.
Не вводить отдельные колонки для каждого метода.

- Native acceptance ratio нормализуется в 0..100.
- Если есть только cumulative draft/accepted counters, брать их приращения
  между валидными наблюдениями одного `(profile_name, pid)`.
- Сброс counters сбрасывает baseline, не создаёт отрицательное/ложное значение.
- При отсутствии предложенных draft-токенов: NULL, не 0%.
- Bonus/main-model токены не входят в numerator принятых draft-токенов.
- Draft/accepted counts нужны адаптеру для вычисления, но не создают новые
  видимые карточки и отдельные числовые колонки истории.
- Не угадывать acceptance из общей скорости или числа выходных токенов.

## 3. История использования API и метрик по запросам

Использовать существующий RequestJournalService/RequestJournalRecord, расширить
запись полями `pid`, `cached_input_tokens`, `usage_received_at`, `usage_source`.
`profile_name`, `input_tokens`, `output_tokens` и статус уже есть в журнале.
Связь с внутренним instance_id может остаться для существующего API, но история
и сравнение не требуют нового Run ID и группируются по имени профиля и PID.

В той же итоговой строке хранить `client_id` — числовую ссылку на отдельную
таблицу `api_clients`, IP данного запроса (`client_ip`) и метрики запроса.
Использовать стандартный `Authorization: Bearer <key>` без специальных
клиентских заголовков. Пока ключ необязателен и любой непустой ключ принимается;
проверка разрешённых ключей не вводится. Не переопределять ключ как публичное
имя клиента и не добавлять пользовательскую документацию об использовании
ключа в качестве имени. Это решение для текущего личного использования.

### 3.1. Клиенты API

`api_clients`:
- `id` — SQLite INTEGER PRIMARY KEY AUTOINCREMENT, без UUID; стабильный client_id;
- `api_key` — nullable значение полученного ключа, уникальное для непустых ключей;
- `anonymous_ip` — nullable уникальный IP для клиента без ключа;
- `ip_addresses` — JSON-массив уникальных нормализованных IP, замеченных у клиента;
- `created_at`, `last_seen_at` — UTC время первого и последнего обращения.

Для клиента по ключу api_key заполнен, anonymous_ip=NULL. Для клиента без ключа
api_key=NULL, anonymous_ip содержит IP. Эти два вида записей не объединяются
автоматически по совпадению IP. Один ключ с разных IP остаётся одним клиентом;
несколько ключей с одного IP — разные клиенты. Клиенты без ключа с одного IP
объединяются в одну запись; IP не гарантирует идентичность физического пользователя.
При отсутствии и ключа, и достоверного IP client_id=NULL.

При поступлении запроса атомарно найти/создать клиента по ключу, а без ключа —
по IP; обновить last_seen_at и добавить новый IP в массив без дубликатов.
Уникальные ограничения и транзакционное обновление массива исключают дубли
клиентов и потерю IP при параллельных запросах. client_id и client_ip фиксируются
при приёме запроса, не вычисляются повторно при завершении.

Регистр и содержимое ключа значимы. Сохранять ключ только в таблице клиентов,
не дублировать в журнале запросов, metadata, технических логах и ответах
статистического API; upstream-авторизация остаётся отдельной конфигурацией.
IP брать из адреса соединения либо уже настроенной обработки доверенного
reverse proxy, не доверять произвольному X-Forwarded-For от клиента.
Журнал запросов и api_clients не участвуют в автоматической очистке снимков.

### 3.2. Метрики конкретного запроса

| Поле | Значение для конкретного запроса |
|---|---|
| `started_at`, `finished_at` | UTC начало и завершение запроса |
| `latency_ms` | Полная длительность запроса; использовать существующее поле |
| `ttft_ms` | Время до первого токена, если оно достоверно измерено/возвращено |
| `queue_time_ms` | Время ожидания этого запроса в очереди движка |
| `prefill_time_ms` | Длительность обработки входа движком |
| `generation_time_ms` | Длительность генерации движком |
| `prefill_tps` | Скорость обработки входа для этого запроса |
| `decode_tps` | Скорость генерации для этого запроса |
| `prefix_cache_hit_percent` | Доля кешированных входных токенов этого запроса |
| `spec_acceptance_percent` | Доля принятых draft-токенов этого запроса |
| `metric_meta` | Источник и семантика показателей, включая знаменатели для скоростей |

Сохранять возвращённые движком показатели, относящиеся именно к этому запросу.
При отсутствии готовой скорости её можно вычислить только при известных
совместимых числе токенов и длительности соответствующей стадии; например,
decode = generated_tokens / generation_seconds. Для prefill учитывать,
считает ли движок обработанные токены без кеша или весь вход, и фиксировать
это в metadata. Нулевой/неизвестный знаменатель означает NULL.

TTFT, измеренный прокси до первого токена содержимого или reasoning, включает
время доставки и обработки запроса; не смешивать его с native TTFT без указания
источника. Служебный streaming chunk не считать первым токеном. Для
непотокового ответа не выводить TTFT из полной длительности.

Cache hit вычислять как cached_input_tokens / input_tokens при совместимой
семантике. Speculative acceptance вычислять только по счётчикам данного запроса
или брать native процент. Общие счётчики `/metrics` при параллельных запросах
не позволяют распределить стадии или draft acceptance между запросами.
Не копировать в строку запроса последний снимок скорости, кеша или acceptance
всего движка. Отсутствующие показатели оставлять NULL.

Занятость KV cache, число активных запросов и длина очереди остаются состоянием
движка в `metric_samples`, а не агрегатами отдельного запроса. В журнале есть
время ожидания конкретного запроса и его cache hit, а не эти глобальные значения.
Будущие агрегаты строить по профилю, PID, клиенту и времени: суммы токенов и
запросов, средние длительности, скорости по сумме совместимых токенов/времени.
Средние cache/draft проценты требуют соответствующих весов; для draft сохранять
достоверные знаменатель и числитель в metadata, если источник их предоставляет.
Без весов не объявлять среднее процентов общей долей принятых токенов.

- PID и профиль фиксируются при выборе upstream для запроса, не берутся из
  текущего процесса при позднем завершении: за это время профиль мог перезапуститься.
- Одна итоговая запись на каждый фактический запрос. Для streaming — после
  получения финального usage/завершения, не отдельная строка на каждый chunk.
- usage_received_at — UTC момент получения итогового usage. created_at текущего
  журнала не переопределять без необходимости; новое поле имеет явный смысл.
- cached_input_tokens извлекается из документированных полей usage, например
  prompt_tokens_details.cached_tokens/input_tokens_details.cached_tokens.
- cached tokens — часть input_tokens, а не дополнительные входные токены.
  В будущем бары: input_total, cached_subset, output_total; cache не прибавлять
  к input второй раз. При сопоставимых значениях uncached=input-cached.
- Отсутствующий usage/кеш остаётся NULL. Ошибка или прерванный streaming
  сохраняются с реально известными значениями; неизвестное не превращается в 0.
- Повторная корреляционная request_id не является ключом дедупликации:
  retries и отдельные запросы могут иметь одинаковую request_id.
- Снимки cumulative totals раз в 5 секунд не записываются как отдельные запросы.
  Будущие суммы токенов берутся по событиям запросов; periodic counters служат
  отдельным источником наблюдения и не суммируются с событиями.
- Прямые обращения сторонних клиентов к движку не видны прокси Студии.
  /metrics предоставляет агрегаты, но не события отдельных запросов. Для них
  сохраняются periodic totals; полноценный per-request учёт требует источника
  в движке. Нельзя восстанавливать выдуманные запросы из разницы counters.
- История использования API хранится бессрочно и не участвует в ежедневной
  очистке метрик движка. Фильтры периода применяются только при чтении;
  ограничения последних 24 часов для usage API нет. Существующий TokenStats
  сохраняет возможность учитывать весь журнал либо выбранный период.
  Старые строки без pid/cache остаются неизвестными.

В этой задаче реализовать запись и чтение событий usage. Сами новые бары,
агрегации бенчмарков и экран сравнения профилей — дальнейшая задача.

## 4. SQLite и экстремумы

### `metric_samples`

Одна строка на наблюдаемый процесс и цикл записи:
`id`, `profile_name` nullable, `pid`, `engine_id`, `model_name`, `recorded_at`,
`observed_at`, nullable numeric колонки раздела 2 и `metric_meta` JSON.
Metadata содержит state/source/semantic/window/observed_at, когда эти поля
различаются между показателями. История внешнего процесса имеет profile_name=NULL;
не приписывать её автоматически похожему сохранённому профилю.

Индексы `(profile_name, pid, observed_at)`, `(profile_name, observed_at)` и
`observed_at`. Пакетная транзакционная запись, без хранения всех raw exporters.
NULL означает отсутствие, 0 — реально измеренный ноль. NaN/Inf не сохраняются
как достоверные numeric значения.

### `metric_launch_extrema`

Ключ `(profile_name, pid)` для managed профилей. Хранятся maxima Decode, Prefill,
активных запросов, очереди, занятости кеша; минимум положительного измеренного
TTFT mean. Только свежие наблюдения обновляют extrema. Изменения live-опроса
тоже учитываются, запись в БД производится фоновым циклом каждые 5 секунд.
После перезапуска backend восстанавливаются extrema того же profile/PID.

Это extrema с начала наблюдения данного запуска, не доказанные максимумы за
период до обнаружения процесса. Последние незаписанные изменения могут потеряться
при аварии между 5-секундными записями. Отдельного lifetime рекорда профиля нет.

## 5. Сбор и фоновые задачи

- Lifespan backend запускает collector и cleanup task; при shutdown завершает их.
- Каждые 5 секунд collector собирает все обнаруженные запуски и пишет снимки,
  независимо от браузера и настройки Prometheus.
- Live API допускает сбор раз в 2 секунды. Общий per-process lock/snapshot/baseline
  объединяет пересекающиеся запросы, без конкурирующих scrape llama.cpp.
- Свежий snapshot до 1 секунды может использоваться повторно. Фоновая задача
  обращается к сервису напрямую, не к HTTP своего приложения.
- Ошибка одного процесса не прерывает сбор остальных. Timeout ограничен.
- Labels/TYPE/HELP сохраняются parser и агрегируются только явными mappings.
- Rates/mean используют реальные интервалы; при reset первая производная NULL.
- Нет новых наблюдений TTFT/queue latency — NULL, не фиктивный 0.
- Stale данные не превращаются в свежие изменением timestamp и не обновляют maxima.

## 6. Чтение и frontend

Единый endpoint `GET /api/v1/metrics`:
`mode=current|bootstrap|history|peaks|usage`, `profile_name`, `pid`, `scope`,
для истории/usage `from`, `to`, ограниченный `limit` и pagination для usage.
Существующий endpoint instance metrics остаётся совместимым адаптером.
Стандартный envelope проекта; response указывает фактический source, freshness,
observed_at и источники отдельных полей.

- URL Prometheus пустой: current из live collector без чтения history БД.
- URL задан: current из пригодных свежих данных Prometheus, иначе последний
  snapshot SQLite. В fallback значения обновляются раз в 5s, polling остаётся 2s.
- bootstrap: последние 120 настоящих snapshot + current + launch extrema.
- History предпочтительно Prometheus, иначе SQLite; usage — локальный журнал,
  поскольку Prometheus не предоставляет per-request events.
- После bootstrap браузер добавляет live-точки с новыми observed_at каждые 2s,
  хранит максимум 120, без повторного чтения истории при каждом polling.
- Время охвата может быть любым: ограничение четырьмя минутами убрать. Не создавать
  искусственные промежуточные точки из 5-секундных snapshot.
- На графике соединять соседние валидные точки одной серии, даже при большом
  временном разрыве. Не добавлять фиктивные значения в промежутке. Tooltip
  показывает только реально измеренные значения. Отдельные profile/PID линии
  не соединять; NULL не подменять нулём.
- Пока bootstrap не закончился, live polling ещё не дополняет этот буфер;
  устаревший ответ другой вкладки не изменяет текущую.
- Сохраняются три графика Prefill, Generation, Requests. Scalar TTFT/KV остаются.
  Cache current/mean, queue latency и draft % размещаются компактно в подробной
  таблице внутри вкладки. Не возвращать ранее убранные ресурсные карточки.
- Вкладка «Все» суммирует совместимые throughput/requests; TTFT/queue/cache ratios
  взвешиваются по достоверным counts. При отсутствии весов общее среднее NULL.

## 7. Очистка

В 00:00 по timezone ОС сервера, а также при старте/после пропущенной полуночи,
пакетно удалять только snapshot старше now-24h. В БД и API timestamps UTC.
History API для снимков независимо фильтрует последние 24 часа до физической
очистки. Журнал использования API не удаляется; usage API поддерживает любой
сохранённый период с ограниченным размером страницы и pagination.
Согласовано физическое наличие данных возрастом почти 48h перед следующей
полуночью. Ежедневного VACUUM нет; освобождённые страницы переиспользуются SQLite.
Extrema активного profile/PID сохраняются, даже если процесс работает больше суток.
Extrema завершённого profile/PID удаляются, когда его история вышла из окна.

## 8. Prometheus

`PROMETHEUS_URL=` уже добавлен пустым в env-файлы и пример; runtime support ещё нет.
Docker продолжает использовать только .env.local. При непустом URL асинхронно
проверить query API с timeout 2s; ошибка не блокирует startup.

Предоставить `/metrics` Студии из локального Collector, без чтения Prometheus
обратно, без повторного независимого scrape. Labels: постоянный studio_id,
profile_name (если есть), pid, engine_id. Новый Run ID не вводится.
Оператор один раз добавляет адрес Студии в scrape_configs; URL в env сам по себе
не настраивает сбор. В документации предоставить готовый YAML.

Чтение через query/query_range, scopes экранируются; произвольный PromQL от
браузера не принимается. Query timestamps не подменяют observed_at исходных
sample. Freshness current не более 10s; пустой ответ, wrong profile/PID/studio,
stale и HTTP/timeout дают локальный fallback. После ошибки cooldown 30s и
автоматическая повторная проверка. Без повторяющихся toast на каждом polling.
Локальная запись остаётся включена всегда. History gaps могут дополняться SQLite,
без дублирования точек и с явным указанием mixed sources.

Для guarded HTTP использовать optional bearer token из env; HTTPS проверяет
сертификат, credentials не показываются в UI и логах. Prometheus снаружи не
устанавливается и не перенастраивается автоматически.

Raw counters hits/query/draft/accepted могут экспортироваться для вычислений
Prometheus, не создавая новых колонок snapshot и видимых карточек. Локальный
сбор сохраняет baseline независимо от выбранного источника чтения.

Источники: [Prometheus API](https://prometheus.io/docs/prometheus/latest/querying/api/),
[scrape config](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#scrape_config),
[исследование exporter](../research/2026-10-02-engine-metrics.md).

## 9. Дополнительные предложения, не включённые без согласования

Больше новых метрик сейчас не требуется. Если выбирать один дополнительный
показатель для сравнений, полезен `spec_acceptance_length`: процент принятых
токенов одинаков, а среднее число токенов за verification step может различаться
из-за длины draft. Пользователь пока выбрал только процент; это предложение,
не обязательная реализация.

## 10. Критерии приёмки и порядок

1. Closed browser: независимая запись двух профилей каждые 5s.
2. Строки и extrema разделены по profile/PID, без нового Run ID.
3. Bootstrap восстанавливает до 120 точек; live не перечитывает историю БД.
4. Большие временные разрывы соединены линией между реальными точками одной серии.
5. Одно TTFT; queue latency; cache current/launch mean; draft % корректны или NULL.
6. Ratio с нулевым знаменателем не превращается в 0%; weighted cache не усредняет
   snapshots; counter resets не дают ложных всплесков.
7. Один запрос даёт одну запись input/output/cached usage с правильным profile/PID;
   streaming chunks не умножают токены; недоступный cache остаётся неизвестным.
8. Запросы напрямую к движку не выдаются за наблюдаемые прокси events.
9. Midnight/startup cleanup и API 24h filter применяются только к снимкам движка;
   extrema активного запуска сохраняются. Журнал API не очищается и доступен
   за любой сохранённый период.
10. Empty URL: без Prometheus requests; configured/fresh: Prometheus source;
    outage/empty/stale: SQLite fallback; локальная запись продолжается.
11. Никакие новые TTFT percentiles и дополнительные метрики не добавляются.

После утверждения: migrations/journal → Collector/storage/cleanup → mappings/API →
bootstrap/charts → Prometheus exporter/reader/fallback → проверки и документация.

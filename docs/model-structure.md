# Структура локальных моделей и наборов Hugging Face

Документ описывает, как Neural Deck представляет модель на диске, сопоставляет
её с Hugging Face и группирует содержимое в карточке.

## Папка хранения

Корень локальных моделей задаётся настройкой `models_root`. Типичная структура:

```text
models_root/
└── namespace/
    └── model-name/
        ├── config.json
        ├── tokenizer.json
        ├── Q4_K_M/
        │   ├── model-00001-of-00002.gguf
        │   └── model-00002-of-00002.gguf
        └── Q8_0/
            └── model.gguf
```

`namespace/model-name` является одной локальной моделью. Вложенные каталоги
квантов становятся логическими группами внутри этой карточки, а не отдельными
карточками. Сканирование учитывает фактическую файловую систему, поэтому
вручную добавленная или частично загруженная модель не скрывается.
Отдельный файл модели вне папки также остаётся самостоятельной локальной
моделью.

## Компоненты модели

### Варианты модели

Вариант — основной набор весов: BF16, SafeTensors, GGUF-квант и т.п. Файлы с
shard-суффиксами `-00001-of-00004` объединяются в один вариант. Вложенная
папка с весами также является одним вариантом.

Карточка показывает одну компактную строку на вариант. Отдельное удаление
разрешено только если у модели больше одного варианта: для вложенного варианта
удаляется его папка, а для корневого shard-набора — точно входящие в него
файлы. Один оставшийся вариант удаляется только вместе со всей папкой модели.

### Вспомогательные блоки

Вспомогательный блок — часть, которая дополняет модель, но не является её
основными весами. Это могут быть MTP, проектор, Vision/Audio-компонент,
adapter, `mmproj` или другой компонент, поставляемый отдельной группой файлов.

Блок может находиться в собственной вложенной папке или набором файлов в корне
репозитория. В UI используется название **«Вспомогательные блоки»**, а не
«варианты модели». Блок показывается одной строкой и удаляется как логическая
группа. Для корневого блока удаляются только его файлы; общие конфигурации и
tokenizer в него не попадают.

### Общие файлы

README, LICENSE, `config*.json`, tokenizer, vocabulary, merges, шаблоны чата и
индексные JSON-файлы считаются общими служебными файлами. Они участвуют в
проверке скачанного набора, но не показываются как варианты или вспомогательные
блоки и отдельно не удаляются.

## Определение роли группы

Группировка не привязана к конкретному имени модели:

1. Для репозитория Hugging Face используется список файлов выбранной ревизии
   и та же логика наборов, которая применяется при скачивании варианта.
2. Для скачанных через Neural Deck ожидаемый набор фиксируется в
   `.neural-deck-hf.yaml` до начала передачи файлов, а роль группы определяется
   тем же общим алгоритмом группировки.
3. Для вручную добавленной папки используются структура каталогов, расширения,
   shard-последовательности и границы компонентных суффиксов в именах файлов.
   Это эвристика только для случаев, когда нет данных Hugging Face.

Названия MTP, Vision или другого продукта не являются списком моделей. Они
используются только как признаки роли внутри уже сформированной группы. Если
признаков недостаточно, группа остаётся видимой с неопределённым статусом и не
объявляется вспомогательной без достаточных доказательств.

Если у папки вида `namespace/model` нет manifest или в ней появились локальные
группы, которых нет в выборочном manifest, сканер пытается получить публичную
ревизию этого репозитория Hugging Face. Найденные локальные группы
сопоставляются по относительным путям и размерам, после чего manifest создаётся
или дополняется атомарно. При отсутствии сети или репозитория папка остаётся в
списке с неопределённым источником.

## Manifest и проверка полноты

Для папки модели manifest хранится в:

```text
<model-dir>/.neural-deck-hf.yaml
```

В нём сохраняются `repo_id`, commit `revision`, область загрузки (`snapshot` или
`selection`) и ожидаемые файлы с размерами и доступными hash/etag.

Manifest записывается атомарно до начала передачи файлов. После отмены или
ошибки каталог может содержать только часть ожидаемого набора, но эта часть
остаётся в локальном списке.

Выборочные загрузки одной и той же ревизии накапливаются в одном manifest:
загрузка следующего кванта не заменяет сведения о ранее загруженных. При
сканировании выборочный manifest также сверяется с локальными файлами и при
необходимости восстанавливает сведения о ранее загруженных группах.

Статусы группы:

- `complete` — все ожидаемые файлы присутствуют и совпадают по размеру;
- `incomplete` — хотя бы один ожидаемый файл отсутствует или имеет другой размер;
- `unknown` — для проверки недостаточно manifest или метаданных Hub.

Неполная группа помечается предупреждающим треугольником. Неизвестный статус
не используется как доказательство того, что файл повреждён.
40-символьный `etag`/OID Hugging Face не считается хешем содержимого: при таком
идентификаторе файл подтверждается размером, а хеш показывается как
непроверенный, чтобы LFS-файл не ошибочно считался отсутствующим.

Кнопка **«Сканировать»** запускает полную синхронизацию локальных моделей:
сканер обновляет сведения о файлах ревизии из локального кэша Hugging Face
(при его отсутствии — из публичного tree API), сохраняет SHA-256 для LFS и
Git blob-идентификаторы для обычных файлов, затем пересчитывает хеш каждого
локального файла. Обычное чтение каталога остаётся быстрым и не выполняет
полный пересчёт.

## API локального каталога

### Выбор модели в профиле

Пикер профиля использует группы каталога: каждый квант GGUF — отдельный
пункт с названием модели и варианта. Одиночный GGUF передаётся как абсолютный
путь к файлу; разделённый набор — как путь к `00001-of-…`, включая подпапку.
Остальные части набора не становятся отдельными пунктами. Если первая часть
отсутствует, набор не предлагается для запуска.

Для Safetensors и других папочных моделей передаётся папка группы, а при
размещении весов в корне — сама модельная папка. Шарды одной папки не создают
несколько одинаковых пунктов. Неполные группы видны, но недоступны для выбора.

Основная модель сохраняется в `model.path` и подставляется через `{{model}}`.
`{{model_name}}` подставляет `model_name` профиля — поле «Публичное имя модели».
Заполнитель должен быть отдельным аргументом вне кавычек: подстановка сама
экранирует пробелы и специальные символы и не повторяет подстановки внутри значений.
Стандартные шаблоны передают имя через `--served-model-name` (vLLM, SGLang,
FreeToken), `--alias` (llama.cpp) или `--model-id` (NInfer).
Например: `{{engine}} serve {{model}} --served-model-name {{model_name}}`.
Сохранённые команды не переписываются: добавьте аргумент вручную или примените
«Шаблон движка», проверьте остальные параметры, сохраните и перезапустите профиль.
Позиционные аргументы также поддерживаются, например, `{{engine}} serve {{model}}`.
Подстановки экранируются как самостоятельные shell-аргументы.

Отдельного выбора draft-модели в форме нет. Вспомогательные блоки (draft,
MTP, DFlash, DSpark, image projector) подключаются параметрами команды
конкретного движка; пути к ним указываются прямо в команде. Каталог не
утверждает их совместимость с основной моделью и не добавляет флаги автоматически.

Например, llama.cpp имеет отдельные параметры `--model-draft` и `--mmproj`,
а vLLM использует `--speculative-config` с выбором метода. MTP может быть
встроен в основную модель и не требовать отдельного файла. Поэтому общее поле
«Draft-модель» не описывает эти случаи корректно.

Источники:

- [Параметры llama.cpp server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- [Speculative decoding в vLLM](https://github.com/vllm-project/vllm/blob/main/docs/features/speculative_decoding/README.md).

Для draft-модели путь задаётся непосредственно аргументами команды запуска,
например `--model-draft /models/draft.gguf` или внутри `--speculative-config`.
Отдельное поле `model.draft_path` и заполнитель `{{model_draft}}` удалены.

`GET /api/v1/models/local` возвращает одну `LocalModel` на модельную папку.
Помимо старых плоских полей совместимости, модель содержит:

- `groups` — логические варианты модели;
- `auxiliary_blocks` — логические вспомогательные блоки.

Каждая группа содержит `id`, подпись, тип, список исходных файлов для операций,
размер, количество файлов, статус полноты и `deletable`. UI использует эти
данные для компактного отображения и не классифицирует файлы повторно.

Удаление группы выполняется через:

```text
DELETE /api/v1/models/local/{model_id}/groups/{group_id}
```

Backend повторно разрешает группу по текущему каталогу, проверяет, что путь не
выходит за `models_root`, и удаляет либо одну вложенную папку, либо точный набор
корневых файлов вспомогательного блока.

Полное удаление модели остаётся отдельной операцией над всей папкой модели.

## Выбор GPU в профиле

Форма использует список NVIDIA GPU из того же `GET /api/v1/system`, что и
дашборд. Backend получает `index`, имя и `uuid` через `nvidia-smi`.
В списке выбора отображаются номер и имя; UUID доступен в подсказке.

Выбранные карты записываются в `environment.CUDA_VISIBLE_DEVICES` списком
UUID через запятую. CUDA поддерживает UUID, поэтому выбор не зависит от
изменения индексов `nvidia-smi`. Внутри дочернего процесса выбранные устройства
нумеруются заново с нуля в порядке переменной. Параметры распределения модели
между картами остаются в команде конкретного движка.

«Все GPU» удаляет переопределение из профиля: процесс наследует доступность
карт из окружения приложения. «Без GPU» записывает `-1`. Обычный выбор GPU
заменяет только эту переменную; остальные переменные не меняются. Текстовое
поле и список используют одно состояние. Ранее введённые индексы и UUID
отображаются без автоматического переписывания; неизвестные идентификаторы
сохраняются и могут быть сняты пользователем.

Это настройка CUDA-процесса, а не проброс устройств в контейнер: список
ограничен картами, доступными самому backend. Выбор не гарантирует, что движок
поддерживает запуск без GPU или автоматически настроит tensor parallelism.

Источник: [CUDA environment variables](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html).

# Универсальные движки Neural Deck: простой реестр

Статус: В реализации; согласована пользователем 2026-10-12.
Дата: 2026-10-12. Заменяет предыдущую архитектуру с пакетами, recipes и stacks.
Документ описывает план изменений, а не уже реализованное поведение.

## 1. Цель и границы первого объёма

Регистрировать новый движок по имени, скрипту установки, пути executable и команде
запуска. Сохранять определение как многоразовый YAML-шаблон. Выбирать установку
в существующем профиле, запускать несколько сервисов и включать их в автозапуск.

Первый законченный контур охватывает семь направлений:

- Генерация текста.
- Генерация аудио: на первом этапе синтез речи, TTS.
- Транскрибация аудио, ASR.
- Генерация видео.
- Генерация изображений.
- Эмбеддинги.
- Структурированные решения, decision: проверка условия, выбор и оценка.

Для каждого нужен работающий сценарий с моделью и результатом. Добавить только
типы в интерфейс недостаточно. Музыка, диаризация и двусторонний голосовой диалог
не обязательны для завершения этого этапа.

Запуск и интеграция с общим API независимы. Сервис со своим UI/API можно просто
запускать и открывать напрямую. Наличие UI не является типом модели и не
исключает одновременного подключения к общему API.

## 2. Минимальная модель данных

Остаются четыре существующие сущности, без пакетов и новой платформы плагинов.

| Сущность | Ответственность |
|---|---|
| Определение движка | Имя, типы, скрипт, executable, запуск, необязательные настройки API/UI |
| Установка | Конкретная папка/venv, разрешённый executable, версия и результат установки |
| Профиль | Установка, имя, необязательная модель, команда, GPU, environment, autostart |
| Экземпляр | Процесс, identity, состояние, адрес и логи |

Встроенные определения поставляются с приложением; пользовательские —
в `<DATA_ROOT>/engines/<id>.yaml`. Профили остаются в существующем файловом
каталоге. SQLite хранит состояние/историю, но не является источником этих настроек.

Engine ID становится валидируемой строкой вместо перечисления названий в коде.
Обновление приложения не перезаписывает пользовательские определения.
Редактирование шаблона не меняет автоматически команды сохранённых профилей и
не переустанавливает окружения. В установке сохраняются использованный шаблон
и известная фактическая версия/commit. Выбор latest допустим при установке.

## 3. Регистрация и установка

Для нового устанавливаемого движка задаются:

1. Постоянный ID и отображаемое имя.
2. Один или несколько типов: text, tts, asr, video, image, embeddings, decision.
3. Обычный скрипт установки.
4. Путь executable относительно выбранной папки установки либо абсолютный путь.
5. Шаблон команды запуска.

Дополнительно: рабочая папка, environment, скрипт обновления, простая проверка
установки/готовности, протокол API, API URL и UI URL. Уже установленный executable
можно зарегистрировать без выполнения установочного скрипта.

Существующий механизм операций исполняет скрипт, который создаёт venv, скачивает
бинарник или собирает репозиторий. По завершении проверяется наличие executable
и, если задана, лёгкая проверочная команда. Проверка установки не загружает модель
на GPU и не выдаётся за проверку генерации.

Executable может быть Python из venv, а команда — запускать main.py или модуль.
Отдельный бинарник движка не обязателен. Python runtime и окружения хранятся
в постоянных каталогах, в том числе при работе приложения в Docker.
Чтение определения не выполняет код; установка — явное действие администратора.

Пример предлагаемого формата, не готовый установщик:

```yaml
version: 1
id: my-server
name: My server
types: [text, embeddings]
install_script: |
  # Обычный скрипт установки в {{target}}
executable: "{{target}}/bin/my-server"
working_directory: "{{target}}"
command: "{{engine}} --model {{model}} --host 127.0.0.1 --port 8000"
api:
  protocol: openai
  base_url: http://127.0.0.1:8000/v1
ui_url: null
```

Переменные: target — папка установки, engine — сохранённый executable,
model — выбранный локальный путь, model_name — публичное имя.
Используется безопасное экранирование существующего форматтера; неизвестные
переменные дают ошибку. Команда сервиса без модели не содержит model.
Скрытые environment variables для host/port не вводятся.

## 4. Три независимые настройки подключения

- **Типы:** что умеет движок; можно несколько.
- **UI URL:** прямая ссылка кнопки «Открыть», необязательна.
- **Протокол API:** готовый способ подключения либо «Не подключать».

Профиль наследует настройки, может сузить типы и переопределить адрес/протокол.
Публикуются только настроенные операции, поддержанные выбранной моделью.
Объявление image/video у ComfyUI само по себе не создаёт поддержку этих операций
в нормализованном API.

| Протокол | Поведение |
|---|---|
| none — Не подключать | Установка, процессы, логи, GPU, автозапуск и прямая ссылка UI |
| openai — OpenAI-совместимый | Готовые обработчики поддержанных text/embeddings/TTS/ASR/image операций |
| comfyui — ComfyUI | Специализированная существующая интеграция API/workflow |
| jev — Jev-compatible | Готовое преобразование OpenAI Decisions в нативный /v1/systemone выбранного сервера и обратно |

В списке только реально реализованные протоколы. Новый движок с известным
протоколом добавляется без изменения кода. Новый нестандартный протокол потребует
отдельного встроенного адаптера, только если понадобится общий API.

Наличие API не означает стандартность; OpenAI-compatible не означает поддержку
всех операций. Для нестандартного сервиса достаточно none и прямого использования.
Для закрытия общего API выбирается готовый совместимый serving-вариант или
небольшая обёртка конкретного сервиса, запускаемая обычным шаблоном.

Произвольные field mappings, eval, Python-плагины и общий worker SDK откладываются.
Это не мешает разработчику позже добавить новый готовый протокол.

Для openai base_url включает /v1, обработчик добавляет относительный путь операции
один раз. Для comfyui URL указывает корень сервера. API URL и UI URL независимы.
Нативный UI автоматически не проксируется. Существующий native ComfyUI proxy
сохраняется для совместимости, но не требуется для регистрации других движков.

## 5. Общий API и семь рабочих направлений

| Тип | Первый доступный интерфейс | Результат приёмки |
|---|---|---|
| text | /v1/chat/completions | Ответ и streaming через существующий LLM-движок |
| embeddings | /v1/embeddings | Векторы выбранной embedding-модели |
| tts | /v1/audio/speech | Аудиофайл через совместимый speech server |
| asr | /v1/audio/transcriptions | Multipart-аудио преобразуется в текст |
| image | /v1/images/generations и UI | Изображение через существующую интеграцию ComfyUI |
| video | Собственный UI/API ComfyUI | Сгенерированный воспроизводимый видеофайл |
| decision | /v1/decisions в формате OpenAI | Типизированные ответы локального decision-движка через адаптер |

Согласованная граница первого объёма: семь работающих функций, но не обязательная
унификация всех семи API. Видео используется непосредственно через ComfyUI.
Новый универсальный video endpoint, video adapter и общая очередь задач пока
не вводятся. Эта граница должна быть сохранена явно в плане приёмки.

ComfyUI и Qwen TTS с порталом можно запускать с none. Но для общего TTS API
контрольная конфигурация должна содержать совместимый serving-вариант.
Собственный Gradio API не маркируется OpenAI-compatible без подтверждения.
ASR и embeddings также должны реально работать через заявленные endpoints.

Для ComfyUI с none workflow выбирается в его UI. Для image API нужен конкретный
поддержанный workflow. Согласован один явно настроенный workflow на операцию
в первом объёме; в собственном UI доступны любые другие графы.
Сохраняется имеющаяся интеграция; компоненты выбираются
явно, а не по первому найденному файлу. Универсальный редактор mapping узлов
для разных графов в первый этап не входит.

Маршрутизация: операция + публичное имя модели → готовый подходящий экземпляр.
Используем текущие алиасы/приоритеты. none исключается из /v1/models и
inference-инструментов MCP. Список чата фильтруется по text, а не имени движка.
Embeddings alias не смешивает разные пространства векторов/размерности.
Неподдерживаемая операция даёт ошибку, а не уходит в произвольный движок.

Сохраняются /v1, OPENAI_PORT, VITE_OPENAI_API_BASE_URL и same-origin внутреннего
чата. Авторизация распространяется на новые endpoints. Audio обработчики
поддерживают multipart/binary и передачу больших файлов с ограниченной памятью.
Отправленная генерация после timeout автоматически не повторяется.

### 5.1. Decisions: внешний контракт OpenAI, внутренний — движка

Согласованное решение: Neural Deck предоставляет `POST /v1/decisions` по
[официальному контракту OpenAI Decisions](https://developers.openai.com/api/docs/guides/decisions).
Upstream использует собственный API реально запущенного движка. Выбор движка
не меняет формат запросов клиента. Это отдельная операция, не chat/completions.

Внешний запрос содержит `model`, `input`, массив `questions`. Типы вопросов:
`predicate`, `choice`, `score`; результат содержит массив `answers` с именами
и типами ответов. `model` — публичное имя локального профиля/алиаса, а не
обязательное имя модели OpenAI. Наличие этого endpoint не требует облачного
запроса или ключа OpenAI.

Для Jev-compatible runtime, например
[vllm-jev](https://github.com/mode-io/vllm-jev), адаптер направляет запрос в
нативный `POST /v1/systemone`. В настройке `jev` base_url — корень сервера;
адаптер добавляет этот путь один раз. Он преобразует `input` в состояние движка,
массив именованных вопросов — в его представление вопросов, `predicate` — в
поддержанный Noul, а ответы — в внешний формат OpenAI. Сопоставление Choice/Score
и их полей фиксируется для выбранной версии протокола, а не редактируется пользователем.

Первый обязательный сценарий — текстовый input и три типа вопросов. Входы с
изображениями публикуются только при поддержке конкретного адаптера и модели;
иначе возвращается явная ошибка неподдерживаемого входа.

Совместимость означает корректные значения и структуру, а не только похожие имена:

- `predicate.probability` — вероятность истинности от 0 до 1.
- `choice` сохраняет пользовательские значения вариантов и распределение по ним.
- `score` соответствует взвешенному по вероятностям среднему индексов уровней
  с нуля. Нативная оценка иной шкалы не копируется без преобразования.
- `confidence` не подменяется максимумом вероятностей; отсутствующие значения
  и usage не выдумываются. До публикации адаптера определяется, как выполнить
  обязательные поля внешнего контракта; неподдерживаемый режим отклоняется явно.
- Сохраняются соответствие именам вопросов, ошибки и предусмотренные контрактом
  отказы. Полный envelope ответа и валидация сверяются с официальной reference
  при реализации, включая ограничения текущей beta-версии.

Для первого адаптера необходимы фиксированные примеры запросов/ответов всех трёх
типов, смешанного запроса и ошибок. Маршрутизация сохраняет общую авторизацию и
выбирает только ready-профили с decision. Движок не получает чужое публичное имя
модели, если его нативный API требует другого идентификатора или вообще не требует model.
Общий конструктор mappings и отдельный публичный Jev endpoint не нужны.

### 5.2. Примеры локальных decision-моделей

По предложению пользователя основные примеры — **Amazon/Strands Decider 2B**
и **Cloudflare Clef**. Это модели; установка и команда относятся к выбранному
runtime, а не к отдельному функциональному типу для каждого производителя.

- **Первый контрольный пример — Strands Decider 2B.**
  [Официальный проект](https://github.com/strands-labs/strands-decider)
  предоставляет CLI `strands-decider serve`; в текущем README модель называется
  `StrandsAgents/strands-decider-2B-qwen3.5-v1-2610`.
  В шаблоне executable — `{{target}}/bin/strands-decider`, команда —
  `{{engine}} serve {{model}} --port 8000`, тип — `decision`.
  Нативный endpoint — `/v1/systemone`, проверка — `/health`.
  [Документация сервера](https://github.com/strands-labs/strands-decider/blob/main/docs/inference.md)
  показывает Choice, Noul и Score, но прямо не гарантирует полную совместимость
  с Jev API и не подтверждает конкурентные запросы. Поэтому протокол `jev`
  для этого runtime включается после сверки конкретных ответов; до проверки
  параллелизма запросы к этому экземпляру выполняются последовательно.
- **Второй пример — Cloudflare Clef.**
  [Карточка модели](https://huggingface.co/Cloudflare/clef)
  описывает модель 27B и совместимость API с Jev/SystemOne.
  Для локального примера рассматриваем runtime
  [vllm-jev](https://github.com/mode-io/vllm-jev), в списке которого есть
  `Cloudflare/clef` и `Cloudflare/clef-flash`.
  Это отдельный шаблон установки runtime; модель выбирается в профиле.
  Формат и поддержка входов проверяются для выбранной версии runtime, а не
  выводятся из формата облачного Cloudflare Workers AI.

Оба примера снаружи используют один `/v1/decisions` и тип `decision`.
Для первого завершённого контура достаточно одного реально проверенного примера;
второй показывает заменяемость модели/runtime без изменения внешнего контракта.
Версии runtime и revision весов фиксируются при подготовке установочного шаблона.
На этапе спецификации ничего не устанавливаем и веса не скачиваем.

## 6. Использование и профиль

1. «Движки → Добавить»: имя, типы, установка, executable, запуск.
2. При необходимости выбрать API-протокол и UI URL. Сохранить шаблон.
3. Установить в выбранную папку, увидеть результат и путь executable.
4. Скачать модель текущим интерфейсом либо подготовить её в UI движка.
5. Создать профиль: выбрать установку, имя, модель при необходимости, GPU и команду.
6. Запустить, открыть UI или использовать API, включить autostart.

Сохраняется единый список установок «Движок», без второго обязательного выбора.
Настройки определения находятся на странице движков. Уточнение 2026-10-29:
профиль не переопределяет типы задач, API-протокол, API URL и UI URL движка.
Порт — отдельное необязательное видимое поле редактора профиля; command
показывается без скрытых подстановок. Draft-модель задаётся прямо в command.

Host/port задаются в команде. Для известных команд сохраняется извлечение адреса;
для произвольного скрипта API URL задаётся в определении движка. Нельзя гарантированно разобрать
любой shell-скрипт. Несовпадение адреса с сервером видно в диагностике подключения.

UI URL должен быть доступен браузеру пользователя, API URL — backend.
Серверный localhost автоматически не подставляется в ссылку удалённого браузера.
Прямой доступ к UI в Docker требует обычной публикации порта в Compose;
регистрация определения не редактирует Compose скрыто.

## 7. Модели

Модель в профиле необязательна, если сервис выбирает её самостоятельно.
Профиль разрешено сохранить до загрузки весов. Обязательные файлы проверяются
перед запуском, а не при сохранении определения.

Используем существующий каталог и выбор конкретных HF-файлов/папок.
Не скачиваем все варианты квантования. Для многокомпонентной модели достаточно
инструкции с точными файлами и ожидаемыми путями, без новой системы bundles.
Пользовательские веса не перемещаются скрыто.

Известные признаки помогают фильтровать модели. Неизвестная модель допускает
ручной путь; расширение safetensors не гарантирует совместимость.
Компоненты задаются обычной конфигурацией движка или workflow, без нового
универсального языка описания моделей.

### 7.1. ComfyUI: общий каталог через extra_model_paths.yaml

Согласован второй вариант: сохраняем текущую структуру общей папки MODELS_ROOT
с каталогами репозиториев. Веса не копируются, не перемещаются в установку ComfyUI
и не требуют объединения в отдельную структуру хранения.

Neural Deck автоматически формирует штатный `extra_model_paths.yaml` по найденным
совместимым каталогам. Для категорий `diffusion_models`, `text_encoders`, `vae`
и других поддержанных категорий перечисляются реальные пути компонентов внутри
MODELS_ROOT. Произвольный HF-репозиторий не объявляется совместимым только по
расширению файлов. Список строится детерминированно, без повторов; неоднозначные
совпадения имён внутри одной категории диагностируются, не выбираются наугад.

Сгенерированный файл хранится в постоянном runtime Neural Deck, отдельно от весов
и исходников ComfyUI. Запуск получает его через
`--extra-model-paths-config <абсолютный-путь-к-файлу>`.
Пути внутри файла должны быть видны процессу: в Docker это контейнерные пути.
Файл — производная конфигурация, которую приложение может атомарно пересоздавать;
это не новый редактируемый вручную источник списка моделей.

У стандартного многомодельного профиля убирается привязка
`--models-directory {{model}}` к одной выбранной модели. `--base-directory`
не возвращается. Модель в таком профиле необязательна, а запуск UI не требует
полного комплекта весов конкретного workflow.

Разделение этапов:

- При запуске подключаются каталоги доступных компонентов всех подходящих моделей.
- При генерации workflow явно выбирает модель, энкодеры, VAE и другие компоненты.
- Для вызова через наш image API используется настроенный workflow с явными
  компонентами; отсутствие нужных весов относится к этой операции, а не ко всему UI.

Файл обновляется перед запуском и после изменения каталога моделей. В первом
варианте реализации новые пути применяются при следующем запуске ComfyUI:
показываем необходимость перезапуска, но не прерываем генерацию автоматически.
Запись нового YAML сама по себе не считается hot reload работающего процесса.

Загрузки через Neural Deck сохраняются в MODELS_ROOT. Эта настройка отвечает
за поиск существующих моделей; она не гарантирует каталог записи произвольного
загрузчика/custom node ComfyUI. Поддержка таких загрузчиков требует отдельной
настройки и не должна приводить к скрытому копированию весов.

Приёмка: два совместимых набора image/video в разных каталогах MODELS_ROOT видны
одному ComfyUI; workflow используют каждый набор без изменения команды и без
перезапуска между генерациями. Проверяются сохранение исходных путей весов и
понятная диагностика неполного набора. Новая папка после запуска получает статус
«потребуется перезапуск», а не ложное обещание немедленной доступности.

Основа: [официальный пример конфигурации](https://github.com/Comfy-Org/ComfyUI/blob/master/extra_model_paths.yaml.example)
и [штатная загрузка путей](https://github.com/Comfy-Org/ComfyUI/blob/master/utils/extra_config.py).

## 8. Одновременная работа и автозапуск

Используем текущие ProcessManager, GPU assignment, логи и autostart.
Несколько профилей имеют разные порты и назначенные пользователем ресурсы.
Одна установка может использоваться несколькими процессами, если движок это
допускает; конфликты порта/общей рабочей папки не скрываются.
Один ComfyUI может закрывать image и video в собственном UI без двух процессов.

При старте портала поднимаются отмеченные профили. Сначала обнаруживаются
сохранившиеся экземпляры, затем запускаются недостающие; дубли не создаются.
Ошибка одного не блокирует остальные. Ручная остановка не отменяется до
следующего явного запуска или нового старта портала.
Автозапуск не скачивает веса и не устанавливает зависимости скрыто.

Готовность проверяется простым HTTP-запросом или готовой проверкой протокола.
Если проверка не задана: «процесс запущен, готовность API не проверена».
Живой PID не достаточен для готовности маршрута. Сохраняются текущие таймауты
и диагностика; отвечать на /v1/models не обязан каждый движок.

Не вводим новый supervisor framework, DAG зависимостей, scheduler GPU,
автовыгрузку моделей и экран Stacks. Несколько независимых профилей с autostart
достаточны для первого контура. Одновременная работа требует подходящих ресурсов;
вместимость всех моделей на любой GPU не обещается.

## 9. Изменения текущего проекта

| Область | Изменение |
|---|---|
| Схемы engines/profiles | Строковый engine ID, types, optional model, подключение |
| engines | YAML registry вместо статического списка, общая установка и проверка executable |
| profiles | Выбор установки, сохранённая команда, порт, подготовленность |
| process | Запуск по определению, generic readiness вместо engine_id == image |
| proxy | Готовые protocol handlers, operation routing, audio endpoints |
| models | Фильтрация без фиксированного перечня движков |
| frontend | Динамический список, редактор определения, кнопка UI |

Это изменения существующего приложения, без дополнительных платформенных
микросервисов и ML-зависимостей backend. Пять существующих движков и ComfyUI
используют тот же формат, что пользовательские.

Миграция image → comfyui сохраняет installation/profile references и работающие
image API routes. Перед миграцией сохраняется копия файлов профилей.
Миграция не отключает действующие подключения и не переносит веса.

## 10. Этапы и критерии завершения

### 10.1. Выбор моделей и сервисов

Согласованные направления и результаты исследования на 2026-10-12:

| Направление | Выбор |
|---|---|
| TTS | Qwen3-TTS — основной локальный вариант до доступности локальной Qwen-Audio-3.1-TTS-Next |
| ASR | NVIDIA; основной кандидат `nvidia/nemotron-3.5-asr-streaming-0.6b` |
| Embeddings | Google EmbeddingGemma 2 — основной мультимодальный вариант; `Qwen/Qwen3-VL-Embedding-2B` — альтернатива |
| Image/video | ComfyUI; видео пока только через его собственный UI/API |
| Decision | Strands Decider 2B — выбранный первый пример; Clef остаётся альтернативой |
| Text | Существующие LLM-движки и выбранная пользователем модель профиля |

Назначение GPU и доступные модели определяются существующими профилями,
командами запуска и visible devices, включая `CUDA_VISIBLE_DEVICES`.
Фиксированная схема «тип задачи → конкретная GPU» в спецификацию не закладывается.

**Qwen3-TTS.** По уточнённому выбору пользователя основной локальный TTS —
[Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS). Он заменяет ранее выбранный
NVIDIA TTS в первом контуре; выбор NVIDIA для ASR остаётся без изменений.
Конкретный checkpoint и режим синтеза фиксируются при подготовке шаблона профиля.
Serving должен предоставить наш `/v1/audio/speech` через готовую совместимую
обёртку или узкий адаптер. Собственный UI можно использовать напрямую;
его наличие не считается подтверждением OpenAI-совместимости API.

**NVIDIA ASR.**
[Nemotron 3.5 ASR Streaming 0.6B](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-0.6b)
имеет локальные веса; русский указан среди transcription-ready языков.
Первый сценарий портала — транскрибация файла через `/v1/audio/transcriptions`;
realtime-протокол не обязателен для завершения. Версия локального serving
фиксируется при подготовке шаблона, модель и её HTTP-сервер не смешиваются.

**Мультимодальные embeddings.** По уточнённому решению пользователя основной
вариант — [Google EmbeddingGemma 2](https://blog.google/innovation-and-ai/technology/developers-tools/embeddinggemma-2/),
выпущенная 6 октября 2026 года: 740 млн параметров, открытые веса, Apache-2.0,
текст, изображения, аудио и видео в общем векторном пространстве.
Поддерживаемые размерности — 128, 256, 512 и 768. Конкретные checkpoint,
ревизия и локальный serving фиксируются при подготовке шаблона профиля.
Заявленные возможности модели не означают, что каждый HTTP-сервер
поддерживает все её модальности: это проверяется для выбранного runtime.

[Qwen3-VL-Embedding-2B](https://huggingface.co/Qwen/Qwen3-VL-Embedding-2B)
остаётся альтернативой через отдельный профиль: текст, изображения и видео,
открытые веса, Apache-2.0; аудио этот вариант не покрывает.
Смена модели не является прозрачной заменой эмбеддингов в существующем индексе:
разные модели используют разные векторные пространства.

Приёмка embeddings должна включать текст и изображение в одном векторном
пространстве, а не только текстовый запрос к мультимодальной модели.
Текст сохраняет стандартный `/v1/embeddings`. Для изображений, аудио и видео используется
документированный media-вход выбранного serving; он не объявляется стандартным
OpenAI text embeddings input. Точный media-контракт адаптера фиксируется при
подготовке шаблона; поддержка текстовых embeddings сервером сама по себе
не подтверждает поддержку мультимодального входа. Text+image обязательны
для первого мультимодального примера. Аудио и видео включаются в возможности
профиля после проверки соответствующих входов выбранного serving;
до этого они не объявляются доступными через прокси.

**Новая Qwen Audio.** Пользователь указал актуальную Qwen-Audio-3.1 как возможную
дальнейшую альтернативу. В официальной документации Alibaba Cloud присутствует
[Qwen-Audio-3.1-TTS-Next](https://www.alibabacloud.com/help/en/model-studio/qwen-audio-3-1-tts-next)
и другие варианты семейства. Подтверждено наличие облачного предложения;
доступность официальных скачиваемых весов 3.1 данным исследованием не установлена.
Не включаем её в обязательный локальный контур до подтверждения весов и runtime.
До подтверждения локальных весов и runtime Qwen-Audio-3.1-TTS-Next используем
Qwen3-TTS как основной TTS. Облачную 3.1 не подставляем вместо локальной модели;
будущий переход оформляется новой установкой/профилем без изменения общего API.

### 10.2. Порядок реализации

1. Перенести существующие движки в YAML и поддержать динамическую регистрацию.
2. Добавить generic launch/readiness, UI URL и выбор протокола.
3. Подключить TTS/ASR и Decisions endpoints, Jev adapter и operation routing.
4. Подготовить конкретные шаблоны серверов и инструкции моделей для всех семи
   направлений, включая video workflow.
5. Когда пользователь разрешит выполнение, проверить реальные запросы,
   одновременный запуск и autostart на согласованной машине.

Точные serving-версии, модели и варианты под GPU выбираются при подготовке
шаблонов. Совместимость не считается проверенной на основании наличия типа.
Источники предыдущего исследования:
[ComfyUI](https://github.com/Comfy-Org/ComfyUI),
[Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS),
[faster-whisper](https://github.com/SYSTRAN/faster-whisper),
[Text Embeddings Inference](https://github.com/huggingface/text-embeddings-inference).
Библиотека и готовый HTTP-сервер различаются; выбранный launcher фиксируется явно.

Готово, когда новый сервис с известным протоколом добавляется без изменения кода,
все семь направлений дают результат, несколько профилей работают одновременно,
autostart поднимает отмеченные сервисы, собственный UI работает без обязательной
модели и подключения к прокси. Одних шаблонов и бейджей недостаточно.

За рамками: packages/bundles/recipes, произвольный API mapping, SDK плагинов,
общая очередь задач, realtime sessions, диаризация, музыка, распределённый
scheduler и унифицированный video endpoint. Обычный запуск внешних сервисов
таких типов уже возможен через тот же механизм регистрации.

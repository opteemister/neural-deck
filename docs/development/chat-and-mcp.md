# Чат, внутренние инструменты и внешний MCP

## Ответственность

Внутренние инструменты чата (`generate_image`, `edit_image`, `generate_video`,
`get_image`) — часть бизнес-логики приложения. Модель выбирает их через
function calling внутри `ChatService`. Здесь же находятся инструкции модели,
подготовка PDF, владение вложениями, история, ограничения шагов, выполнение
генераций и восстановление длительных запросов.

Внешние MCP-инструменты — технические адаптеры для внешнего клиента. Они
проверяют контракт транспорта и вызывают общие прикладные сервисы. Их каталог
не является каталогом внутренних инструментов модели; совпадающие имена
не означают общий инструмент. Внутренние инструменты не публикуются через
MCP автоматически, а модель чата не получает инструменты управления сервером.

## Общий путь чата

`nd_chat_send`, `nd_chat_get`, `nd_chat_stop` — обёртки над тем же `ChatService`, который обслуживает HTTP API
`/api/v1/chat` и frontend. Они используют ту же схему `ChatTurnRequest`, историю,
модели, настройки генерации, вложения и результаты. Подготовка PDF, выбор
операции по модели и генерация медиа не реализуются повторно в MCP или UI.

Новые возможности чата добавляются в общий сервис и становятся доступны
через оба транспорта. Проверки должны подтверждать этот общий путь, включая
PDF и вызовы внутренних инструментов. Отдельный MCP-инструмент для конкретной
операции допустим как обёртка над существующим сервисом, без копирования его
бизнес-логики.

`nd_chat_send` запускает сохраняемый запрос и возвращает снимок диалога. `nd_chat_get`
читает его состояние, `nd_chat_stop` останавливает только этот диалог. Закрытие
MCP-вызова или страницы не отменяет выполняемую генерацию. Повтор отправки
использует исходные идентификаторы диалога и запроса; автоматическая повторная
генерация после потери ответа запрещена. Результат относится к исходному
диалогу. MCP annotations описывают внешнюю операцию, а не расширяют права
внутренней модели.

Внешний OpenAI-совместимый `/v1` сохраняет свой контракт и отдельный порт;
унификация UI и MCP не превращает его в агентный чат.

## Хранение чатов

История, вложения и состояние запросов чата хранятся отдельно в
`<NEURAL_DECK_DATA_ROOT>/data/chats.sqlite3`. Основная база
`data/neural-deck.sqlite3` не содержит чатовых таблиц.

SQLite создаёт отсутствующий файл при подключении; `CREATE TABLE IF NOT EXISTS`
на подключении создаёт схему. Для чатов используется стандартный `NullPool`,
чтобы не удерживать соединения с удалённым файлом. Проверок inode, фонового
наблюдения и автоматического исправления повреждённой базы нет.

Удаление файла после завершения текущих запросов очищает тестовые чаты.
Следующий запрос или запуск приложения создаёт пустую базу автоматически.
Удалённый диалог и его вложения возвращают обычный 404; отправка нового
сообщения создаёт новый диалог, даже если в URL остался прежний ID.
Сохранённая в памяти история не восстанавливается поверх очищенной базы.
Готовые файлы ComfyUI остаются на стороне ComfyUI.

По прямому решению пользователя миграция `0011_drop_old_chat_tables`
при запуске новой версии удаляет старые `chat_conversations` и
`chat_attachments` из основной базы через `DROP TABLE IF EXISTS`.
Переноса истории и создания резервных копий при запуске нет.

Список и удаление диалогов обслуживаются тем же `ChatService`: HTTP
`GET /api/v1/chat`, `DELETE /api/v1/chat/{id}` и внешние MCP-инструменты
`nd_chat_list`/`nd_chat_delete`. Удаление прекращает запись текущего задания
до очистки истории и вложений, чтобы фоновая задача не восстановила чат.
Удаление не распространяется на другие диалоги и общие файлы ComfyUI.

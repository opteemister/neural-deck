# Быстрый старт и устройство

Черновик. Дополняет `README.md` для нового пользователя: как запустить за
несколько минут и что означают ключевые термины. Команды, пути и имена
переменных взяты из `docker-compose.yml`, `.env.example`, `.env.local`,
`deploy.env.example` и `DEPLOYMENT_RULES.md`.

> [!NOTE]
> Проект в состоянии версии-ноль, спецификации в `docs/specs/` могут
> уточняться. Состав переменных и пути запуска фиксирует `DEPLOYMENT_RULES.md`.

## Три способа запустить

| Способ | Когда | Основной файл |
| --- | --- | --- |
| Docker на машине разработчика | macOS/Linux, быстрая проверка без установки зависимостей в ОС | `.env.local` (отслеживаемые недефолтные значения) |
| Нативная установка локально | Linux с systemd, явное подтверждение `Y/N` | `.env` |
| Удалённое развёртывание по SSH | целевая машина LXC/Linux | `deploy.env` + `.env` |

## Docker: запуск за пару минут

Нужен только Docker. Зависимости Python и frontend ставятся внутри образа при
сборке, в ОС разработчика их держать не обязательно.

```bash
# из корня репозитория
docker compose --env-file .env.local up --build
```

Явный `--env-file .env.local` нужен, чтобы Compose не читал продакшен-`.env`.
Локальные значения и порты фиксированы в `.env.local` и `docker-compose.yml`:

- `3000` — интерфейс управления и management API: http://127.0.0.1:3000
- `8080` — общий OpenAI-совместимый API `/v1`
- `8188` — собственный web-интерфейс движка (например, ComfyUI)

Данные монтируются из соседних каталогов: `./data`, `./models`, `./logs`. Для
первого запуска их создавать не нужно — достаточно самого репозитория.

Проверка, что сервис поднялся:

```bash
curl -I http://127.0.0.1:3000          # интерфейс управления
curl http://127.0.0.1:8080/v1/models   # API /v1; маршруты зависят от запущенных профилей
```

Остановка: `Ctrl+C`, затем `docker compose down`.

## Нативная и удалённая установка

Нативная установка поддерживает Linux с systemd и `apt-get` (Debian/Ubuntu) или
`dnf` (Fedora/RHEL); нужны root или `sudo` и доступ в интернет. Драйверы NVIDIA,
CUDA и сами движки при этом не ставятся — их ставят отдельно через шаблоны в
интерфейсе (см. `docs/engine-installation.md`).

1. Заполнить runtime-конфиг `.env` (обязательные значения по умолчанию пусты):

   ```bash
   cp .env.example .env
   ```

   - `NEURAL_DECK_DATA_ROOT` — корень постоянных данных;
   - `HOST`, `PORT` — интерфейс и management API (обычно `0.0.0.0` и `3000`);
   - `OPENAI_PORT` — отдельный слушатель OpenAI-совместимого API (`8080`);
   - `MODELS_ROOT`, `LOG_ROOT` — при пустых значениях выводятся из
     `NEURAL_DECK_DATA_ROOT`.

2. Для удалённой машины создать `deploy.env`:

   ```bash
   cp deploy.env.example deploy.env
   ```

   - `DEPLOY_TARGET` — SSH-хост; оставьте пустым для локальной установки с
     интерактивным подтверждением;
   - `DEPLOY_PATH` — каталог установки на целевой машине.

3. Запустить установщик:

   ```bash
   bash scripts/deploy.sh      # сборка и регистрация службы на целевой машине
   ```

Полезные команды:

```bash
bash scripts/status.sh            # состояние службы
bash scripts/uninstall.sh --scan  # обследование и план удаления
bash scripts/uninstall.sh         # план → подтверждение Y/N → выполнение
```

Удаление меняет только установку: исходники, локальный `.env`, рабочие пути и
веса моделей остаются на месте. Подробности — `DEPLOYMENT_RULES.md` и
`docs/specs/2026-10-10-service-uninstall.md`.

## Файлы конфигурации

| Файл | Для чего | Передаётся контейнеру локально |
| --- | --- | --- |
| `.env` | runtime-настройки нативной службы; обязательные значения без дефолтов | нет |
| `.env.local` | отслеживаемые недефолтные значения для локального Docker Compose | да |
| `deploy.env` | SSH-цель установки/удаления: `DEPLOY_TARGET`, `DEPLOY_PATH` | нет |

## Как устроено: модель → движок → профиль → `/v1`

Цепочка, из которой состоит работа приложения:

**Модель → Движок → Профиль → Экземпляр → маршрут `/v1`**

- **Модель** — скачанные веса из локального каталога или Hugging Face; можно
  выбрать нужный квант и компоненты, неполный набор не считается ошибкой.
- **Движок** — YAML-определение с установкой в отдельный каталог/venv
  (например, llama.cpp, vLLM, ComfyUI). У движка свои системные требования.
- **Профиль** — конкретная команда запуска модели выбранным движком с GPU,
  `environment` и портами. Профили хранятся в файлах отдельной папки и
  пригодны для ручного редактирования; SQLite их не хранит.
- **Экземпляр** — запущенный процесс профиля; за ним идёт наблюдение
  (CPU/RAM/GPU, метрики, логи).
- **Маршрут `/v1`** — единый OpenAI-совместимый API поверх экземпляров, со
  стабильными `profile_id`, алиасами и порядком кандидатов.

Ключевые термины из `README.md`:

- **Management origin** — адрес сервиса в браузере; на нём же находится `/mcp`.
  Отдельный от API `/v1` и от `OPENAI_PORT`.
- **Алиас** — короткое имя маршрута прокси; назначается автоматически или вручную.
- **Типы задач** — `text`, `embeddings`, `TTS`, `ASR`, `image`, `video`,
  `decision`. **Протоколы** включают OpenAI-compatible, ComfyUI и Jev-compatible.
- **Внутренний чат** обращается к backend на том же origin и не использует
  внешний URL из шапки (подробности — `docs/openai-endpoint.md`).

## Проверки (для разработки)

Статические проверки и тесты можно запустить вне Docker, если на машине есть
`uv` и `pnpm`:

```bash
bash verify/run-verify.sh   # pytest, ruff, mypy, frontend test/lint/typecheck/build
```

Проверки выполняются офлайн и не меняют зависимости в checkout.

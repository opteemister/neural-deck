# Совместимость API Neural Deck с LiteLLM

**Историческое исследование.** Промежуточные архитектурные предложения ниже
заменены решением пользователя о простом прокси. Актуальные требования —
[простая архитектура](../specs/2026-10-27-unified-provider-api.md) и
[список API для тестирования](../specs/2026-10-27-unified-provider-api.md#10-api-для-тестирования).
Универсальные mappings/координатор, сроки хранения и дополнительные pipeline
из прежнего обсуждения не являются текущими требованиями.

Дата проверки: 27 октября 2026 года.

Статус: исследование и список для согласования. Это не утверждённая
спецификация; реализация не начата.

По результатам обсуждения подготовлены [общая архитектура](../specs/2026-10-27-unified-provider-api.md)
и [контракты API](../specs/2026-10-27-unified-provider-api.md#10-api-для-тестирования).
Они развивают этот исследовательский список и являются черновиком целевой
спецификации; первоначальный список ниже не ограничивает их объём.

Ветка: `codex/multimodal-api-compatibility`, создана от локальной `main`
на коммите `9ed262d`. На момент создания локальная `main` опережала
`origin/main` на один коммит; обновление remote в этой задаче не выполнялось.

## Границы проверки

Проверены исходники Neural Deck, актуальная документация LiteLLM и отдельные
адаптеры в upstream `main`. Версия установленного у пользователя LiteLLM и
её конфигурация не проверялись. Сквозных запросов через работающий LiteLLM
к локальным моделям не было. Наличие обработчика в коде не означает
подтверждённую работу конкретной модели.

Цель: использовать уже принятые контракты провайдеров. Для большинства
операций это OpenAI; для OCR LiteLLM использует формат Mistral. Jev — модель
решений, для которой различаются публичный Decisions API и нативный System One.

## Согласованное направление после обсуждения

Neural Deck должен предоставлять максимально широкое покрытие существующих
форматов API для выбранных возможностей. Несколько стандартных представлений
одной операции могут быть доступны одновременно. В частности, наружу нужны
и `POST /v1/decisions`, и `POST /v1/systemone`.

Клиент или LiteLLM выбирает нужный формат подключения, но во всех случаях
обращается к Neural Deck. Несколько коннектов LiteLLM под разные типы и
провайдерские форматы — ожидаемый сценарий. Особенности ComfyUI и конкретного
serving преобразуются внутри Neural Deck.

В настройках прокси задаётся связь публичной модели и операции с профилем,
workflow и отображением параметров. Для изображений и видео это позволяет
выбрать разные workflow для generations, edits, variations и других операций.
Стандартные пути API сохраняются; выбор workflow не требует собственного
публичного формата запроса. Точная схема конфигурации и UI ещё не утверждены.

Хранение ID задач, артефактов изображений и видео, статусов и результатов,
получение файлов и восстановление после рестарта входят в сопутствующие
доработки задачи. Их отсутствие в текущем коде не является основанием
сокращать целевое покрытие API. Внешние поля и операции следуют выбранному
стандарту: внутренний ID изображения не требует добавлять собственное поле
`id` в стандартный Images response.

Собственные расширения не должны становиться обязательными для этих
сценариев. Существующий `/v1/embeddings/media` не выбирается целевым форматом
интеграции без сверки с уже существующими контрактами мультимодальных embeddings.
Реализация по-прежнему начинается после утверждения спецификации.

## 1. Предварительная таблица операций

| Возможность | Внешний контракт Neural Deck | Вход и результат | Состояние в текущем коде |
|---|---|---|---|
| Список моделей | `GET /v1/models` | OpenAI `object: list`, `data[].id` | Есть |
| Генерация изображений | `POST /v1/images/generations` | JSON: `model`, `prompt`, `n`, `size`; ответ `created`, `data[]` с `b64_json` либо `url` | Есть OpenAI forwarding и ComfyUI-адаптер с ограниченным набором полей |
| Редактирование изображений | `POST /v1/images/edits` | Multipart: `model`, `prompt`, одно/несколько изображений, опциональная `mask`; ответ Images | Маршрута нет |
| Вариации изображений | `POST /v1/images/variations` | Multipart: изображение и параметры; ответ Images | Маршрута нет; включать только при поддержке моделью |
| Генерация видео | `POST /v1/videos` | `model`, `prompt`, `seconds`, `size`, опциональный `input_reference`; ответ — объект задачи | Маршрута нет |
| Статус видео | `GET /v1/videos/{video_id}` | Объект задачи с состоянием, прогрессом и ошибкой | Маршрута нет |
| Скачивание видео | `GET /v1/videos/{video_id}/content` | Бинарный файл видео | Маршрута нет |
| OCR документов | `POST /v1/ocr` | Mistral: JSON `model`, `document`; ответ `pages[].markdown`, `model`, `usage_info` | Маршрута и отдельной операции OCR нет |
| Решения / Jev | `POST /v1/decisions` | JSON `model`, `input`, `questions[]`; типизированные `answers[]` | Есть адаптация в `/v1/systemone`; требуется сверка ответа с LiteLLM |
| Решения / System One | `POST /v1/systemone` | JSON `model`, `state`, именованные `questions`; именованные `answers` | Добавить публичный маршрут и общий выбор профиля с Decisions |

| Синтез речи | `POST /v1/audio/speech` | JSON `model`, `input`, `voice`, опции; аудиобайты с корректным MIME | Есть forwarding и экспериментальный TTS-адаптер |

## 2. Как LiteLLM должен обращаться к Neural Deck

Для OpenAI-совместимых операций исходный вариант подключения —
`model: openai/<публичное-имя-Neural-Deck>` и
`api_base: http://<neural-deck>:<OPENAI_PORT>/v1`.
Endpoint добавляет клиент LiteLLM; полный путь операции в `api_base` не нужен.
OpenAI-клиент требует значение API key, даже если целевой сервер не проверяет
его. Реальное требование авторизации нужно согласовать с конфигурацией сервера.

Пример конфигурации для последующей проверки, не результат живого теста:

```yaml
model_list:
  - model_name: nd-image
    litellm_params:
      model: openai/qwen-image-turbo
      api_base: http://neural-deck:8080/v1
      api_key: os.environ/NEURAL_DECK_API_KEY
```

Источник: [OpenAI-Compatible Endpoints](https://docs.litellm.ai/docs/providers/openai_compatible).

Для OCR нужен соответствующий Mistral-совместимый маршрут провайдера LiteLLM;
одного префикса `openai/` недостаточно. Точный `mistral/<имя>`, построение URL
при custom `api_base` и принятие произвольного имени локальной OCR-модели
остаются предметом проверки на выбранной версии LiteLLM.

Для Decisions можно проверять OpenAI-провайдера, направленного на наш
`/v1/decisions`. Указывать `typesafe/` поверх этого маршрута нельзя без
соответствующего System One API: такой провайдер ожидает `/v1/systemone`.
LiteLLM умеет преобразовывать клиентский формат между двумя маршрутами.
По решению пользователя Neural Deck предоставляет оба формата самостоятельно;
наличие преобразования в LiteLLM не заменяет наш публичный System One API.

## 3. Изображения: уточнения к исходному предложению

Предложение пользователя с `model`, `prompt`, `n`, `size`, `quality`,
`background`, `output_format` соответствует направлению Images API.
Поддержку конкретных значений определяет модель/workflow.

Уточнение: `quality`, `background`, `output_format` отсутствуют в текущей
схеме нашего ComfyUI-адаптера. Это не установленное ограничение LiteLLM.
`quality` указан в документации LiteLLM Image Generations, `quality` и
`background` — в списке поддерживаемых параметров OpenAI Image Edit adapter.
Для `output_format` и каждого маршрута нужно проверить фактическую передачу
в закреплённой версии LiteLLM. На стороне Neural Deck эти стандартные поля
входят в целевой контракт и реализуются через workflow или обработку результата.

Источники: [LiteLLM Image Generations](https://docs.litellm.ai/docs/image_generation),
[OpenAI Image Edit adapter LiteLLM](https://github.com/BerriAI/litellm/blob/main/litellm/llms/openai/image_edit/transformation.py).

Предлагается различать:

- `output_format` — формат файла: PNG/JPEG/WebP;
- `response_format` — способ возврата результата: `b64_json` или `url`,
  если выбранный контракт модели поддерживает этот параметр;
- `background` — требование к фону; непрозрачный результат нельзя выдавать
  за исполненное `transparent`;
- `quality` — режим качества с явно заданным отображением в workflow.

`b64_json` содержит base64 самих байтов изображения, без префикса data URI.
Нужно поддержать способы возврата, предусмотренные выбранным Images-контрактом,
включая base64 и URL там, где он определён. Для URL сопутствующая доработка —
хранение артефактов и адрес, доступный внешнему клиенту: сейчас ComfyUI-адаптер
возвращает относительный `/v1/images/{asset_id}`.

Edits должны обрабатывать одно и несколько входных изображений и маску
только там, где это умеет workflow. Вариации — отдельная возможность, которую
нельзя автоматически объявлять для любой img2img-модели. LiteLLM помечает
вариации как beta; наличие SDK-функции само по себе не подтверждает нужный
маршрут в установленном Proxy.

Источники: [OpenAI Image API](https://developers.openai.com/api/docs/guides/image-generation),
[LiteLLM image edits](https://docs.litellm.ai/docs/image_edits),
[LiteLLM variations](https://docs.litellm.ai/docs/image_variations).

В текущем ComfyUI-коде `ImageGenerationRequest` запрещает неизвестные поля;
`quality`, `background`, `output_format` отсутствуют. Есть собственные
`transparent`, `steps`, `seed`, `image` в JSON. Граф строится функцией
`build_workflow`, затем сохраняется в runtime. Это не библиотека произвольных
сохранённых workflow с декларативным сопоставлением параметров.

Соответствие `model + операция → сохранённый workflow` входит в направление
задачи по решению пользователя. Внешние клиенты должны знать публичное имя модели, а не
номера узлов ComfyUI. OpenAI-совместимые image-серверы также должны оставаться
доступны через общий контракт, без обязательной привязки к ComfyUI.

Локальные основания: `backend/app/schemas/image.py`,
`backend/app/image/service.py`, `backend/app/image/workflow.py`,
`backend/app/proxy/service.py`.

## 4. Видео и OCR

Для генерации видео подтверждённый основной цикл — создание, статус, скачивание.
В сопутствующие доработки входят время жизни задачи и файла, поведение после рестарта,
закрепление ID за профилем/экземпляром и выдачу ошибок. GET-запросы по ID
не содержат `model`, поэтому обычного выбора модели для каждого запроса
недостаточно. JSON и multipart с reference image нужно сверять именно на
границе LiteLLM → Neural Deck. List, remix, edits, extensions и другие
существующие операции нужно включить в полный инвентарь для согласования
спецификации; создавать искусственное ограничение тремя маршрутами не нужно.

Документация LiteLLM содержит противоречивые сокращённые названия video routes;
для списка выше взяты её реальные примеры `/v1/videos/{video_id}` и
`/content`, совпадающие с [API reference LiteLLM](https://docs.litellm.ai/api-reference).

Для OCR базовый JSON: `document.type` равен `document_url` или `image_url`,
соответствующее поле содержит URL или data URI. Результат — страницы Markdown
и статистика обработки. `pages`, извлечённые изображения и аннотации —
согласуемые опции. Multipart, принимаемый самим LiteLLM, не доказывает,
что в таком же виде запрос уходит провайдеру. PDF/изображения не означают
автоматической поддержки DOCX/XLSX.

Источник: [LiteLLM OCR](https://docs.litellm.ai/docs/ocr).

Понимание изображения/видео моделью — отдельный сценарий от генерации.
Для изображений следует проверить мультимодальные сообщения через уже
существующие `/v1/chat/completions` или `/v1/responses` с подходящей моделью.
Формат видео на входе зависит от провайдера и движка; универсальный контракт
в рамках этой проверки не установлен.

## 5. Существующие операции: конкретные риски совместимости

### Decisions / Jev

Текущий код преобразует `predicate → noul`, `choice` и `score`, принимает
только текст и возвращает массив `answers`. Публичного `/v1/systemone` нет.
По решению пользователя его нужно добавить: клиентам доступны оба стандартных
формата через один Neural Deck. Они используют общий выбор профиля/алиаса,
журналирование и проверку возможностей; запрос и ответ имеют формат выбранного
endpoint. Нативные допустимые поля System One нельзя терять из-за ненужного
преобразования через более узкое представление другого API.

Найдены точки для обязательной сверки:

- Neural Deck опускает `usage`, если upstream не прислал полный набор полей.
  В проверенном upstream LiteLLM `OpenAIDecisionResponse.usage` обязателен.
  Это потенциальный отказ разбора ответа даже при успешном инференсе.
- Наши `choice`/`score` допускают отсутствие `confidence`, тогда как
  текущие модели ответа LiteLLM требуют это поле. Нужно сверить допустимость
  `null` и фактические ответы выбранного serving.
- Отдельно сверить ограничения на число вопросов, `refusal` и неподдержанные
  мультимодальные поля. Изображения и `box` не входят автоматически в базовую
  текстовую совместимость.

Нельзя подставлять выдуманные токены или вероятности ради успешного парсинга.
Нужен согласованный способ получения/нормализации достоверного usage либо
другой поддержанный провайдером контракт.

Источники: [типы LiteLLM](https://github.com/BerriAI/litellm/blob/main/litellm/types/decisions.py),
[OpenAI Decisions adapter](https://github.com/BerriAI/litellm/blob/main/litellm/llms/openai/decisions/transformation.py).
Локально: `backend/app/proxy/decisions.py`, `backend/app/proxy/operations.py`.

### Транскрибация

Общий proxy уже передаёт multipart и дополнительные текстовые поля.
Экспериментальный Nemotron serving принимает только `json` и `text`.
Проверенный OpenAI Whisper adapter LiteLLM при отсутствии явного
`response_format` подставляет `verbose_json`, чтобы получить duration.
Нужны проверка выбранного transport и решение: поддержать этот формат
с реальными метаданными либо явно настроить поддерживаемый формат.
Timestamps, diarization, prompt, language и streaming согласуются по возможностям
модели; сейчас их нельзя считать подтверждёнными.

Источники: [Whisper adapter LiteLLM](https://github.com/BerriAI/litellm/blob/main/litellm/llms/openai/transcriptions/whisper_transformation.py),
`backend/app/proxy/router.py`, `backend/app/serving/nemotron_asr_openai.py`.

### Синтез речи

Общий proxy уже возвращает медиаданные. Экспериментальный Qwen3-TTS serving
выдаёт WAV, принимает нативные имена speakers и отвергает `speed != 1`.
Это состояние текущего адаптера, которое предстоит доработать. Целевой подход:
стандартный запрос Speech API преобразуется в возможности serving, а результат
доводится до запрошенного формата на стороне Neural Deck.

Сопутствующие доработки: кодирование/перекодирование в стандартные аудиоформаты,
правильные MIME и значения по умолчанию, конфигурируемое сопоставление voice
с нативными speakers, управление скоростью через движок или обработку звука.
Для streaming определить реальное поведение и задержку, включая возможность
генерации по частям. Имена голосов других провайдеров не означают наличие их
тембра у локальной модели; mapping должен иметь явно описанный смысл.

Формат API можно адаптировать, но отсутствующий навык модели требует
дополнительного workflow/модели/обработки. Для неисполняемых требований нужен
стандартный явный ответ об ошибке. Это правило корректности конкретной
операции, а не причина ограничивать поддержку форматов всего сервиса.

Источники: [OpenAI Speech](https://developers.openai.com/api/reference/resources/audio/subresources/speech/methods/create),
`backend/app/serving/qwen3_tts_openai.py`.
Музыка и звуковые эффекты не покрываются автоматически контрактом TTS.

### Embeddings

Текстовый `/v1/embeddings` уже существует. Serving-пример принимает строки,
возвращает float-векторы без `usage`, не поддерживает `dimensions` и
`encoding_format: base64`. Нужно сверить ожидания реального клиента и LiteLLM,
порядок batch, размерность, счётчики и ошибки неподдержанных опций.

`/v1/embeddings/media` — собственное расширение Neural Deck с `inputs`.
Обычный OpenAI-провайдер LiteLLM сам не преобразует его в этот контракт.
Мультимодальные embeddings требуют отдельного выбора совместимого формата;
в LiteLLM есть зависящие от провайдера варианты входа с изображениями.

Источники: [LiteLLM Embeddings](https://docs.litellm.ai/docs/embedding/supported_embedding),
`backend/app/serving/embeddings_openai.py`, `backend/app/proxy/router.py`.

## 6. Что уточнить в спецификации перед реализацией

1. Зафиксировать версию LiteLLM для совместимости. Текущая документация
   указывает Decisions начиная с `v1.104.2`, с исключениями отдельных dev/RC;
   это не подтверждение версии нашей установки.
2. Составить полный инвентарь существующих API для выбранных направлений:
   изображения, видео, OCR, решения, embeddings, транскрибация и генерация
   речи. Обязательно включить публичные Decisions и System One; generations,
   edits и variations изображений; операции жизненного цикла видео.
   Для каждого формата определить адаптер и выбранный способ исполнения.
   Не ограничивать инвентарь только уже реализованными маршрутами.
3. Выбрать первый профиль/serving для каждого направления и составить
   таблицу реально поддерживаемых параметров. OCR пока отсутствует и в
   реестре операций; потребуется согласовать его тип/маршрутизацию.
4. В настройках прокси определить выбор workflow по публичной модели и
   операции для изображений/видео, ссылки на workflow и mapping входов/выходов.
   По уточнению пользователя каталог и содержимое workflow читаются только
   через API ComfyUI, даже на той же машине. Содержимое не сохраняется в
   Neural Deck; кешируется только список файлов, с обновлением при каждом
   успешном чтении API и использованием кеша при недоступности.
   Размеры, quality, background и output_format должны иметь проверяемый смысл.
   Включить хранение задач и артефактов, ID, статусов, файлов, политику хранения
   и восстановление после рестарта в состав сопутствующих работ.
5. Согласовать ошибки неподдержанных параметров: предпочтительно HTTP 400
   в OpenAI envelope с указанием поля, без молчаливого отбрасывания.
   Для OCR проверить обработку этого envelope выбранным провайдером.
6. Сохранить единый `model` routing через профили/алиасы, корректный upstream
   model и ограничения возможностей конкретной операции. Наличие типа
   `image` или `video` само по себе не подтверждает все операции этого типа.
7. Сохранить внешний `/v1`, отдельный `OPENAI_PORT` и
   `VITE_OPENAI_API_BASE_URL`; внутренние UI-вызовы остаются на origin backend.
8. Приёмку проводить через закреплённый LiteLLM и выбранный serving:
   успешный результат, декодирование файлов, multipart, ошибки, timeout,
   реальные usage и проверка цепочки video по ID. Отдельно проверить
   SDK/Proxy-поддержку variations и custom base для OCR.

До согласования этих решений не менять runtime и не объявлять полную
совместимость только на основании имён маршрутов.

# Правила запуска и развёртывания

Этот документ фиксирует обязательные свойства процесса. Конкретные команды,
пути и устройство процессов будут определены в спецификации реализации.

## Локальная разработка

- На компьютере разработчика приложение собирается и запускается в Docker.
  Backend и frontend должны быть доступны в этой локальной среде без
  обязательной установки проектных зависимостей непосредственно в macOS.
- Python- и frontend-зависимости устанавливаются только при сборке Docker-
  образа. Обычный запуск готового контейнера не выполняет `uv sync`,
  `pnpm install` или первоначальную сборку frontend: он сразу запускает
  FastAPI и наблюдатель пересборки уже подготовленного frontend.
- Docker-образ не собирает и не устанавливает llama.cpp и vLLM. Движки
  устанавливаются отдельно через интерфейс управления движками при необходимости.
- Compose монтирует локальные `./data`, `./models` и `./logs` в абсолютные
  service-visible пути из `.env.local`. Продакшен-файл `.env` не передаётся
  контейнеру и не определяет локальные bind-mount или опубликованные порты. Контейнер не использует host PID
  namespace и не обнаруживает окружения macOS вне явно смонтированных путей.
- Тесты и статические проверки можно запускать вне Docker, если нужные
  инструменты уже есть на компьютере. Это не должно быть обязательным условием
  разработки.
- Нативная установка на текущую машину допускается как отдельное, явно
  подтверждённое действие, в том числе на macOS.

Локальный запуск:

```bash
docker compose --env-file .env.local up --build
```

Явный `--env-file .env.local` исключает автоматическое чтение продакшен-файла
`.env` самим Compose. Контейнер получает значения только из `.env.local`.
Локальные порты фиксированы: 3000 и 8080; bind-mount — `./data`, `./models`,
`./logs`. Интерполяция переменных из `.env` для этих параметров не используется.

## Выбор места установки

- Скрипты установки и обновления используют одну процедуру на целевой машине.
- Если задана переменная с адресом удалённого сервера, проект передаётся по
  SSH, а зависимости устанавливаются и приложение собирается на удалённой
  машине. Вместе с проектом копируется основной заполненный `.env` с
  параметрами запуска. Кэши, локальные результаты сборки, постоянные данные,
  модели и логи с компьютера разработчика не копируются.
- Если удалённый сервер не задан, скрипт предупреждает, что изменит текущую
  машину, и запрашивает интерактивный ответ `Y/N` **до любых изменений**.
  Только `Y` разрешает продолжение. `N` или отсутствие ответа отменяет
  установку. Этот режим позволяет запускать тот же скрипт из checkout на
  сервере без промежуточного копирования.
- Удалённое развёртывание не должно требовать сборки приложения или установки
  его проектных зависимостей на компьютере разработчика.
- `deploy.env` содержит только `DEPLOY_TARGET` и `DEPLOY_PATH`. Проектом для
  передачи считается checkout, из которого запущен скрипт; SSH-порт и ключи
  берутся из обычной конфигурации SSH. Процесс должен оставаться простым и
  повторяемым.
- Передаются отслеживаемые файлы checkout, а также неотслеживаемые файлы,
  которые не исключены Git и находятся в исходных каталогах `backend/app`,
  `backend/alembic`, `frontend/src` или `frontend/public`. Это позволяет
  развернуть новый модуль до первого коммита и не приводит к передаче всего
  checkout. Корневой `.env` добавляется отдельно. Неотслеживаемые `.env*`
  внутри исходных каталогов исключаются вместе с `.git`, `deploy.env`,
  локальными результатами сборки, `data`, `models` и `logs`.
- Переименованные `deploy/systemd/neural-deck.service.template` и
  `docs/design/neural-deck-reference.html` также передаются до первого коммита
  по точному списку. Удалённые из рабочего дерева файлы индекса пропускаются,
  чтобы переименование не ломало упаковку. Прочие неотслеживаемые файлы из
  `deploy` и `docs` автоматически не включаются.
- При упаковке на macOS отключаются расширенные атрибуты, ACL, файловые флаги
  и AppleDouble-метаданные. `.DS_Store`, `._*`, `__MACOSX` и системные каталоги
  macOS исключаются из списка передаваемых файлов.
- Установщик удаляет оставшиеся от предыдущих передач `._*` и `.DS_Store`
  только в каталогах исходников `backend/app`, `backend/alembic`,
  `frontend/src` и `frontend/public`. Это предотвращает чтение бинарных
  AppleDouble-файлов `._*.py` как миграций Alembic. Постоянные данные и
  окружения зависимостей этой очисткой не затрагиваются.

## Подготовка целевой машины

- Нативная автоматическая установка поддерживает Linux с systemd и пакетным
  менеджером `apt-get` (Debian/Ubuntu) либо `dnf` (Fedora/RHEL). Для передачи
  исходников заранее нужны SSH, Bash и tar. Для установки нужны права root
  либо установленный `sudo` и доступ к интернету.
- Перед сборкой устанавливаются отсутствующие системные пакеты:
  `ca-certificates`, `curl`, `tar`, `gzip`, `coreutils`, `git`, `util-linux`,
  библиотека OpenMP (`libgomp1`/`libgomp`) и `poppler-utils` для обработки PDF.
  Полное обновление ОС не выполняется.
- Отсутствующий `uv` устанавливается официальным скриптом Astral в
  `/usr/local/bin`, без изменения shell-профилей. Если имеющийся `uv` находится
  в другом месте, его бинарник копируется в `/usr/local/bin`, чтобы systemd
  мог использовать его независимо от окружения SSH-сессии.
- Если Node.js отсутствует, его версия ниже 20, либо отсутствует
  npm, устанавливается официальный бинарный дистрибутив Node.js `22.23.3`
  с npm в `/usr/local`. Поддержаны архитектуры `x86_64` и `aarch64`.
  Архив сверяется с официальным `SHASUMS256.txt` до распаковки.
- Устанавливается `pnpm@9.15.9`, если его нет или версия отличается; та же
  версия используется в Docker. Установка выполняется через npm в `/usr/local`.
- `uv sync --python 3.12 --locked --no-dev` использует подходящий Python либо
  загружает его автоматически. Зависимости backend, frontend, сборка и
  миграции выполняются от пользователя сервиса. Каталоги `backend` и
  `frontend` передаются этому пользователю; постоянные данные не переносятся.
- После подготовки выполняются миграции, регистрация/перезапуск systemd
  и проверка доступности приложения. При обычном старте службы установка
  зависимостей и сборка не выполняются.
- Драйверы NVIDIA, CUDA и движки не устанавливаются при деплое приложения.
  Движки устанавливаются отдельно через редактируемые шаблоны в интерфейсе;
  системные требования этих шаблонов описаны в `docs/engine-installation.md`.

## Работа установленного приложения

- Необходимые процессы регистрируются в менеджере служб целевой системы и
  автоматически запускаются после перезагрузки машины или LXC. Они не должны
  зависеть от открытой SSH-сессии. На Linux используется systemd; для явно
  подтверждённой нативной установки на macOS — launchd. Служба работает от
  того же системного пользователя, который вручную запускает движки.
- На целевой машине работает один сервис приложения: backend отдаёт собранный
  frontend и API управления на `PORT` (локально 3000), а общий OpenAI-совместимый
  API — на отдельном `OPENAI_PORT` (8080 по умолчанию). Оба HTTP-слушателя
  используют один реестр процессов и одну конфигурацию профилей.
  Для сервиса определены запуск и остановка.
- Чаты хранятся отдельно в `<NEURAL_DECK_DATA_ROOT>/data/chats.sqlite3`;
  основная база — `data/neural-deck.sqlite3`. Файл чатов можно не переносить
  при развёртывании: приложение создаст его автоматически.
- Основной `.env` копируется с проектом. Файлы профилей запуска, модели, база
  данных и логи хранятся отдельно от каталога проекта; обновление не должно
  их перезаписывать.
- После установки скрипт проверяет состояние службы и ответ приложения.
  Ошибка любой проверки означает неуспешный деплой и показывается явно.
- Отдельная команда статуса без изменений на сервере использует тот же выбор
  цели: SSH при заданном удалённом сервере либо текущую машину. Она сообщает
  состояние службы и доступность приложения и явно показывает ошибки SSH и
  проверки приложения.

Каталоги релизов и архивы сборки для первого процесса развёртывания не
требуются.

## Независимые модели

Нативный установщик готовит пользовательский systemd-менеджер и запускает
модели как отдельные временные units. Основной сервис сохраняет
`KillMode=control-group` для служебных операций. Units моделей не включаются
в автозапуск ОС; после перезагрузки модели запускает только механизм
`autostart` профилей backend. Docker использует обычные процессы.
Подробности: `docs/model-process-lifecycle.md`.

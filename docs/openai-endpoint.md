# Адрес OpenAI API в интерфейсе

## Внешний API: жёсткое требование

Копируемый URL в шапке и внешний контракт `/v1` предназначены для подключения
сторонних клиентов к Neural Deck. Исправления внутреннего чата не должны
менять эти маршруты, отдельный `OPENAI_PORT` или адрес в шапке.

По умолчанию внешний URL имеет вид
`http://<локальный IP приложения>:<OPENAI_PORT>/v1`, где `OPENAI_PORT` по
умолчанию равен `8080`. Backend отдаёт URL через `GET /api/v1/openai-endpoint`.
IP берётся из локального адреса сокета, принявшего запрос: например,
`http://192.168.1.50:8080/v1`. Домен страницы, `Host`, `X-Forwarded-Host` и
`VITE_API_BASE_URL` не используются для выбора IP. Если локальный IP
недоступен, API возвращает `machine_ip_unavailable`; подстановок нет.

При запуске внутри Docker это IP контейнера. Если он недоступен браузеру,
нужный адрес задаётся явно через `VITE_OPENAI_API_BASE_URL`.

Для переопределения при сборке frontend задайте `VITE_OPENAI_API_BASE_URL`
в окружении команды сборки или в `frontend/.env.local`:

```env
VITE_OPENAI_API_BASE_URL=https://ai.example.com/v1
```

Также поддерживается адрес без `/v1`: префикс будет добавлен автоматически.
Изменение переменной требует пересборки frontend; переменная в окружении
уже запущенного backend не меняет готовую сборку.

## Внутренний чат

Согласованное требование: браузер чата обращается к собственному пути backend
на origin интерфейса. Этот путь использует тот же OpenAI-прокси, реестр
запусков, кеш моделей и обработку потоковых ответов, что и внешний `/v1`.
Адрес в шапке и `VITE_OPENAI_API_BASE_URL` не определяют адрес запросов чата.

Внутренние маршруты `/api/proxy/models`
и `/api/proxy/chat/completions` вызывают общий `ProxyService` внутри backend.
Дополнительный HTTP-запрос backend к собственному `OPENAI_PORT` для этого
не требуется. Список моделей, обычные и потоковые ответы чата используют
эти маршруты; внешний URL продолжает использоваться только для отображения
и копирования адреса сторонним клиентам. При заданном `VITE_API_BASE_URL`
внутренние запросы используют тот же base URL, что и API управления.

Для потокового внутреннего чата прокси принудительно добавляет
`stream_options.include_usage: true` перед запросом к поддерживаемому движку,
сохраняя остальные поля `stream_options`. Это позволяет получать финальный
блок usage и записывать токены в журнал. Публичный `/v1` этот параметр сам не
добавляет.

## Responses API

На том же внешнем `OPENAI_PORT` доступен маршрут:

```text
POST /v1/responses
```

На origin интерфейса тот же обработчик доступен как `POST /api/proxy/responses`.

Он использует общий `ProxyService`: поле `model` выбирает текстовый профиль
или алиас, а движку передаётся его собственное имя модели. Запрос направляется
в нативный `/v1/responses` выбранного движка. Тело запроса, включая `input`,
`instructions`, `tools`, `store` и параметры reasoning, передаётся без
преобразования в Chat Completions. Поддержку этих полей определяет движок.

При `stream: true` SSE-события Responses передаются клиенту по мере получения
без изменения содержимого. Вызовы инструментов и их результаты обрабатываются
клиентом и движком; прокси инструменты не выполняет. Параметр
`stream_options.include_usage`, используемый внутренним чатом, для Responses
автоматически не добавляется.

Запросы учитываются в общем журнале с маршрутом `/v1/responses`, выбранным
профилем и доступными токенами. Для SSE токены и сведения о кешировании берутся
из вложенного объекта `response.usage`. События `response.failed`,
`response.incomplete` и поток без терминального события отмечаются ошибкой
в журнале; содержимое потока остаётся ответом движка. После начала передачи
потока переключение на другой профиль не выполняется.

Neural Deck не хранит объекты Responses и не предоставляет маршруты их
получения, удаления или отмены по ID. Для алиаса с несколькими профилями
клиенту следует передавать полную историю в `input` с `store: false`:
`previous_response_id` привязан к состоянию конкретного движка, а алиас
не закрепляет последующие запросы за этим экземпляром.

## Генерация изображений через ComfyUI

Профиль с движком ComfyUI публикуется через тот же внешний `OPENAI_PORT`:

```text
POST /v1/images/generations
```

Запрос использует стандартный OpenAI-совместимый контракт: `prompt`, `model`,
`size`, `n`, `response_format`, а также дополнительные `seed`, `steps`,
`transparent` и `image` для img2img. Ответ содержит `data` с `url` или
`b64_json`, поэтому обычные клиенты, поддерживающие Image Generations API,
могут обращаться к Neural Deck без знания ComfyUI.

Для клиентов, которым нужен нативный ComfyUI API, доступен проксируемый путь:

```text
/comfyui/{profile_name}/...
```

Он передаёт HTTP-маршруты ComfyUI, включая `/prompt`, `/history/{prompt_id}`,
`/view` и WebSocket `/ws`, только в явно выбранный профиль. Внешний API
изображений и нативный путь используют один и тот же запущенный профиль.

MCP-сервер Neural Deck также получает tool `generate_image`, если в приложении
зарегистрирован image-профиль. Он запускает тот же сервис и возвращает
OpenAI-совместимый результат с изображением.

## Обновление списка моделей прокси

При каждом `GET /v1/models` прокси проверяет список запущенных процессов.
Подтверждённый непустой ответ `/v1/models` движка кешируется отдельно для
каждого запуска на 10 минут. Пустой ответ, ошибка или недоступный движок не
создают кеш: такой запуск опрашивается при каждом следующем запросе.
Готовые запуски при этом используют собственный кеш.

После истечения срока следующий запрос повторяет опрос движка. Фонового
опроса по этому таймеру нет. Перезапуск (смена PID или времени запуска),
смена порта или имени модели профиля инвалидируют кеш. Кеш исчезнувших
процессов удаляется при следующем запросе. Имя модели из профиля остаётся
публичным идентификатором; имя для отправки движку обновляется из его ответа.

Каждое открытие выбора модели в чате отправляет новый запрос к прокси.
Кнопки «Повторить» в выборе модели нет.

Этот кеш относится к общему `GET /v1/models`. Мониторинг метрик и обнаружение
внешних процессов через другие management API продолжают работать отдельно.

## Параметры изображений

Для подготовки новых графов используется целевой
[контракт API-workflow ComfyUI v1](comfyui-workflow-contract.md).
Он описывает именованные входы и выходы независимо от модели;
единый адаптер использует только этот контракт, без анализа внутренних ветвей и обратной совместимости.

Для алиасов ComfyUI внешний `/v1/images/generations`, multipart
`/v1/images/edits` (включая маску) и `/v1/images/variations` используют тот же
`ComfyImageService`, что внутренний чат. Поля передаются в запросе;
пользовательские привязки узлов и дополнительные настройки UI не нужны.

| Поле | Контракт NeuralDeck |
| --- | --- |
| `quality` | Qwen Turbo принимает `auto`, `low`, `medium`, `high` как совместимые имена одного сохранённого режима (`auto` по умолчанию). Неизвестные значения — HTTP 400. |
| `output_format` | `png` (по умолчанию), `jpeg`, `webp`; кодирование выполняется после ComfyUI, размер и количество не меняются. |
| `output_compression` | Целое 0–100 для JPEG/WebP, по умолчанию 100: большее значение сохраняет больше деталей и обычно увеличивает файл. Для PNG поле отклоняется с 400. |
| `seed` | Необязательное расширение, целое 0–2^64−1. Передаётся в именованный вход `ND.v1.seed` по объявленному диапазону алиаса. Без значения выбирается новый случайный seed на каждый запрос. |
| `size`, `n` | Подстановка в именованные входы workflow; результат по размерам/количеству не аудируется адаптером. |
| `background` | `auto`, `opaque`, `transparent`; режим передаётся во вход workflow, который отвечает за реализацию фона. `jpeg` + `transparent` отклоняется до генерации. |
| `response_format` | `url` или `b64_json`; оба варианта возвращают байты выбранного формата. |

У проверенной конфигурации Qwen-Image-2.1-Turbo один рабочий режим —
8 шагов. По согласованному правилу совместимости `auto`, `low`, `medium`,
`high` используют этот сохранённый workflow как `auto`. Отсутствие поля или
`null` также использует сохранённый режим. Это документированное соответствие,
а не разные уровни качества: шаги, sigmas, CFG, разрешение и промпт не меняются.
Разрешение задаётся отдельно через `size`. Правило одинаково для генерации,
edit, edit с маской и вариаций.

Различающиеся режимы качества допускаются после определения их поведения
и тестового подтверждения разницы. Увеличение числа шагов само по себе
не означает улучшения качества. Отдельные режимы quality в ND.v1 не вводятся.

Постобработка выполняется один раз перед ответом. Для `url` преобразованный
файл сохраняется через штатный upload API существующего ComfyUI, а NeuralDeck
хранит его обычный дескриптор; URL остаётся работоспособным после перезапуска.
Для `b64_json` дополнительного сохранения файла не требуется. Расширение,
байты и `Content-Type` соответствуют выбранному кодеку. PNG возвращается без декодирования; JPEG/WebP кодируются по запросу клиента.
Alpha поддерживается WebP, JPEG требует RGB; проверки содержания workflow нет. JPEG и lossy WebP вносят обычные потери кодирования во всё изображение;
для точного пиксельного сравнения области вне маски следует использовать PNG.
Постобработка не меняет маску и не выполняет дополнительную генерацию.

Повторяемость seed относится к пикселям при одинаковых workflow, входных
изображениях, параметрах, весах, backend и условиях исполнения. Имена выходных
файлов и PNG-метаданные не являются критерием воспроизводимости; переход на
другое оборудование или недетерминированные GPU-операции может влиять на неё.
Неоднозначный или неизвестный seed-вход при явно заданном seed возвращает
400, а не игнорируется.

Пример генерации через LiteLLM или напрямую в NeuralDeck:

```json
{
  "model": "qwen-image-turbo",
  "prompt": "A green ceramic teapot on a light background",
  "quality": "auto",
  "size": "1024x1024",
  "n": 1,
  "output_format": "webp",
  "output_compression": 85,
  "seed": 42,
  "response_format": "b64_json"
}
```

В multipart те же поля передаются как form-data; `image` и `mask` остаются
файлами. В LiteLLM это должны быть параметры Images API; если конкретная версия
LiteLLM фильтрует расширение `seed`, его нужно передать через поддержанный ею
`extra_body`/список разрешённых дополнительных параметров, не включая удаление
неподдержанных параметров. NeuralDeck не меняет конфигурацию LiteLLM.

Источники контракта: [OpenAI Images API](https://developers.openai.com/api/reference/resources/images/methods/generate),
[официальная карточка Qwen Turbo](https://huggingface.co/Qwen/Qwen-Image-2.1-Turbo).
Сквозные и локальные тесты этого изменения не запускались по решению пользователя.

# TASK-005 — Бенчмарки производительности

Добавлено: 2026-10-04.

## Цель и границы

Отдельный раздел Benchmarks для воспроизводимых измерений производительности
уже запущенного профиля. В первой версии задача ограничена performance:
prefill, decode, concurrency, смешанная нагрузка и кэширование.

Интеллект и решение задач вынесены в [TASK-006](TASK-006-intelligence-benchmarks.md),
чтобы не смешивать throughput с качеством ответа, agent sandbox и judge.

## Сценарии производительности

### Базовые сценарии

- Один запрос: prefill/TTFT на входных контекстах примерно 10 000, 50 000,
  130 000 и 200 000 токенов. Значение, превышающее served context профиля,
  пропускается с явной причиной, а не считается ошибкой модели.
- Один запрос: decode при контролируемой длине output.
- Повторение сценариев с несколькими типами workload: как минимум prose и
  coding; третий профиль для reasoning/structured task берётся из набора
  Club 3090 или фиксируется отдельным prompt-профилем.
- Каждый script сохраняет результаты отдельных повторов, а не только среднее.

### Поиск оптимальной и предельной concurrency

- **Decode-only concurrency:** синхронно запустить N запросов с пустым или
  минимальным фиксированным prompt и контролируемым output. Это отдельный
  режим для оценки одновременной генерации без длинного prefill.
- **Mixed concurrency:** удерживать несколько активных генераций и после
  завершения отдельных потоков сразу запускать следующие запросы с большим
  контекстом. Так измеряется влияние нового prefill на decode уже работающих
  запросов.
- Для обоих режимов отдельно показывать per-request decode, aggregate output
  throughput, TTFT/prefill, queue/waiting, ошибки и фактическое admission.
- Проверять несколько уровней N и сохранять каждую точку. `optimal` и `limit`
  не должны скрывать кривую и не должны выводиться по одному случайному
  наблюдению очереди.

### Кэширование

- **Cache reuse:** выполнить первый запрос с большим контекстом и output, затем
  повторно отправить тот же prefix с небольшой новой инструкцией. Сравнить
  timings и returned cache usage/engine cache metrics; ответ сам по себе не
  является критерием кэширования.
- **Cache capacity:** последовательно заполнить несколько уникальных больших
  prefixes, например 5, 10 и 20, затем повторно обратиться к ним. Проверить,
  на каком количестве повторный запрос перестаёт показывать cache hit и снова
  выполняет полный prefill.
- **Concurrent cache capacity:** повторить проверку при одновременной работе
  нескольких cache-backed запросов. Отдельно хранить число загруженных cache,
  cache hit/miss, cached tokens и latency каждого повторного обращения.
- Если runtime не возвращает cache information, результат имеет состояние
  `unknown`, а не `cache_miss`.

### Запуск и сбор данных

- Запускать бенчмарки относительно выбранного уже запущенного профиля.
- Выбор профиля определяет endpoint, к которому обращается тест.
- Во время теста обычная статистика приложения продолжает собираться в фоне.
- При наличии дополнительных доступных метрик собирать их для бенчмарка.
- Каждый запуск сохранять в общей таблице истории: дата/время начала и конца,
  выбранный профиль, instance identity, script/тип benchmark, статус и summary.
- Не создавать отдельную таблицу измерений и не сохранять JSONL/копию script-а.
  Script выводит промежуточные данные runner-у, runner оставляет только
  компактный нормализованный итог запуска в этой единственной таблице.
- Использовать обычные профильные метрики, собранные за время бенчмарка, для
  графиков и анализа; запись запуска нужна как временная отметка и подпись,
  а не как дубликат каждого snapshot/request.
- На графиках метрик выделять временной интервал бенчмарка фоновой заливкой,
  например светло-синей, и указывать, какой тест выполнялся.
  Это должно объяснять всплески активности.

### Независимые scripts и расширяемый UI

- Performance scripts хранятся в выделенной папке, например
  `scripts/benchmarks/performance/`, и поддерживают независимое редактирование
  и добавление новых сценариев.
- UI не содержит отдельную ветку кода для каждого script. Он обнаруживает
  только scripts с согласованным descriptor-интерфейсом, получает их название,
  параметры и доступные workload-профили, а затем запускает выбранный script.
- Каждый script должен выдавать единый машинный формат, предпочтительно
  JSONL: события запуска/завершения, raw sample, summary, status и reason.
  Человекочитаемый текст допускается как дополнительный log stream.
- Общая оболочка runner-а передаёт selected profile, endpoint, параметры
  запуска и сохраняет `script_id`/версию. Произвольные файлы в папке нельзя
  запускать без descriptor-а и проверки границ.
- Добавление нового script должно расширять список тестов и универсальную
  таблицу/графики UI без изменения frontend под конкретное имя теста.

## Что уточнить при подготовке спецификации

- Размеры входного контекста и выходной генерации, шаги concurrency,
  максимумы, число повторов, прогрев и критерии завершения теста.
- Определения и формулы prefill/decode: скорость одного запроса
  и суммарная пропускная способность при параллельной нагрузке.
- Как учитывать кэш, точное число токенов, TTFT, время очереди и другие
  доступные измерения; как обнаруживать очередь без догадок.
- Как отделить влияние обычного трафика и других запущенных профилей
  от нагрузки бенчмарка; как отображать смешанные измерения.
- Как связать обычные метрики с запуском и его этапами, особенно при
  одновременных тестах; что делать с недоступными метриками.
- Какие сведения о модели, конфигурации, engine и окружении сохранять
  для сравнения и воспроизводимости результатов.
- Включать ли бенчмарки в общие расход и стоимость, и как фильтровать
  тестовую активность при просмотре статистики.
- Точные параметры третьего workload-профиля и набор prompt-ов Club 3090.
- Точные уровни N, длина output, warmup/repetition и stop policy для первой
  реализации.
- Формат descriptor/JSONL и правила отображения неизвестных полей в UI.
- Политика включения benchmark-трафика в статистику и стоимость TASK-003.

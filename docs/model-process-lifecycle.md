# Запуски моделей и перезапуск backend

В нативной Linux/LXC установке модели работают в независимых временных
пользовательских systemd units. Перезапуск neural-deck.service сохраняет модели;
после восстановления backend они остаются управляемыми, включая остановку,
логи, метрики и общий API.

Установщик подготавливает user@UID.service и включает linger пользователя.
Сервис backend ожидает менеджер перед запуском. Модельные units не включаются
в системный автозапуск и используют Restart=no. После перезагрузки ОС
модели не восстанавливаются средствами systemd; backend запускает только
профили с autostart. При завершении модельного unit systemd очищает его.
Установки и служебные команды остаются дочерними основного сервиса и
завершаются при его остановке благодаря KillMode=control-group.

SQLite model_runs содержит текущий снимок управляемых запусков с PID и
временем создания. Завершённые процессы удаляются при наблюдении; живые
восстанавливаются перед автозапуском. История здесь не хранится. YAML
по-прежнему содержит конфигурацию профилей.

В Docker применяется режим process, без systemd. Сохранившиеся после
перезапуска только backend процессы также восстанавливаются по SQLite.
Перезапуск контейнера завершает все находящиеся в нём модели.

NEURAL_DECK_MODEL_LAUNCHER — параметр окружения службы: systemd для нативного
установщика, process по умолчанию для Docker и прямого запуска. Ошибка
systemd не приводит к скрытому запуску модели в основном сервисе.

Изменение требует обновления установленного systemd-сервиса через установщик,
а не только перезапуска старого backend. Модели, запущенные старой версией без
записи привязки, автоматически не присваиваются профилям.

Согласованные требования: [спецификация](specs/2026-10-02-model-process-lifecycle.md).

## Готовность профиля

После создания процесса профиль остаётся в состоянии `starting`
(«Запускается»). Backend проверяет локальный `/v1/models` каждые две секунды,
пока процесс жив. Общего таймаута загрузки нет: длительная загрузка модели
сама по себе не меняет статус на «Запущена» или ошибку.

Состояние `ready` устанавливается только после ответа HTTP 200 с непустым
списком моделей. После восстановления живого процесса при перезапуске backend
готовность подтверждается заново. Обновление списка без проверки API не
меняет `starting`. Завершение или остановка процесса имеет приоритет над
ответом проверки, полученным позднее.

## Потеря соединения с SQLite

Перед повторным использованием соединения из пула выполняется `pool_pre_ping`.
Закрытое соединение исключается из пула до выполнения прикладного запроса.
Потеря соединения во время транзакции возвращается как ошибка: автоматического
повтора записей нет. Следующий запрос получает новое соединение.

Предупреждение `app.db` сообщает тип ошибки и `during_checkout`: `True`
означает обнаружение закрытого соединения при получении из пула, `False` —
при выполнении запроса. SQL и параметры в это предупреждение не включаются.
Диагностика `process_discovery` отражает текущую ошибку и снимается после
успешного сканирования; отменённое сканирование предупреждение не снимает.

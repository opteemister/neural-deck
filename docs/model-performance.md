# Производительность выбранного запуска

Панель справа на Dashboard показывает показатели выбранного процесса. Состояние
процесса остаётся в заголовке. Сырые названия exporter и API latency в панель
не выводятся. Общие ресурсы машины остаются отдельным блоком.

## Источники и смысл

### Включение метрик при запуске

Проверено 2026-10-02 по документации и исходникам upstream. Это проверка
контракта движков, а не установленных на сервере версий.
Стандартные шаблоны LLM Studio уже включают доступные HTTP-метрики:

| Движок | Источник | Включение | Переменная окружения |
|---|---|---|---|
| llama.cpp | `/metrics` | `--metrics` в стандартном шаблоне | Поддерживается `LLAMA_ARG_ENDPOINT_METRICS=1` |
| vLLM | `/metrics` | Включены по умолчанию | Отдельная переменная включения не найдена; не требуется |
| SGLang | `/metrics` | `--enable-metrics` в стандартном шаблоне | Эквивалент флага в проверенных исходниках не найден |
| FreeToken | `/v1/stats` | Доступен по умолчанию | Отдельный переключатель включения не найден; не требуется |
| NInfer | Статистика throughput в логах | Включена по умолчанию: `--log-stats-interval-ms 5000`; `0` выключает её | Эквивалент не найден; поддерживаемый HTTP-endpoint метрик отсутствует |

Для llama.cpp можно вместо `--metrics` задать в поле окружения профиля
`LLAMA_ARG_ENDPOINT_METRICS=1`. В стандартном шаблоне сохранён явный флаг.
Переменные SGLang `SGLANG_ENABLE_METRICS_DEVICE_TIMER` и
`SGLANG_ENABLE_METRICS_DP_ATTENTION` относятся к дополнительным измерениям
и не заменяют `--enable-metrics`. `PROMETHEUS_MULTIPROC_DIR` также не является
переключателем включения exporter.

В форме профиля есть галочка «Включить метрики», по умолчанию включённая.
Её значение сохраняется в YAML как `enable_metrics` (старые профили без поля
считаются включёнными). При сохранении профиля или запуске редактируемой
конфигурации для llama.cpp добавляется `--metrics`, для SGLang —
`--enable-metrics`, если соответствующего аргумента нет. Для детализации usage
по cached tokens добавляются `--enable-prompt-tokens-details` у vLLM и
`--enable-cache-report` у SGLang и FreeToken. Это отдельные параметры от экспорта `/metrics`:
без них общий KV Hit может быть доступен, а cached tokens конкретного запроса — нет.
В актуальных llama.cpp и NInfer `usage.prompt_tokens_details.cached_tokens` возвращается
без дополнительного флага. При включённой галочке
vLLM также получает `--disable-access-log-for-endpoints /metrics`, SGLang —
`--log-level-http warning`. У SGLang скрываются все HTTP access-записи уровня INFO,
но сохраняются warnings/errors HTTP-сервера и обычные логи движка. Явно заданные
значения этих опций (включая синтаксис `--option=value`) не перезаписываются.
Источники параметров детализации: [vLLM](https://docs.vllm.ai/en/latest/cli/serve/#--enable-prompt-tokens-details),
[SGLang](https://docs.sglang.io/docs/advanced_features/server_arguments),
[FreeToken](https://github.com/FlashML-org/FreeToken/blob/main/python/freetoken/server/args.py).
Возврат без флага: [llama.cpp](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/server-task.cpp),
[NInfer](https://github.com/Neroued/ninfer/blob/master/src/serve/openai_chat_response.cpp).

В актуальном llama.cpp HTTP logger отключён, а `/metrics` исключён из его фильтра;
FreeToken по умолчанию фильтрует polling, включая `/v1/stats` (при `LOG_LEVEL=DEBUG`
фильтрация отключается). NInfer не требует параметра для HTTP-опроса метрик.
Эти сведения относятся к проверенным upstream-версиям; старые установки могут
отличаться. Для старого vLLM без поддержки параметра задайте вручную
`--disable-uvicorn-access-log` и снимите галочку автоматической модификации.
Новые параметры применяются также при запуске ранее сохранённых профилей,
без переписывания YAML. Добавленный флаг сохраняется в `command` и
отображается в фактической команде в карточке профиля.

Карточка получает фактическую команду через `POST /api/v1/profiles/preview`.
Backend использует общую с запуском подготовку конфигурации: разрешает путь
установки и добавляет параметры по `enable_metrics`, затем подставляет
shell-quoted значения заполнителей. Поэтому новые автоматические параметры
видны и у ранее сохранённых профилей до повторного сохранения YAML.
Предпросмотр не запускает процесс и не меняет файл профиля. При ошибке
подготовки интерфейс показывает её вместо неполной команды.
Снятая галочка оставляет команду в точности как введена, включая уже указанные
флаги: она отключает автоматическую модификацию, а не метрики движка.
Чтение старого YAML и запуск сохранённого профиля сами файл не переписывают.
Для составного shell-скрипта без флага автоматическое добавление отклоняется:
пользователь добавляет флаг к вызову движка вручную или снимает галочку.
Комментарии не считаются аргументами; простые команды с переносами через `\`
и завершающим комментарием поддерживаются. Для NInfer нельзя обещать показатели
Dashboard только на основании включённой статистики в логах: HTTP-адаптер
метрик для него отсутствует.

### Показатели

- llama.cpp: `/slots` для текущей генерации, `/metrics` с параметром запуска
  `--metrics` для счётчиков завершённых запросов. Decode/Prefill — разность
  `next_token.n_decoded` / `n_prompt_tokens_processed` между опросами одного
  slot/task, делённая на время. Первый опрос и смена task не дают известную
  скорость. Если slots недоступны, остаётся средняя скорость завершённых
  запросов из exporter. Live output tokens показываются отдельно от
  завершённых токенов, без сложения двух несинхронных снимков.
  Requests и Queue — processing/deferred; токены — счётчики prompt/predicted.
  TTFT и Served не выводятся как известные, если exporter их не предоставляет.
  KV cache поддерживается в версиях, отдающих `kv_cache_usage_ratio`.
- vLLM: `/metrics`, running/waiting, cache usage, prompt/generation counters,
  request success и histogram TTFT.
- SGLang: `/metrics`, running/queue, token usage, prompt/generation counters,
  request counters и histogram TTFT. Exporter должен быть включён в движке.
- vLLM Prefill: `delta(request_prefill_kv_computed_tokens_sum) /
  delta(request_prefill_time_seconds_sum)`. Числитель уже исключает кешированные
  токены, знаменатель — интервал от первого планирования до первого токена,
  без начальной очереди и decode, но с возможными прерываниями Prefill.
  Обе histogram относятся к одним завершённым запросам; проверяются labels,
  count и сбросы счётчиков. Скорость обновляется при завершении запроса,
  до следующего измерения UI удерживает последнее известное значение.
  Если версия vLLM не предоставляет эти histogram, показатель неизвестен:
  все входные токены / интервал опроса не используется как замена.
  При нескольких запросах это скорость, взвешенная по длительности Prefill,
  а не суммарная пропускная способность параллельных GPU. Этот же вес
  сохраняется для суточного avg. Полностью кешированный интервал без новой
  вычислительной работы не добавляет измерение скорости.
  [Исходники vLLM](https://github.com/vllm-project/vllm/blob/main/vllm/v1/metrics/loggers.py).
- [Club 3090](https://github.com/noonghunna/club-3090/blob/master/scripts/bench.sh)
  использует `prompt_tokens / TTFT` с уникальными промптами, исключающими
  попадания в prefix cache. Это клиентская скорость с сетевыми и другими
  накладными расходами; для обычных кешируемых запросов напрямую не подходит.
- vLLM Decode и SGLang throughput: разность счётчика токенов / время между свежими
  измерениями. Первое измерение и сброс счётчика дают неизвестное значение.
  TTFT — среднее по новым наблюдениям histogram: delta(sum)/delta(count).
  Отсутствие новых запросов не заменяется нулевым TTFT.
- FreeToken: известные поля `/v1/stats`; процент KV — used/total pages.
- NInfer: неизвестные показатели обозначаются прочерком; endpoint не угадывается.
- Uptime: с начала текущего процесса, а не накопленное время жизни профиля.
- VRAM: `nvidia-smi --query-compute-apps=pid,used_gpu_memory`, сумма по
  подтверждённому PID и его дочерним процессам. Если PID в namespace не совпадает
  с данными драйвера либо память недоступна, результат неизвестен.
- Power/Energy: без отдельного источника измерения на процесс остаются неизвестными.
  Мощность общей карты не приписывается выбранной модели.

Значения относятся к серверному процессу, включая запросы напрямую к движку.
При нескольких моделях/репликах в одном exporter значения счётчиков и запросов
суммируются, занятость KV берётся по наиболее занятому пулу. Это не отдельная
статистика каждой модели внутри multi-model server.

## Графики

Отдельные графики Prefill, Generation и активных Requests. Браузер хранит
не более 120 точек без ограничения числа минут. При открытии восстанавливает
последние сохранённые точки, затем добавляет live-наблюдения раз в 2 секунды.
История профиля загружается по имени, без ограничения по PID: точки предыдущих
запусков сохраняются после перезапуска модели. История не перечитывается при каждом опросе. Разрывы во времени соединяются
между валидными точками одной серии; неизвестные значения не заменяются нулями.
Подсказка показывает значение конкретной точки. Масштабы графиков вычисляются
по видимым точкам. Max и avg в карточках берутся отдельно за последние 24 часа
по имени профиля, включая предыдущие PID. Они не ограничены 120 точками графика.

## Хранение

Фоновый сбор независимо от браузера пишет снимки движков каждые 5 секунд.
История доступна за последние сутки. Очистка происходит при старте и ежедневно
в полночь по времени ОС сервера; физически записи могут оставаться почти 48 часов.
Журнал API-запросов с токенами, PID и доступными метриками конкретного запроса
хранится бессрочно. Неизвестные показатели остаются NULL. Запросы напрямую к
движку не создают отдельных записей в журнале API Студии.

`GET /api/v1/metrics` поддерживает `mode=current|bootstrap|history|peaks|usage`,
`profile_name`, `pid`, `scope=all`, `from`, `to`, `limit`. Журнал usage также
поддерживает `client_id` и `offset`; ответ содержит `next_offset`.

## Последние известные значения на UI

Числовые показатели панели удерживают последнее известное значение, если
следующий опрос вернул неизвестное значение или не вернул показатель.
Ноль является новым измерением и заменяет предыдущее значение. Удержанное
значение имеет время последнего измерения только в подсказке; устаревание источника
также отмечается в подсказке. Значения разделены по экземплярам запуска и при открытии
восстанавливаются из доступной истории. Это только отображение: расчёты движка,
снимки базы и точки графиков не заполняются удержанными значениями.

Панель состоит из двух строк по пять показателей: Prefill, Decode, TTFT,
Requests, KV Hit; KV cache, Tokens, Served, Queue, Draft Acceptance.
Текущие показатели сохраняют прежнюю логику. TTFT, поскольку это среднее,
отображает суточное avg и max.
Подписи max/avg в карточках и Prefill/Decode avg в сводной таблице берутся
из `GET /api/v1/metrics?mode=aggregates` за скользящие 24 часа. В подписи KV Hit
и Draft Acceptance также показывается суточное avg, а не среднее за запуск.
SQLite считает агрегаты по всей истории без лимита числа записей и исключает
повторы одного измерения. TTFT взвешивается по count, KV Hit и Draft Acceptance
по denominator, если доступны; иначе — вес 1. Нули и пустые значения исключены.
В режиме «Все» скорости и Requests складываются внутри пятисекундных интервалов.
Суточные агрегаты обновляются каждые 30 секунд, текущие показатели — каждые две.
Prometheus используется при наличии данных для всего суточного окна; иначе — SQLite. Время в Queue должно соответствовать
максимальному возрасту **текущих** ожидающих запросов: среднее histogram
завершённых ожиданий его не заменяет. Пока движок не отдаёт такое значение,
показывается прочерк (при пустой очереди — 0 ms).
На Generation светлая линия Per request — общая скорость / активные запросы
из того же снимка. При неизвестном числе запросов точки нет; при нуле запросов
скорость на запрос показывается как 0. Фоновый пунктир немного шире основной
линии, чтобы при совпадении координат обе серии оставались различимыми.
У линии независимая вертикальная шкала с общей временной осью и прежней сеткой.
Пропорциональные серии с независимыми шкалами могут совпадать геометрически.
Per request имеет пунктирную линию; Generation — сплошную линию на переднем
плане. Точки обеих серий одинакового размера и заполнены цветом своей линии. Верхняя граница основной шкалы подписана слева, Per request —
справа. Границы вычисляются по видимым точкам; при восстановлении другого окна
истории они могут измениться. Значения и координаты искусственно не сдвигаются.
Подписи с максимумом включают `avg` по положительным доступным измерениям.
Нулевые, пустые и нечисловые значения пропускаются при расчёте наблюдаемого
среднего, включая восстановленную историю. Текущие нули остаются на карточках
и графиках. Нативное положительное среднее движка (например TTFT) сохраняет
свою семантику; отсутствие новых запросов не добавляет в него измерений. Prefill отображается
полным числом без `k`; TTFT автоматически использует ms, s, min или h.

После Requests расположен составной столбчатый график Tokens за последние
24 часа: 24 интервала по одному часу. Каждый столбец состоит из некешированного
Input, Output и Cached. Cached вычитается из Input при построении, чтобы не
считать его дважды; tooltip показывает полный Input, Output и Cached.
Источник — завершённые запросы в журнале API Студии. Прямые запросы к движку
в обход API не входят. Агрегация выполняется в SQLite без ограничения числа
запросов, по времени получения usage или завершения. Неизвестные значения
сохраняют отдельный счётчик в данных, но его количество в UI не показывается.
Tooltip расположен рядом с курсором с отступом 12 px; если справа нет места,
он появляется слева и остаётся в пределах экрана. Страница опрашивает
агрегаты раз в 30 секунд; при закрытии страницы опрос прекращается.
На вкладке «Все» учитываются все профили и запуски за последние 24 часа; на вкладке
профиля применяется только фильтр по имени, включая предыдущие запуски.

Таблица вкладки «Все»: профиль и модель, статус, Prefill avg, Decode avg,
Served, Output tokens, кнопка остановки. Средние скорости вычисляются тем же
механизмом, что в модельной панели, по восстановленной истории и новым измерениям.
Остановка остаётся доступна только при подтверждённых идентичности и правах.

## Опциональный Prometheus

Укажите `PROMETHEUS_URL` — базовый URL query API. Если требуется Bearer
авторизация чтения, задайте `PROMETHEUS_TOKEN`. При пустом URL чтение идёт
из локального сборщика. При настроенном URL свежие данные Prometheus имеют
приоритет; при ошибке или устаревании используются снимки SQLite. Локальная
запись всегда продолжается. Журнал отдельных запросов читается из SQLite.

Prometheus должен отдельно опрашивать `/metrics` Студии на порту интерфейса.
Настройка URL не регистрирует источник в Prometheus автоматически. Пример
для `prometheus.yml` (адрес заменить адресом своей Студии):

```yaml
scrape_configs:
  - job_name: llm-studio
    scrape_interval: 5s
    scrape_timeout: 2s
    static_configs:
      - targets: ["studio-host:3000"]
```

Labels: `studio_id`, `profile_name`, `pid`, `engine_id`. Постоянный studio_id
хранится в DATA_ROOT/studio-id. Экспортируются только свежие известные значения,
их исходное время измерения и доступные веса для вычисления средних.
Query timestamp Prometheus не выдаётся за время наблюдения движка.

## Бессрочный дневной архив

Перед каждой очисткой, включая старт сервиса, снимки дополняют `metric_daily`
и `metric_concurrency_daily`. Checkpoint хранит последний обработанный ID,
время измерений и исходные histogram предыдущего снимка. Архив, checkpoint и
удаление снимков старше 24 часов фиксируются одной транзакцией. Ошибка сохраняет
подробные данные. ID снимков используют SQLite AUTOINCREMENT и не переиспользуются.
Снимки, поступившие после начала архивации, не удаляются этим проходом.

День — календарная дата в часовом поясе ОС сервера. Ключ архива: дата, профиль,
модель, движок; PID объединяются. Модель под прежним именем профиля остаётся
отдельной группой. Архив бессрочный, API-журнал также остаётся бессрочным.

В `metric_samples.distributions` записываются исходные histogram движка:
TTFT, Prefill/Queue/Decode time и доступные histogram токенов. Сохраняются
labels, время наблюдения, cumulative buckets, sum, count. На UI они не выводятся.
После первого базового снимка считаются приращения. Сбросы счётчиков и смена
bucket-схемы начинают новый baseline; несовместимые схемы в архиве не смешиваются.
Приращения относятся к дню наблюдения, поэтому запросы около полуночи могут
попасть в соседний день с погрешностью интервала сбора. Процентили histogram
приблизительны и ограничены диапазонами движка; индивидуальные запросы из них
восстановить нельзя. Ранее удалённые данные и события до первого baseline
не восстанавливаются.

Для положительных свежих нормализованных измерений хранятся sum, weight, count,
max и распределение с фиксированными логарифмическими bucket шириной 5%.
Нули/NULL и повторения одного измерения исключены. Avg использует доступные
нативные веса; p10/p50/p95 этих измерений отличаются от процентилей запросов.
Для запросов отдельно хранятся приращения нативных histogram и p50/p95.
При объединении дней складываются суммы, веса и buckets, а не средние или
процентили отдельных дней. Токены API берутся из журнала запросов; cumulative
счётчики движка не складываются между снимками.

`GET /api/v1/metrics/daily?profile_name=...&days=7` возвращает дневную историю.
`GET /api/v1/metrics/concurrency?profile_name=...&days=7` возвращает группы
наблюдаемой Generation по числу активных запросов. Оба API добавляют ещё
не архивированные снимки без двойного счёта. Число дней: 1–3650.

График Generation / параллельность показывает 7 календарных дней, включая
сегодня. X — активные запросы; Y — tok/s, общая шкала Total/Per request.
Группы разделены по профилю, модели и движку. Скорость взвешивается временем
между соседними снимками при неизменной известной положительной параллельности.
Интервалы более 15 секунд, переходы параллельности, устаревшие скорости и
нулевые скорости исключаются. Per request = Total / число запросов.
Смена параллельности между самими опросами может остаться незамеченной; график
описывает наблюдаемую нагрузку, а не контролируемый бенчмарк насыщения GPU.

График параллельности расположен в общей сетке между Requests и Tokens.
Обе линии начинаются с опорной точки (0, 0); она служит началом координат
и не записывается в статистику как измерение. Верхняя граница общей шкалы
округляется до удобного числа с запасом около 20%: 113 → 150, 178 → 200.

Линейные графики используют единый `MetricLineChart`, включая Parallel:
одинаковые область 400×120, высота, сетка, точки и подсказка ближайшего
измерения. У Parallel подсказка показывает параллельность и Total/Per request;
нулевая точка и округлённый предел сохранены. Вертикальная шкала общая.

Столбцы Tokens привязаны к часам: 10:00–11:00, 11:00–12:00 и т. д.
Окно содержит 23 завершённых часовых интервала и текущий час. Границы
`from`/`to` и `items.at` не меняются внутри часа; значения продолжают обновляться.
Окно сдвигается на один столбец при наступлении следующего часа. Для текущего
часа учитываются только события до текущего времени, а не будущие записи.

Адаптивность верхних метрик и нижних графиков использует общие пороги по
ширине контейнера содержимого:

- От 1000 px: метрики в 5 колонок (две строки), нижние графики в 4 колонки.
- От 500 до 999 px: метрики в 2 колонки, нижние графики тоже в 2 колонки.
- Ниже 500 px: метрики остаются в 2 колонки; Parallel переносится после них,
  нижние графики идут по одному в строке.

Parallel занимает отдельную колонку, по ширине совпадающую с Tokens.
Его высота фиксирована на всех ширинах: 156 px, как две стандартные строки
метрик по 68 px с промежутком 20 px. Переносы метрик не растягивают Parallel.

# Правила запуска и развёртывания

Этот документ фиксирует обязательные свойства процесса. Конкретные команды,
пути и устройство процессов будут определены в спецификации реализации.

## Локальная разработка

- На компьютере разработчика приложение собирается и запускается в Docker.
  Backend и frontend должны быть доступны в этой локальной среде без
  обязательной установки проектных зависимостей непосредственно в macOS.
- Python- и frontend-зависимости устанавливаются только при сборке Docker-
  образа. Обычный запуск готового контейнера не выполняет `uv sync`,
  `pnpm install` или первоначальную сборку frontend: он сразу запускает
  FastAPI и наблюдатель пересборки уже подготовленного frontend.
- Перед копированием исходного кода Docker-образ устанавливает фиксированные
  CPU-сборки vLLM `0.11.2` и llama.cpp `b5046`. vLLM хранится в отдельном
  окружении `/opt/venvs/vllm`, а `llama-server` — в `/usr/local/bin`.
- Compose монтирует локальные `./data`, `./models` и `./logs` в абсолютные
  service-visible пути из основного `.env`. Контейнер не использует host PID
  namespace и не обнаруживает окружения macOS вне явно смонтированных путей.
- Тесты и статические проверки можно запускать вне Docker, если нужные
  инструменты уже есть на компьютере. Это не должно быть обязательным условием
  разработки.
- Нативная установка на текущую машину допускается как отдельное, явно
  подтверждённое действие, в том числе на macOS.

## Выбор места установки

- Скрипты установки и обновления используют одну процедуру на целевой машине.
- Если задана переменная с адресом удалённого сервера, проект передаётся по
  SSH, а зависимости устанавливаются и приложение собирается на удалённой
  машине. Вместе с проектом копируется основной заполненный `.env` с
  параметрами запуска. Кэши, локальные результаты сборки, постоянные данные,
  модели и логи с компьютера разработчика не копируются.
- Если удалённый сервер не задан, скрипт предупреждает, что изменит текущую
  машину, и запрашивает интерактивный ответ `Y/N` **до любых изменений**.
  Только `Y` разрешает продолжение. `N` или отсутствие ответа отменяет
  установку. Этот режим позволяет запускать тот же скрипт из checkout на
  сервере без промежуточного копирования.
- Удалённое развёртывание не должно требовать сборки приложения или установки
  его проектных зависимостей на компьютере разработчика.
- `deploy.env` содержит только `DEPLOY_TARGET` и `DEPLOY_PATH`. Проектом для
  передачи считается checkout, из которого запущен скрипт; SSH-порт и ключи
  берутся из обычной конфигурации SSH. Процесс должен оставаться простым и
  повторяемым.
- Передаются отслеживаемые файлы checkout и корневой `.env`. Не передаются
  `.git`, `deploy.env`, локальные результаты сборки, `data`, `models` и `logs`.

## Работа установленного приложения

- Необходимые процессы регистрируются в менеджере служб целевой системы и
  автоматически запускаются после перезагрузки машины или LXC. Они не должны
  зависеть от открытой SSH-сессии. На Linux используется systemd; для явно
  подтверждённой нативной установки на macOS — launchd. Служба работает от
  того же системного пользователя, который вручную запускает движки.
- На целевой машине работает один сервис приложения: backend отдаёт собранный
  frontend и API управления на `PORT` (локально 3000), а общий OpenAI-совместимый
  API — на отдельном `OPENAI_PORT` (8080 по умолчанию). Оба HTTP-слушателя
  используют один реестр процессов и одну конфигурацию профилей.
  Для сервиса определены запуск и остановка.
- Основной `.env` копируется с проектом. Файлы профилей запуска, модели, база
  данных и логи хранятся отдельно от каталога проекта; обновление не должно
  их перезаписывать.
- После установки скрипт проверяет состояние службы и ответ приложения.
  Ошибка любой проверки означает неуспешный деплой и показывается явно.
- Отдельная команда статуса без изменений на сервере использует тот же выбор
  цели: SSH при заданном удалённом сервере либо текущую машину. Она сообщает
  состояние службы и доступность приложения и явно показывает ошибки SSH и
  проверки приложения.

Каталоги релизов и архивы сборки для первого процесса развёртывания не
требуются.

# Управление локальными агентами Codex через MCP

Статус: проект для согласования. Реализация не начата.

## Цель

Дать родительскому агенту в текущем чате инструменты запуска, наблюдения,
продолжения и остановки агентов на локальной модели Neural Deck. Использовать
готовый runtime Codex с системным ограничением прав выполнения команд.

Согласованное расположение: управляющий процесс и Codex работают на Mac
рядом с текущей сессией и имеют доступ к текущему репозиторию в пределах
заданного sandbox. Модель вызывается через Neural Deck на сервере.
Пользователь подтвердил этот вариант 2026-10-16. Запуск runtime на сервере
в данную реализацию не входит.

## Подтверждённая основа

- В этой беседе успешно выполнен отдельный `codex exec` с моделью `qwen`
  через `http://192.166.77.115:8080/v1`, протокол `responses`.
- Модель вызвала shell-инструмент и получила его результат в том же диалоге.
- Проверка системного sandbox подтвердила чтение рабочего файла и запрет
  записи, чтения пользовательского конфига вне рабочей папки и сетевого
  соединения из команды модели.
- В документации app-server описаны `thread/start`, `thread/resume`,
  `thread/read`, `turn/start`, `turn/steer`, `turn/interrupt` и события работы.
- Обнаружена отдельная проблема: обычный `/v1/models` Neural Deck не является
  каталогом метаданных Codex. Проверенный CLI использовал fallback metadata.

Проверка `codex exec` не считается проверкой реализации app-server-обёртки.

## Архитектура

```text
Родительский Codex
    -> локальный MCP-сервер по stdio
        -> отдельный codex app-server по stdio
            -> Neural Deck /v1/responses -> модель qwen
            -> команды в системном sandbox на машине runtime
```

MCP-сервер управляет жизненным циклом и преобразует RPC/события в tools.
Модельный цикл, историю и выполнение инструментов ведёт Codex app-server.
Его JSON-RPC-протокол не является MCP; между ними требуется адаптер.

Сервер запускает собственный процесс app-server, не подключается к daemon
текущего приложения и не управляет посторонними пользовательскими чатами.
Провайдер задаётся при запуске этого процесса и не меняет провайдера
родительского чата.

## Предлагаемые инструменты

| Инструмент | Назначение |
|---|---|
| `local_agent_start` | Создать сессию с задачей, разрешённым workspace и профилем прав; вернуть agent_id и turn_id сразу после принятия задачи |
| `local_agent_send` | Дополнить активный ход через turn/steer либо начать следующий ход в той же сессии через turn/start |
| `local_agent_status` | Вернуть фактическое состояние, текущий ход, последнюю активность и известную ошибку |
| `local_agent_events` | Прочитать ограниченную страницу событий по cursor: сообщения, команды, результаты и изменения файлов |
| `local_agent_wait` | Ждать завершения или блокировки ограниченное время; при таймауте вернуть текущий статус и cursor |
| `local_agent_stop` | Запросить прерывание активного хода; подтвердить остановку по событию завершения |
| `local_agent_list` | Перечислить только сессии, созданные этой обёрткой |

Идентификаторы родительского MCP-клиента и сессий нельзя принимать за
доказательство права управлять произвольным Codex thread_id. Обёртка
проверяет принадлежность agent_id собственному реестру.

### Состояние и сообщения

- agent_id стабильно связан с одним Codex thread_id; следующие задания
  продолжают его историю, а не создают новый диалог неявно.
- Каждый ход имеет отдельный turn_id. `turn/steer` получает expectedTurnId;
  гонка с завершением хода возвращается явно, без повторной доставки сообщения.
- Статус берётся из событий runtime; текст модели не является доказательством
  выполнения команды, сохранения файла или успешного завершения.
- Таймаут ожидания не означает остановку агента.
- Ошибка процесса или потеря соединения не выдаётся за успешное выполнение.
  Хранящийся диалог можно возобновить, но потерянный активный ход не
  перезапускается автоматически: его команды могли уже выполнить действия.
- Подтверждение stop требует терминального события либо подтверждённого
  завершения управляемого процесса. При завершении MCP-сервера он прекращает
  активные задания и освобождает дочерние процессы.
- История Codex и реестр обёртки хранятся вне каталогов, доступных для записи
  командам модели. Секреты в задачах, логах и метаданных не сохраняются намеренно.

## Разрешения

1. По умолчанию — чтение разрешённого workspace и минимальных системных
   файлов. Доступ к точному исполняемому файлу Codex разрешается для его
   sandbox helper, как потребовалось в выполненной проверке.
2. Для редактирования — отдельный заранее разрешённый профиль с записью
   только в выбранный workspace. Рабочая папка выбирается из списка,
   настроенного владельцем сервера; произвольные пути не принимаются.
3. Запрет полных прав закреплён в серверной конфигурации. Tools не принимают
   shell-команду запуска Codex, произвольные флаги, overrides sandbox,
   дополнительные writable roots или параметры отключения защиты.
4. В первой версии повышение прав автоматически отклоняется. Блокировка
   возвращается родительскому агенту; он не может разрешить её отдельной
   MCP-тулой. Дальнейшие изменения прав требуют решения пользователя.
5. Сеть из команд модели по умолчанию запрещена. Связь самого клиента Codex
   с Neural Deck является отдельным модельным соединением.
6. Дочернему runtime не передаются автоматически пользовательские MCP,
   приложения, плагины, hooks и секреты окружения. Дополнительные инструменты
   требуют отдельной конфигурации и оценки их собственных прав.
7. При невозможности обеспечить sandbox запуск завершается ошибкой.
   Запуск без sandbox как fallback запрещён.

## Подключение и интерфейс

После реализации MCP-сервер необходимо зарегистрировать в клиенте Codex.
Написанный Python-файл сам по себе не добавляет tool в активную сессию.
Доступность tools проверяется после подключения/переподключения клиентом.

Базовый интерфейс — вызовы MCP-tools в родительском чате и их структурированные
результаты. Публичного документированного механизма регистрации внешней сессии
в качестве штатного дочернего агента текущего чата не обнаружено; такое
отображение не входит в обещания первой версии.

Отдельная панель со списком агентов и событиями возможна как последующий этап
через MCP Apps в поддерживающем их клиенте. Поддержку панели именно в текущем
локальном интерфейсе нужно проверить отдельно. Панель не заменяет и не
имитирует штатные карточки субагентов.

## Критерии приёмки

- Инструменты обнаруживаются настоящим MCP-клиентом.
- Агент вызывает разрешённый инструмент, родитель получает реальный результат.
- Два последовательных задания используют один thread_id и сохранённый контекст.
- Активный ход принимает дополнительное сообщение; гонки не теряют и не
  дублируют его.
- Status/events работают во время генерации; ожидание не блокирует MCP-сервер.
- Stop подтверждается фактическим прерыванием хода.
- На целевой машине проверяются запреты записи, чтения вне разрешённых путей,
  сети команд и повышения прав; для режима редактирования — границы workspace.
- Процесс после сбоя, закрытия клиента или отмены не остаётся бесконтрольным.
- Исправно обрабатываются неизвестные agent_id, ошибка провайдера, отсутствие
  Codex, неподдерживаемый sandbox и недоступный Neural Deck.
- Проверен каталог метаданных qwen; свойства чужой модели не подставляются.

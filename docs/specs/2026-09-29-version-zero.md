# LLM Studio — спецификация первой версии

Статус: **черновик для обсуждения**

Дата: 2026-09-29

Ветка реализации: `codex/version-zero`

Документ собирает все требования, озвученные владельцем проекта. **Все
перечисленные ниже функции входят в первую версию и должны быть реализованы в
этой ветке.** Этапы задают порядок работы, а не сокращают объём версии.
Исключение — страница Benchmarks: в первой версии это только заготовка;
выполнение бенчмарков будет отдельной будущей функцией. Документ пока не
утверждён: нерешённые детали перечислены в конце.

## 1. Цель и среда

LLM Studio — веб-оболочка для удобного использования движков локального
инференса. Она обнаруживает установленные движки и модели, позволяет создавать
профили запуска, запускает несколько моделей одновременно, показывает
состояние и метрики, а также предоставляет общий OpenAI-совместимый API и
простой чат. Студия должна по возможности наблюдать реальное состояние машины,
включая процессы, запущенные вне неё, а не опираться только на собственные
записи о запуске.

Основная целевая среда — Linux LXC на сервере Proxmox. Разработка идёт на
локальном компьютере, где приложение запускается в Docker. Доступ к веб-сервису
предполагается из домашней сети. Адрес привязки и порт приложения задаются
переменными окружения `HOST` и `PORT`. В первой версии аутентификации нет;
её добавление — отдельная будущая задача.

Соседний проект `vllm-studio` служит источником примеров для уже решённых
задач. Его код и UX не копируются автоматически. При явном отличии требований
этого документа приоритет имеет LLM Studio.

## 2. Объекты предметной области

- **Движок** — поддерживаемая реализация инференса. В первой версии нужны
  `vLLM`, `llama.cpp`, `SGLang`, `ninfer` и `FreeToken`. Последние два названия
  сопоставлены с официальными проектами `Neroued/ninfer` и
  `FlashML-org/FreeToken`; детали конкретных установок нужно проверять при
  проектировании адаптеров.
- **Установка движка** — конкретный бинарный файл или Python-окружение с
  путём, определённой версией и состоянием доступности. Один движок может
  иметь несколько установок.
- **Локальный артефакт модели** — папка либо файл в настроенном хранилище,
  включая конкретную ревизию, квант или набор файлов, если их удаётся
  определить достоверно.
- **Профиль запуска** — сохранённая конфигурация с уникальным именем,
  выбранной установкой движка, моделью, переменными окружения, командой и
  настройкой автозапуска. Профили хранятся в файлах отдельной папки, а не в
  базе данных. Имя профиля связывает настройки, логи и статистику.
- **Экземпляр** — наблюдаемый запущенный процесс и его API. Экземпляр бывает
  запущенным через профиль либо запущенным вручную вне LLM Studio.
- **Реестр доступных моделей** — актуальный список моделей, к которым может
  обращаться общий API. Он формируется из наблюдаемых экземпляров, а не
  только из сохранённых профилей.

Это смысловые понятия; структура таблиц и публичных API пока не установлена.

## 3. Поддержка движков и окружений

### Обнаружение и выбор

1. На целевой машине искать установки всех пяти движков. Показывать путь,
   версию, тип установки и результат проверки доступности. Если версия не
   определяется, так и показывать; не подставлять предполагаемую.
2. Находить несколько виртуальных окружений одного движка и давать выбрать
   конкретное для профиля. Поддерживать параллельное наличие рабочей и
   экспериментальной версии.
3. Давать обновить результаты поиска после изменений, сделанных вручную.
   Изменение файлов на диске не должно требовать пересоздания профилей,
   если выбранная установка по-прежнему существует.
4. При исчезновении или поломке выбранного окружения показывать проблему.
   Нельзя молча переключать профиль на другое окружение.
5. Предусмотреть расширяемый интерфейс обнаружения и проверки, так как
   способ установки и сведения о версии у движков могут различаться.
6. Считать найденный Python лишь кандидатом: отдельно проверять в нём каждый
   поддерживаемый движок. В списке установленных и при выборе окружения для
   профиля показывать только подтверждённую пару «движок + окружение».
   Окружение с vLLM без SGLang не должно появляться как установка SGLang.
   Неподтверждённый путь можно показывать отдельно как диагностический
   результат или место установки, но не как готовый к запуску движок.
7. Для движков, запускаемых бинарным файлом, включая самосборный
   `llama-server`, обнаруживать и проверять конкретный исполняемый файл.
   Разрешать указать его путь вручную, даже если файл лежит вне `PATH` и
   стандартных каталогов. Не выводить наличие или версию движка только из
   имени файла или каталога; отсутствие доступной версии показывать явно.
8. Помимо встроенных путей поиска поддерживать необязательную переменную
   `EXTRA_VENV_ROOTS` в `.env` со списком дополнительных корневых каталогов
   виртуальных окружений через запятую. В первой версии добавлять эти
   каталоги через интерфейс не требуется. Встроенный в код набор: искать
   исполняемые файлы через `PATH`, а окружения — в `/opt/venvs` и
   `<data-root>/runtime/venvs`. Пустое значение дополнительной переменной
   оставляет только этот набор. Проверять сам корень и его непосредственные
   дочерние каталоги, включая ссылки на каталоги; недоступный корень
   пропускать с диагностикой, не срывая весь поиск. В указанных корнях искать окружения,
   проверять найденные Python и показывать лишь те движки, установка которых
   подтверждена. Параметр действует и при запуске в Docker, и на сервере.

### Принцип реализации обнаружения

- Общий механизм собирает кандидатов из встроенных путей, дополнительных
  корней, `PATH`, явно заданных файлов и наблюдаемых процессов, устраняет
  дубликаты и возвращает единый формат результата с источником проверки.
- Проверка кандидата реализуется отдельным адаптером каждого движка.
  Адаптер знает допустимые способы установки, как подтвердить наличие
  движка, получить версию и путь запуска. Python-окружение, собранный
  бинарник и другой тип установки не приводятся искусственно к одному
  способу проверки.
- Общая часть не объявляет движок установленным только потому, что найден
  `bin/python` или подходящее имя бинарного файла. Неуспешная проверка
  сохраняет диагностическую причину, но не создаёт доступную для запуска
  установку.

### Управление окружениями

9. Для движка, устанавливаемого через Python, дать создать новое пустое
   виртуальное окружение и установить в него актуальную доступную версию
   движка. Выбор номера версии, форка или источника пакета в первой версии
   не нужен. Клонировать существующее окружение не требуется. Несколько
   созданных окружений могут сосуществовать; установка нового не изменяет
   рабочее окружение, а профиль переключается на новое только явно.
   Кнопка «Обновить» обновляет движок в выбранном существующем виртуальном
   окружении на месте до актуальной доступной версии, не меняя другие
   окружения. После операции повторно проверить установленную версию и явно
   показать результат или ошибку. Если из выбранного окружения сейчас
   работает модель, обновление не начинать: показать причину и потребовать
   сначала остановить запуск.
   Студия не останавливает его автоматически ради обновления.
   Для llama.cpp и NInfer в первой версии достаточно находить и подключать
   готовые бинарники, в том числе по явно указанному пути. Студия не обязана
   скачивать их исходники, собирать бинарники или устанавливать выбранную
   версию. Несколько готовых бинарников можно выбирать по отдельности;
   доступную версию каждого показывать по результату проверки.
10. Дать вручную выполнить разовую команду обслуживания для выбранного
    окружения. Перед запуском показывать её текст, после завершения — вывод
    и код ошибки. Автоматическое выполнение таких команд не требуется.

Для исследования использовать реализацию поиска в
`vllm-studio/controller/src/modules/engines/runtimes/`; проверить, какие
движки и способы установки она действительно поддерживает.

### Проверенные ориентиры для двух новых движков

- В [документации NInfer](https://github.com/Neroued/ninfer/blob/master/docs/serving.md)
  сервер запускается отдельным собранным бинарным файлом
  `build/apps/ninfer-serve`; первым аргументом передаётся путь к артефакту
  `.ninfer`, затем можно указать `--host` и `--port`. Движок предоставляет
  OpenAI-совместимый HTTP API, в том числе `/health` и `/v1/models`. Поиск
  NInfer должен учитывать установку в виде бинарного файла и checkout, а не
  предполагать обязательное Python-окружение.
- По [официальному CLI FreeToken](https://github.com/FlashML-org/FreeToken/blob/main/docs/cli.md)
  сервер запускается как `ft serve --model <path-or-hf-id>`; `--host` и
  `--port` задаются отдельно, а `ft --version` сообщает версию. Значение
  `--model` может обозначать локальную папку, Hugging Face ID или папку FTW.
  FreeToken может быть установлен в Python-окружение. У него документированы
  `/v1/models`, `/health` и `/v1/stats`, что даёт ориентиры для обнаружения
  модели, проверки доступности и метрик.

Эти команды — примеры формата запуска, а не преднастроенные профили для любой
машины. Действительные пути и флаги берутся из конкретной установки.

## 4. Хранилище моделей и Hugging Face

1. В настройках задать папку хранения моделей. После выбора или обновления
   сразу сканировать её и показывать все доступные в ней модели: папки и
   отдельные модельные файлы, в том числе добавленные вне Студии. Отсутствие
   сведений о формате или происхождении не должно скрывать локальную модель.
   Искать и во вложенных папках; неизвестный формат показывать как локальный
   артефакт с неопределённой совместимостью.
2. Обнаруживать модели, добавленные или удалённые вручную, без требования
   скачивать их через LLM Studio. Локальный каталог определяется по
   фактическому состоянию файловой системы.
3. Через Hugging Face искать публичные модели, просматривать сведения о них и
   скачивать выбранные модели либо отдельные нужные файлы в настроенную
   папку. Доступ к закрытым и gated-репозиториям в первой версии не нужен.
4. Показывать разные кванты и файлы, когда это необходимо для осмысленного
   выбора модели и запуска.
5. Сопоставлять результаты Hugging Face с локальными файлами. Достоверно
   найденный артефакт отмечать как скачанный, неполный — как неполный, а
   сомнительный — как неопределённый. Совпадение только по похожему имени
   не является достаточным подтверждением.
6. Давать выбрать локальную модель в профиле запуска. Если данные о формате
   или совместимости отсутствуют, отображать ограничение явно.

Точное соответствие вручную скопированного файла репозиторию, ревизии и кванту
Hugging Face подтверждается доступными метаданными или содержимым. Если
доказательств нет, модель остаётся видимой локально, но связь с Hugging Face
помечается неопределённой. Новые форматы добавляются адаптерами каталога без
скрытия неизвестных файлов.

Ориентир в соседнем проекте: `controller/src/modules/models/model-browser.ts`
и `controller/src/modules/models/routes.ts`. Их текущая логика определения
«скачано» не считается достаточной для этого проекта.

## 5. Профили и управление запусками

1. Создавать множество профилей с уникальными именами. Профиль хранит
   выбранную установку движка, модель, переменные окружения, команду запуска
   и признак автозапуска при старте LLM Studio. Файлы профилей находятся в
   отдельной папке вне копируемого при деплое проекта; именно эти файлы, а не
   записи базы данных, являются источником конфигурации профилей.
2. Основой запуска является многострочный shell-скрипт, который ввёл и
   проверил оператор. Редактор сохраняет переносы строк и позволяет вставить
   готовую однострочную или многострочную команду. Для однострочной команды
   дать отдельное действие форматирования в читаемый многострочный вид.
   Форматирование не должно менять поведение скрипта: если безопасное
   преобразование невозможно, оставить исходный текст и объяснить причину.
   Интерфейс не должен поддерживать несколько расходящихся представлений,
   где поля многократно превращаются в команду и обратно.
3. Поддерживать два простых способа задания скрипта: полностью готовый
   текст, вставленный оператором, либо скрипт с заполнителями `{{engine}}`
   и `{{model}}`. Первый обозначает путь к исполняемому файлу выбранной
   установки движка, второй — путь к выбранному локальному артефакту модели.
   Можно использовать оба заполнителя, один из них либо ни одного. Отсутствие
   конкретного заполнителя означает, что соответствующий выбор не меняет
   текст команды скрыто. После запуска фактически обслуживаемую модель нужно
   сверять с API движка, если он предоставляет такую информацию.
4. Перед запуском показывать итоговый скрипт после подстановок и выбранные
   установку движка и модель. Каждый подставленный путь, даже с пробелами и
   специальными символами, должен оставаться одним аргументом; простая
   небезопасная замена текста не подходит. Выбирать конкретный профиль для
   запуска и остановки.
5. Запускать профиль как отдельный процесс на целевой машине. Отображать
   состояния запуска, готовности API, работы, завершения и ошибки.
6. Останавливать конкретный экземпляр, не затрагивая другие запущенные
   профили. Поддерживать одновременную работу нескольких профилей, в том
   числе экземпляров одного движка на разных портах и моделях.
7. Для каждого экземпляра показывать обнаруженный порт, модель, движок,
   профиль, состояние и доступные логи.
8. При старте LLM Studio запускать только профили с включённым автозапуском.
   При перезапуске Студии применяется то же правило. Сохранять состояние
   процессов между запусками, восстанавливать их или заново связывать с
   профилем не требуется. Отдельно отслеживать судьбу дочерних процессов
   после остановки Студии не нужно.
9. Связывать логи, метрики и статистику с уникальным именем профиля.
10. Позволять вручную редактировать файлы профилей и затем перечитывать их
    без переноса данных в базу. Ошибку в одном файле показывать явно, не
    уничтожая остальные профили и не подменяя некорректные данные догадкой.
    Для первой версии использовать один читаемый YAML-файл на профиль;
    многострочный скрипт хранить как многострочное значение. Перечитывать
    файлы при получении списка профилей и непосредственно перед запуском,
    без отдельного наблюдателя за папкой. Имя профиля — постоянный
    идентификатор: переименование можно выполнить созданием нового профиля,
    чтобы не смешивать исторические логи и статистику.

Пример скрипта профиля с выбранными движком и локальной моделью:

```sh
{{engine}} serve \
  --model {{model}} \
  --host 127.0.0.1 \
  --port 1919
```

Фактический путь `{{engine}}` берётся из выбранной установки. Оператор также
может вставить скрипт с готовыми путями вместо заполнителей. Порт задаётся
для конкретного профиля и не должен конфликтовать с другими запусками.

Переменные окружения профиля задаются отдельно от скрипта; значения секретов
не попадают в предварительный просмотр и логи. Порт, GPU и рабочую папку
оператор задаёт в скрипте или переменных окружения профиля, без отдельного
конструктора параметров. Детали безопасной подстановки путей и управления
процессом определяются при реализации; отдельного согласования с оператором
для этого не требуется.

## 6. Процессы, запущенные вне LLM Studio

1. Обнаруживать поддерживаемые процессы движков, запущенные вручную.
   Отсутствие сохранённого профиля не скрывает работающий процесс.
2. Определять связанный порт и, если доступен API движка, запрашивать
   фактически обслуживаемые модели. Показывать достоверно известные сведения
   и явно отмечать то, что определить не удалось.
3. Не показывать один экземпляр дважды, если он одновременно обнаружен в
   списке процессов и известен как запуск профиля.
4. Давать отправлять запросы такому экземпляру через общий API, если он
   доступен и его модель определена достаточно надёжно для маршрутизации.
5. Давать остановить внешний экземпляр после однозначного определения
   конкретного процесса. Нельзя завершать посторонний процесс из-за
   совпадения имени движка или порта. В первой версии останавливать только
   процесс того же системного пользователя, от которого работает Студия;
   непосредственно перед остановкой повторно сверять PID и время старта.
   Если идентичность не подтверждена, кнопку остановки не предлагать.
6. Обновлять наблюдаемое состояние при открытии страницы и по явной команде
   обновления. Отдельный фоновый наблюдатель за внешними процессами не нужен.

Глубокое управление внешним экземпляром не требуется: из действий над ним
нужна остановка. Принадлежность GPU, имя модели и порт нельзя выдумывать по
одному признаку; неполное наблюдение должно оставаться видимым.

## 7. Общий OpenAI-совместимый API

1. Предоставлять клиентам одну точку доступа для получения списка доступных
   моделей и отправки запросов выбранной модели.
2. Маршрутизировать запрос к нужному экземпляру, когда одновременно
   работают разные движки, профили или несколько экземпляров одной модели.
3. Включать в доступный список подходящие внешние экземпляры, а не только
   запущенные через профиль.
4. Отображать недоступность движка, неподдерживаемую операцию и ошибку
   маршрута без фиктивного успешного ответа.
5. Поддерживать сценарии обычного чата и моделей для embeddings там, где
   выбранный движок и модель предоставляют соответствующие возможности.
   Первая версия общего API включает `/v1/models`, `/v1/chat/completions` и
   `/v1/embeddings`; потоковые ответы чата передаются, когда их поддерживает
   движок. Неподдерживаемый метод возвращает явную ошибку. Имена моделей в
   общем API должны быть уникальными между одновременно работающими
   экземплярами: для запуска профиля публичное имя включает уникальное имя
   профиля, для внешнего — наблюдаемый идентификатор экземпляра. Внутреннее
   имя модели для движка сохраняется при маршрутизации. Точный синтаксис
   идентификатора является деталью API-контракта.

Общий API — маршрутизатор поверх существующих движков. Он не должен
предполагать, что на машине существует только один активный запуск.

## 8. Простой чат

1. На отдельной странице показывать модели, доступные через общий API.
2. Дать выбрать модель, отправить текстовое сообщение и получить ответ.
3. Не добавлять в первый чат браузер, инструменты или агентные сценарии.
4. Нужны понятные состояния ожидания, ошибки и недоступной модели.

История простого чата живёт в текущей сессии страницы. Сохранение её между
сеансами браузера в первой версии не требуется. Если выбранный движок
поддерживает потоковую выдачу, чат может показывать ответ по мере поступления.

## 9. Dashboard, метрики, логи и токены

### Обзор оборудования и экземпляров

1. Отдельная страница dashboard показывает локальное оборудование и все
   одновременно работающие экземпляры.
2. Для найденных NVIDIA GPU показывать доступные достоверные показатели:
   использование памяти, загрузку GPU и температуру. Позже можно расширить
   список показателей.
3. Дать переключаться между экземплярами и общей картиной. Для запусков
   через Студию основной группировкой служит имя профиля; для внешних нужен
   идентификатор на основе PID и времени старта процесса, устойчивый в
   течение жизни этого процесса.
4. Показать основные текущие показатели работы движка для выбранного
   экземпляра с максимально полезной для оператора детализацией.
5. Для каждого показателя знать источник, единицы измерения и момент
   получения. Недоступное или устаревшее значение обозначать отдельно от
   настоящего нуля. Нельзя выводить догадки как измерения.

### Адаптеры метрик движков

6. Задать единый интерфейс сбора метрик с реализациями для разных движков.
   Адаптеры `vLLM`, `llama.cpp`, `SGLang`, `ninfer` и `FreeToken` должны
   учитывать реально доступные источники каждого движка.
7. Показывать различия возможностей: метрика, которой у движка нет, не
   заполняется искусственно. Текущие показатели обновлять, пока открыт
   dashboard; постоянное хранение рядов метрик в первой версии не требуется.

### Логи и статистика токенов

8. Показывать логи запусков профилей и привязывать их к соответствующему
   профилю и экземпляру. Доступ к логам внешнего процесса зависит от
   фактически обнаруженного источника.
9. Собирать статистику входных и выходных токенов и разбивать её по профилям.
   Общая сумма может дополнять разбивку, но не заменяет её. Для запросов через
   общий API хранить учёт в SQLite; когда движок не сообщает расход токенов,
   оставлять значение неизвестным.
10. Различать учёт запросов через общий API и счётчики движка: прямые запросы
    к порту движка могут обходить прокси. Предел полноты статистики для
    внешних процессов показывать явно.
11. Вести отдельный журнал запросов к общему API. По умолчанию записывать
    только метаданные: время, идентификатор запроса, маршрут, выбранные
    профиль и модель, статус, длительность и число токенов, если оно известно.
    Тексты запросов и ответов по умолчанию не сохранять. Этот журнал не
    смешивать с логами приложения и движков.

Метрики соседнего проекта — пример UI и возможных источников, а не эталон
точности. Изучить код в `vllm-studio/controller/src/modules/system/` и
сверить показатели с документацией и наблюдаемыми данными каждого движка.

## 10. Страница статуса и Benchmarks

- Отдельная страница статуса показывает состояние backend, общего
  OpenAI-совместимого API и других необходимых компонентов. Работающий
  веб-процесс сам по себе не доказывает, что запросы к моделям проходят.
- Отдельная страница **Benchmarks** присутствует в первой версии как
  заготовка. Она явно сообщает, что функция появится позже. Запуск тестов,
  сравнение скорости, качества, уровней контекста и типов заданий в первую
  версию не входят.

## 11. Интерфейс и навигация

1. До реализации основных страниц определить дизайн-систему: сетку,
   типографику, цвета, отступы, состояния компонентов, адаптивность и
   правила отображения данных. Затем использовать её последовательно.
2. Предусмотреть страницы для dashboard, движков и окружений, моделей,
   профилей, чата, статуса, настроек и Benchmarks. В первой версии логи и
   статистику профиля показывать внутри его страницы.
3. Состояние страницы, которым нужно поделиться, отражать в URL: маршрут,
   выбранный раздел, фильтры и другие значимые параметры. При открытии
   ссылки и перезагрузке страницы это состояние восстанавливается.
4. Интерфейс не должен выдавать выбор профиля или модели за подтверждённый
   запуск процесса. Запуск, готовность и ошибки отражают состояние backend.

## 12. Backend, MCP и доступ

- Backend реализуется на Python, frontend — на JavaScript или TypeScript.
  В первой версии frontend собирается в статические файлы и отдаётся через
  backend вместе с API. На целевой машине работает один сервис приложения.
- У backend должен быть MCP endpoint для подключения агентов и управления
  Студией. В первой версии предоставить получение состояния системы, списка
  моделей и профилей, а также запуск и остановку профиля. Реализацию
  транспорта и контрактов инструментов определить при проектировании API.
- В первой версии аутентификация приложения не реализуется. Доступность из
  домашней сети предполагается; адрес привязки `HOST` и порт `PORT` задаются
  в `.env` и применяются при запуске приложения.
- Добавление аутентификации позже не является условием завершения первой
  версии.

## 13. База данных и конфигурация

1. Использовать локальную базу данных, предварительно SQLite. Локально её
   папка монтируется в Docker отдельно от временных файлов контейнера; на
   сервере она хранится вне каталога развёртываемого проекта.
2. С первой схемы предусмотреть миграции через Alembic.
3. Хранить профили в YAML-файлах каталога `<data-root>/profiles/`, а не в SQLite.
   Файлы должны быть пригодны для ручного редактирования и перечитываться
   перед запуском профиля. База может хранить статистику и другие данные, но не должна
   становиться вторым источником конфигурации профилей.
4. Настраивать пути к моделям, установкам движков, конфигурации и логам.
   Набор переменных, значения по умолчанию и проверка путей ещё обсуждаются.
5. Использовать `.env` для параметров работы приложения и в Docker, и на
   сервере. Поддерживать `.env.example` как шаблон без секретов.
6. Использовать отдельный файл параметров развёртывания для SSH-цели и
   настроек установки: `deploy.env`, с примером `deploy.env.example` без
   секретов. Этот файл не заменяет `.env` приложения и не хранится в Git.
7. Не хранить секреты, модельные файлы, базу и журналы в Git или в каталоге,
   который перезаписывается при деплое.
8. Использовать отдельный настраиваемый корневой каталог постоянных данных.
   Начальная структура внутри него:

   ```text
   <data-root>/
     data/             SQLite
     profiles/         редактируемые файлы профилей
     runtime/
       venvs/          окружения, созданные Студией
     logs/
       studio/         логи приложения
       engines/        логи отдельных запусков движков
       api/            журнал запросов к общему API
     audit/            место для будущего журнала аудита
   ```

   Логи движков разделять по экземплярам запуска и связывать с профилем и
   моделью, когда эта связь известна. Каталог `audit/` пока не означает
   реализацию аудита в первой версии. Точные имена файлов, ротацию и сроки
   хранения согласовать отдельно.

## 14. Разработка и развёртывание

`DEPLOYMENT_RULES.md` фиксирует требования к запуску. Для первой версии:

1. Обычный локальный запуск приложения происходит в Docker. Тесты могут
   работать на хосте при наличии инструментов.
2. При заданной SSH-цели общий скрипт передаёт проект и выполняет сборку и
   установку на целевой машине. Если цель не задана, тот же скрипт перед
   любыми изменениями спрашивает `Y/N` и после `Y` работает на текущей машине.
3. Установленное приложение регистрируется как служба и автоматически
   запускается после перезагрузки машины или LXC: через systemd на Linux,
   через launchd при явно подтверждённой нативной установке на macOS. Служба
   работает от того же системного пользователя, который вручную запускает
   движки на целевой машине.
4. После деплоя проверяются и состояние службы, и ответ приложения.
   Отдельная команда статуса выполняет такую проверку локально либо по SSH.
5. Файлы базы, моделей, профилей, конфигурации и логов отделены от файлов
   проекта.

Автозапуск **приложения** после перезагрузки обязателен. Автозапуск **моделей**
определяется индивидуальной настройкой каждого профиля.

## 15. Этапы реализации одной первой версии

Этапы ниже все относятся к `codex/version-zero`. Завершение промежуточного
этапа не означает, что первая версия готова к приёмке.

1. **Основа:** окончательная дизайн-система, структура приложения, локальный
   Docker, конфигурация, SQLite, Alembic, серверный запуск, деплой и статус.
2. **Каталог:** обнаружение пяти движков и их окружений, установка актуальных
   версий Python-движков в новые окружения, подключение готовых бинарников,
   локальное хранилище моделей, поиск и загрузка с Hugging Face, сопоставление
   вручную добавленных файлов.
3. **Запуски:** профили с командой и переменными, одновременные процессы,
   остановка, логи и опциональный автозапуск профилей.
4. **Наблюдение и доступ:** обнаружение внешних процессов, их остановка,
   общий OpenAI-совместимый API, маршрутизация, MCP endpoint и простой чат.
5. **Операционная картина:** dashboard с GPU и метриками движков, статистика
   токенов по профилям, страница статуса, URL-состояние и заготовка Benchmarks.
6. **Сквозная проверка:** одновременные запуски, внешний процесс, ручное
   добавление модели, перезагрузка службы, проверки статуса и деплоя.

Порядок может уточняться по зависимостям. Нельзя объявить первую версию
готовой, оставив один из перечисленных функциональных блоков только планом.

## 16. Сценарии приёмки первой версии

1. Для каждого из пяти поддерживаемых движков обнаруживается установленный
   экземпляр, если он есть на целевой машине. Две версии одного движка
   отображаются отдельно и доступны для выбора.
2. Новое пустое окружение получает актуальную доступную версию движка без
   изменения существующего. Профиль можно явно переключить между
   окружениями.
   Отдельное обновление существующего окружения меняет версию только в нём;
   результат проверяется повторно. При работающей из него модели обновление
   отклоняется без изменения окружения.
3. Ручное добавление модели в настроенную папку отражается в локальном
   каталоге; подтверждённое соответствие Hugging Face отмечается в поиске.
   Неопределённое соответствие не показывается как достоверно скачанное.
4. Два профиля одновременно запускают разные модели или движки на разных
   портах. Остановка одного не останавливает второй. Их логи, показатели и
   статистика разделены по профилям.
5. Профиль с автозапуском запускается при старте Студии. Профиль без него
   не запускается автоматически. При перезапуске действует то же правило,
   без восстановления прежних запусков.
6. Поддерживаемый процесс, запущенный вручную, появляется в интерфейсе и
   доступен через общий API. Если он принадлежит пользователю Студии и его
   идентичность подтверждена, он может быть остановлен без затрагивания
   других процессов.
7. Клиент получает актуальный список доступных моделей через общий API и
   отправляет запрос выбранной. Простой чат использует тот же список и API.
8. Dashboard показывает доступные показатели GPU и экземпляров; отсутствие
   источника обозначено как отсутствие данных. Токены показаны по профилям.
9. Ссылка на страницу с выбранным фильтром восстанавливает это состояние.
   Страницы статуса и Benchmarks доступны; последняя показывает заготовку.
10. Деплой по SSH собирает приложение на сервере. Служба стартует после
    перезагрузки; отдельно проверяются её состояние и ответ приложения.
11. Созданный профиль сохраняется в отдельной папке. После ручного изменения
    его файла Студия перечитывает корректное содержимое; статистика остаётся
    связанной с именем профиля. Скрипт с `{{engine}}` и `{{model}}` показывает
    оба выбранных пути перед запуском. Однострочную команду можно развернуть
    в многострочную без изменения её поведения; многострочный скрипт
    сохраняет переносы при редактировании.

## 17. Дизайн-система

Поиск окружений, формат профилей, базовый состав общего API, простого чата,
метрик, MCP и запуска службы зафиксированы выше. Точный способ безопасной
подстановки путей, определения процесса, опроса метрик и проверки Linux/GPU —
задачи проектирования и реализации, а не дополнительные вопросы владельцу.

Согласована основа **shadcn/ui** и визуальное направление: тёмный графит,
медный акцент, компактные компоненты. Правила, палитра и ссылка на стенд
зафиксированы в [дизайн-системе](2026-09-29-design-system.md).
Стенд показывает компоненты разных страниц; их окончательная компоновка
обсуждается отдельно. Соседний проект служит функциональным ориентиром,
его оформление не копируется автоматически.

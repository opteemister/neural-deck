# Neural Deck: простой API-прокси

Статус: **Согласовано пользователем 2026-10-27. §§1–9 реализованы; сквозные проверки §10 продолжаются.**
Дата: 2026-10-27. Ветка: codex/multimodal-api-compatibility.

Эта редакция заменяет прежнюю расширенную архитектуру.
Единый документ включает архитектуру, [интерфейс и чат](#9-прокси-страница-api-и-чат)
и [список API для тестирования](#10-api-для-тестирования).

[Результат реализации и проверок](../spec-results/2026-10-27-unified-provider-api.md).

## 1. Основной принцип

**Алиас модели + операция → workflow-файл → API ComfyUI → результат.**

Workflow определяет фактическую модель и значения параметров по умолчанию.
Стандартные параметры, переданные клиентом/LiteLLM, подставляются в graph
для конкретного запуска и переопределяют соответствующие defaults.
В Neural Deck настраивается выбор файла для генерации, edit, masked edit,
variations и аналогичных сценариев видео.

Neural Deck предоставляет стандартные внешние форматы API. Небольшой адаптер
преобразует запрос/ответ в нативный формат ComfyUI. Текст, OCR, решения,
embeddings и audio направляются соответствующему compatible serving
через существующий прокси.

Список API — перечень для последовательного подключения и тестирования,
а не обещание заранее реализовать все возможности каждой модели.

## 2. Реализация

Расширяем существующие ProxyService, RouteManager и image-сервис.
Переиспользуем небольшой ComfyUI-адаптер для изображений и видео:

1. Получить выбранный graph через API ComfyUI.
2. Подставить prompt, входные изображения/маску и параметры генерации запроса.
3. Отправить graph в /prompt.
4. Отследить состояние через /history, /queue или /ws.
5. Получить файл через /view и вернуть клиенту нужную форму ответа.

ComfyUI управляет очередью и исполнением. Собственные scheduler, постоянная
очередь генераций, worker/leases и универсальный координатор не вводятся.
Не строим framework преобразований, batch scheduler и систему автоматических
повторных генераций. Для совместимого serving сохраняем прямое forwarding.

## 3. Конфигурация

В существующей конфигурации прокси сохраняются адрес ComfyUI, алиас и
workflow-файл для каждой операции. Пример целевой настройки:

    comfyui:
      sources:
        main:
          base_url: http://127.0.0.1:8188
      models:
        qwen-image-turbo:
          source: main
          workflows:
            generate: workflows/image-generation.json
            edit: workflows/image-edit.json
            edit_masked: workflows/image-edit-masked.json
            variations: workflows/image-variations.json

Существующие текстовые aliases/профили сохраняются. Новую независимую
базу конфигурации моделей не создаём. Для видео действует тот же принцип.
Plain/masked edit выбираются по наличию mask; новый endpoint не нужен.

На той же машине и на отдельной VM используется одинаковый HTTP-доступ.
Подключение remote ComfyUI не требует фиктивного локального процесса.
Установка/управление удалённой ОС в этот механизм не входят.

## 4. Workflow и входы

Файл должен быть пригоден для штатного /prompt API ComfyUI: базовый вариант —
API-format export. Универсальный converter произвольных UI workflow с
widgets/subgraphs в этой задаче не строим.

Ранее прочитанные пользовательские Qwen-файлы — UI-format, несмотря на
_api в одном имени. Для простого прокси нужен штатный API export,
сохранённый на стороне ComfyUI и выбранный из того же каталога.
Neural Deck не ведёт отдельную библиотеку копий.

Тонкий обработчик передаёт prompt/image/mask и стандартные параметры запроса
в соответствующие входы поддержанного graph. Для этого необходимо простое
сопоставление поля API и входа workflow. Оно относится к обработчику/привязке
выбранного файла; универсальный редактор преобразований и DSL не создаются.
На первом рабочем workflow проверяются конкретные входы, без угадывания
первого текстового поля или случайного node.

Обязательные направления подстановки для Images API:

| Поле запроса | Что передаётся в запуск |
|---|---|
| prompt | Текстовый вход workflow |
| image/mask | Входы исходных изображений и маски |
| size | Ширина/высота или соответствующий вход размера |
| n | Число изображений через поддержанный batch/count вход workflow |
| quality | Соответствующий вход/режим качества workflow |
| background | Поддержанный режим фона workflow |
| output_format | Формат сохранения изображения в workflow |
| output_compression | Сжатие для поддержанного выходного кодека |

response_format задаёт возврат b64_json/URL и обрабатывается прокси, а не
подменяет output_format. Для Video аналогично передаются стандартные size,
seconds и reference input в соответствующие входы workflow. Внутренние FPS,
steps и прочие настройки остаются в файле, если их явная передача не входит
в поддержанный контракт запроса.

Если параметр не передан, используется значение из workflow. Если передан,
он валидируется и применяется перед /prompt. Исходный файл ComfyUI не меняется;
подстановка выполняется в памяти отдельно для каждого запроса.
Переданные поля нельзя просто отбросить. Если конкретный workflow не умеет
требуемое значение/режим, вернуть HTTP 400 с указанием поля. Добавление
подстановок стандартных параметров входит в задачу, а не откладывается только
на уже существующие возможности текущего обработчика.

Собственный batch scheduler или дополнительные модели для исполнения этих
параметров не вводятся: используется выбранный поддерживающий workflow.

## 5. Только API и кеш списка

Каталог и содержимое workflow читаются только через userdata API ComfyUI.
Прямого filesystem-доступа, SSH и mounts для workflow нет.

Каждый запрос списка сначала читает API. Успех обновляет кеш списка,
включая корректный пустой ответ. При недоступности берётся последний кеш.
В кеше — только источник, имена/пути и время чтения, без содержимого graphs.
Кеш другого адреса/пользовательского контекста не подставляется.

При запуске актуальный graph запрашивается через API и используется в памяти.
Копии raw/compiled graph в Neural Deck не сохраняются.
При выключенном ComfyUI настройки доступны по кешу, генерация недоступна.

## 6. Ответы, ID, файлы

Обычный Images API ждёт выполнения в очереди ComfyUI и возвращает готовый
ответ в том же HTTP-запросе. Для Videos сохраняется стандартный цикл
create → status → content.

Храним необходимые связи внешнего ID с источником, prompt_id и результатом,
чтобы последующие status/download знали, куда обратиться. Для этого достаточно
существующей SQLite; полноценная система durable execution не требуется.

По возможности результаты остаются в ComfyUI и получаются/проксируются
через API. Для b64_json кодируются полученные байты; URL/download выдают
готовый файл. Обязательную вторую библиотеку медиа и transcoding layer
не создаём.

Принятый prompt не отправляется повторно автоматически после сетевого сбоя.
Неизвестный исход возвращается как ошибка/неизвестное состояние.
Exactly-once не обещается. Глобальный /interrupt не используется для отмены
отдельного запроса чата или provider API.

**Автоудаление выключено.** Сроки хранения, TTL результатов, квоты библиотеки
и фоновая очистка сейчас не реализуются. Это не меняет собственное поведение
хранилища ComfyUI/другого serving.

## 7. Другие API

- Chat/Responses/embeddings/audio — forwarding к совместимому серверу.
- Decisions и System One — оба внешних формата; только необходимый адаптер
  между ними и нативным serving.
- OCR — формат выбранного совместимого OCR serving.
- Возможности конкретных моделей выясняются тестами по приложенному списку.
  Дополнительные модели, aligners, encoders и pipeline заранее не добавляются.
- Background/store/Files проксируются при наличии соответствующего API
  исполнителя; универсальную эмуляцию отсутствующих функций не строим.

## 8. Порядок работы и сохранение контрактов

1. Простая маршрутизация/конфигурация без поломки текущего text API.
2. Каталог workflow через API и кеш списка.
3. Один API-format image workflow: prompt → /prompt → результат.
4. Остальные операции по той же схеме; результаты отмечаются в списке API.
5. Подключение готовых операций к чату и странице API.

Сохраняются /v1, отдельный OPENAI_PORT, VITE_OPENAI_API_BASE_URL и native
ComfyUI proxy. Встроенный UI вызывает backend своего origin.
Профили остаются YAML; разработка/развёртывание — по действующим правилам.
Реализация этой редакции разрешена пользователем 2026-10-27.

## 9. Прокси, страница API и чат

### 9.1. Прокси

| Вкладка | Конфигурация |
|---|---|
| Модели | Существующие текстовые модели, OCR, embeddings, Decisions и другие compatible serving |
| Изображения | Алиас, подключение ComfyUI и workflow-файлы по операциям |
| Видео | Алиас, подключение ComfyUI и workflow-файлы по операциям |

Текстовый алиас можно создать, переименовать и сохранить без профилей.
Он остаётся в конфигурации и ожидает назначения исполнителя; запросы без
доступного исполнителя не выполняются. Последний профиль можно убрать,
сохранив сам алиас.

Согласовано 2026-10-28: на вкладке «Модели» над алиасами размещается блок
«OpenAI-подключения» с компактными строками и кнопкой «+ Подключение».
Создание и редактирование — в общей модалке: имя и полный URL на одной
адаптивной строке, API-ключ ниже. Пустой ключ при редактировании сохраняет
прежний; отдельное действие позволяет очистить его. Ключ хранится только
в приватном конфигурационном файле backend и не возвращается API.
Уточнено 2026-10-28: алиас содержит один общий список кандидатов.
Локальные профили и модели всех OpenAI-подключений показаны вместе;
выбор источника в форме отсутствует. Кандидатов разных источников можно
смешивать и упорядочивать. Подключения и каталоги загружаются в фоне;
имя подключения служит только вторичной подписью для различения моделей.
Уже сохранённые кандидаты остаются видимыми при недоступном каталоге.
Одно подключение используется в
нескольких алиасах; используемое подключение нельзя удалить до отвязки.
Удалённые модели не создают локальных профилей или процессов.
Маршрутизация подставляет upstream model ID и ключ выбранного подключения;
входящий Authorization клиента не пересылается на upstream. JSON, SSE
и доступные OpenAI media-запросы используют общий HTTP-транспорт прокси.
URL `/v1` и внутренний `/api/proxy` сохраняются. Поддержка операций на
удалённой стороне проверяется её ответом; каталог не доказывает совместимость.
Подключения хранятся в `config/openai-connections.yaml` с правами 0600,
связи алиасов — в `proxy-routes.yaml`, секция `alias_candidates`;
прежняя секция `remote_aliases` читается для совместимости.
Management API: GET/POST `/api/v1/proxy/openai/connections`,
PATCH/DELETE `/{connection_id}`, GET `/{connection_id}/models`.
Новый контракт создания/изменения алиаса — упорядоченный `candidates`:
кандидат содержит либо `profile_id`, либо `connection_id` и `model`.
Для изменения порядка и удаления используются непрозрачные `candidate_ids`.
Прежние `profile_ids` и одиночный `remote` читаются для совместимости;
новые и изменённые алиасы сохраняются в секции `alias_candidates`.
Прокси выбирает кандидата по порядку без различия источников. Переход к
следующему допустим только при безопасном сбое соединения до отправки
запроса; ответ сервера или начатый поток повторно на другом кандидате
не запускается. Смешивание embedding-пространств без подтверждения запрещено.
Перед сохранением проверяется существование подключения. Серверные ошибки
авторизации сохраняют upstream HTTP status; ошибки сети возвращают 502.
Переходы по HTTP redirect с ключом не выполняются.

Проверка 2026-10-28: 20 тестов локальных/удалённых маршрутов прошли;
проверка типов frontend и сборка прошли. Через UI создано временное
подключение к отдельному тестовому OpenAI HTTP-серверу в другом контейнере,
выбрана модель из каталога и получен SSE-ответ во встроенном чате.
JSON-запрос через внешний `/v1` на отдельном порту также прошёл.
Тестовый сервер проверял свой Bearer-ключ и настоящий upstream model ID.
Это проверка транспорта и UI, без запуска дополнительной языковой модели.
После объединения кандидатов прошли 23 backend-проверки маршрутов и
9 frontend-проверок списка, сохранения, переименования и перетаскивания.
Отдельно проверены смешанные маршруты в обоих направлениях, подстановка
правильного ключа, сохранение порядка и отсутствие повтора после ответа
upstream. Визуально подтверждено отсутствие выбора источника в модалке.

Для изображений — четыре выбора: генерация по prompt, edit, masked edit,
variations. Для видео действует тот же принцип для его операций.
На вкладке показываются компактные подключения со статусом и список алиасов.
Выбранная вкладка хранится в URL: `/proxy?tab=models`, `?tab=images`
или `?tab=video`. Прямые ссылки, перезагрузка и переходы назад/вперёд
восстанавливают вкладку; без параметра открываются модели.
Подключение `local` к серверу Neural Deck на порту 8188 доступно по умолчанию;
его доступность проверяет backend. Дополнительное подключение добавляется
кнопкой «+»: в модалке только имя и полный URL с портом. Существующие подключения
и скрытые параметры совместимости сохраняются.

Создание и редактирование алиаса выполняется в модалке: имя и подключение
в одной строке при достаточной ширине, затем workflow каждой операции
вертикальным списком с подписью слева. Workflow выбираются
из выпадающих списков без отдельных полей поиска. «Сохранить» сразу сохраняет
конфигурацию, «Отмена» отбрасывает draft. На странице нет полей node/input,
редактора API-привязок или общей кнопки сохранения для медиавкладок.
Карточка алиаса не дублирует список операций. Подписи полей имеют явный
интервал до поля, как в редакторе профилей. При сохранении проверяются только
выбранные workflow: UI-файл не принимается вместо API-графа; при недоступном
ComfyUI конфигурацию по-прежнему можно сохранить без такой проверки.

Workflow определяет фактическую модель и defaults генерации. Стандартные
параметры запроса (size, n, quality, background, output_format и другие
поддержанные поля) подставляются в graph для запуска. Нужное простое
сопоставление входов находится внутри обработчика. Существующие явные
привязки сохраняются для прежнего графа; для стандартных узлов используются
встроенные однозначные привязки. Неоднозначное сопоставление не угадывается.
Алиас вроде qwen-image-turbo используется как публичный model ID.
Текстовые профили и алиасы сохраняют существующее поведение.

### 9.2. Каталог workflow

Читаем только userdata API ComfyUI. Каждый запрос списка сначала идёт
к серверу; успех обновляет кеш списка, недоступность показывает кеш.
Кеш содержит только имена/пути, источник и время чтения.
Graphs в Neural Deck не сохраняются; filesystem/SSH/mounts не используются.

Выбранный workflow запрашивается через API при отправке генерации.
Для /prompt нужен штатный API-format graph. Автоматический converter
произвольных UI graphs не строится. Ранее прочитанные Qwen-файлы — UI-format;
для простого прокси понадобится API export на стороне ComfyUI.

При остановленном сервере вкладка и алиас доступны, конфигурация редактируется
по сохранённому списку. Генерация требует работающего API и доступного graph.
Cold start без полученного каталога имеет честное пустое состояние.
Смена источника не подставляет каталог другого сервера.

### 9.3. Страница API

После «Логи» в верхней шапке добавить «API», открывающую /api-docs.
Страница использует общую оболочку и тему Neural Deck.

Документация реализованных routes генерируется из OpenAPI JSON backend,
а отображается существующими React/shadcn-компонентами.
Второй ручной список параметров на frontend не поддерживается.

Показываются группы API, поиск, методы/пути, параметры, обязательность,
JSON/multipart примеры, ответы/ошибки, binary/SSE и копирование примеров.
Схему можно скачать. Её получение не требует работающей модели.

Backend предоставляет provider schema на origin интерфейса.
Браузер не обращается к внешнему OPENAI_PORT.
Полный инвентарь будущих тестов — отдельное приложение со статусами;
он не выдаётся за OpenAPI уже реализованных маршрутов.

### 9.4. Встроенный чат

Сохранить существующий текстовый чат и добавить:

| Сценарий | Вход | Результат |
|---|---|---|
| Vision | Изображение + вопрос, совместимая текстовая модель | Текстовый ответ |
| Генерация изображения | Prompt и image-алиас | Изображение в сообщении |
| Edit | Картинка + prompt, при необходимости mask | Новое изображение |
| Видео | Prompt, опционально исходная картинка | Встроенный video player |
| OCR | PDF/изображение документа | Текст/Markdown |

По уточнению пользователя от 2026-10-27 чат не содержит переключателя типа
или операции. Пользователь выбирает модель, пишет сообщение и при необходимости
прикрепляет файлы одной кнопкой. Перетаскивание и вставка используют тот же
список вложений; перед отправкой видны previews и удаление.

Маршрут определяется автоматически по объявленным возможностям модели и
вложениям: image-модель без исходного файла генерирует, с изображением и
описанием изменений редактирует; text-модель с изображениями использует vision;
video- и OCR-модели вызывают соответствующие API. Имена моделей и ключевые
слова prompt не используются для скрытого выбора другой модели.
Текстовые файлы читаются как контекст сообщения. Неподдержанное вложение
не отбрасывается: пользователь получает понятное сообщение, файлы и текст
сохраняются для исправления. Недоступная выбранная модель не заменяется молча.

Composer — единое округлое поле, круглая кнопка вложений, компактный выбор
модели и круглая отправка/остановка. Поле остаётся внизу, как в прежнем чате.
Перед выбором модели отображается компактный круговой индикатор заполнения
контекста по последнему известному измерению. Без токенов индикатор скрыт;
при наведении доступно количество токенов и известный лимит. Если лимит
неизвестен, кольцо отображается без заполнения. Подписи под полем нет. Статистика ответа
видна без раскрытия. Прежнее меню модели и reasoning сохраняется без поиска:
для текстовой модели доступны «Авто» и заявленные движком уровни/отключение.
После выбора модели меню остаётся открытым для настройки reasoning.

Для image-модели в том же меню показываются три ориентации: квадрат 1:1,
вертикальный 9:16 и горизонтальный 16:9, и галочка «Прозрачный фон».
Для video-модели используется тот же выбор ориентации, а ниже компактные
переключатели разрешения и длительности с учётом лимитов алиаса.
В последней строке настройки video-алиаса — «Макс. разрешение, p»
(`max_resolution`) и «Макс. длительность, с» (`max_seconds`). Разрешение p
означает короткую сторону; длинная ограничена отношением 16:9.
Эти значения возвращаются в capabilities модели. Чат предлагает 480p,
640p и установленный максимум без повторов и значений выше лимита;
длительность — 2, 5, 10 секунд и максимум, также без повторов и превышений.
Размеры округляются вниз до кратности 32. При 768p доступны 768×768,
768×1344 или 1344×768. Сохранённый выбор ограничивается актуальными
пределами модели; исходные предпочтения других алиасов не меняются.
Для новых алиасов значения по умолчанию — 768p и 15 секунд, пользователь
задаёт пределы своего workflow. API проверяет переданные size/seconds
до обращения в ComfyUI и возвращает 400 при превышении заданных пределов.
По умолчанию выбраны квадрат 640×640 и 2 секунды. Параметры сохраняются
в браузере отдельно для каждого алиаса и передаются в `POST /videos` как
`size` и `seconds`. Закрытый выбор модели не показывает сводку параметров.
Workflow должен поддерживать эти входы; фактическая длительность может
округляться под сетку кадров модели.
Ожидание video ID не имеет общего тайм-аута генерации. Сетевые ошибки и
HTTP 408/429/500/502/503/504 при чтении статуса или файла повторяются
с задержкой до 15 секунд; зависший запрос статуса прерывается через
20 секунд и повторяется. Это предел отдельного HTTP-запроса, а не видео.
POST создания автоматически не повторяется, чтобы не запускать дубликаты.
В чате во время обрыва показывается «Восстанавливаем связь…».
Незавершённая задача (ID, модель, prompt, время) сохраняется в sessionStorage
текущей вкладки и восстанавливается после перезагрузки/возврата на страницу.
Успех, окончательная ошибка и явная остановка ожидания очищают запись;
уход со страницы не отменяет задачу ComfyUI. Ссылка `chat?video={id}`
позволяет получить ранее созданный результат без нового POST.

Проверка 2026-10-28: 21 тест media-клиента (включая сетевой обрыв, 503,
зависший GET, ожидание 31 минуты, отмену и повтор скачивания) и проверка
восстановления страницы без повторного POST прошли. Видео пользователя
с anime-Tokyo prompt сохранилось после перезапуска превью: 1344×768,
362 кадра при 24 fps, 15.083 секунды. ComfyUI выполнял его 2590.95 секунды
(около 43 минут); результат восстановлен и воспроизводится в чате.
Последняя строка модалки image-алиаса содержит одно поле «Максимум, МП».
Значение по умолчанию — 4, оно возвращается в capabilities.max_megapixels.
Чат рассчитывает размеры из половины бюджета для обычного режима и полного
бюджета для «Макс. разр. (дольше)». Используется приблизительный нативный
бюджет 1024² пикселей на МП и округление сторон до кратности 64;
при 4 МП максимальные размеры — 2048×2048, 1536×2752, 2752×1536.
Размеры не хранятся константами на каждую модель. Формат файла, качество,
количество и дополнительные поля в чат не добавляются. Галочка максимума
также сохраняется в браузере; прежние настройки без неё читаются
с выключенным максимальным разрешением. На закрытом trigger параметры изображения
не показываются. Настройки отдельно для каждого алиаса сохраняются в
localStorage браузера и восстанавливаются после перезагрузки.
Размер и background передаются в стандартных image-запросах; исходный
workflow не изменяется. Для известного Qwen-графа обработчик включает
штатный custom-size путь, а прозрачность запрашивает нативным RGBA prompt.
Для masked edit размер canvas и маски согласуются штатными узлами в графе
конкретного запроса; alpha сохраняется при композиции.
Скрытый планировщик намерений не создаётся.

На изображении — кнопка «Скачать» и открытие полного размера.
На видео — player с controls и кнопка скачивания.
Полноразмерное превью изображений и видео показывается на затемнённом фоне
без рамки, заголовка, отступов и нижней панели. Закрытие — круглой кнопкой
поверх медиа справа сверху, скачивание — справа снизу; на видео кнопка
скачивания расположена над штатной полосой управления плеером.
Кнопки доступны мышью, клавиатурой и на touch.
Скачивание получает готовый файл, не запускает новую генерацию.
OCR-результат можно прочитать и скопировать.

Показываются ожидание/выполнение/ошибка запроса. Реальный progress ComfyUI
можно отобразить; неизвестный процент не выдумывается.
Глобальный interrupt не используется для отмены одной chat-операции.

Чат вызывает те же обработчики через backend своего origin.
Новая система chat sessions, постоянная очередь, поиск/организация истории
и автоматические OCR→LLM pipeline не входят в задачу.
Используем текущий ChatOptions; четыре новых режима не являются обязательными.

### 9.5. Минимальная приёмка

- Алиас/операция выбирают указанный workflow.
- Список получается через API; при недоступности работает кеш списка.
- Настройка доступна при остановленном ComfyUI; graphs не копируются.
- Prompt/attachments и стандартные параметры запроса достигают API graph;
  результат соответствует запросу, исходный файл не меняется.
- Картинка видна и скачивается; видео проигрывается и скачивается.
- Vision/OCR выводят текст.
- Страница API соответствует backend schema и теме приложения.
- Текущий text streaming, профили/алиасы и внешние адреса не сломаны.

**Автоудаление выключено.** Сроки хранения и фоновая очистка не реализуются.
Используются действующие компоненты и docs/development/frontend.md.

## 10. API для тестирования

Список нужен, чтобы затем проверять API на выбранных моделях/workflow.
Он не подтверждает совместимость и не требует заранее строить дополнительную
платформу исполнения. Часть маршрутов уже есть в коде.
Статус ниже относится к сквозному тесту клиент → Neural Deck → исполнитель.

### 10.1. Models и текст

| Endpoint | Что проверить | Статус |
|---|---|---|
| GET /v1/models | Публичные имена/алиасы доступных моделей | Работает: ComfyUI alias, прямой HTTP, 2026-10-27 |
| GET /v1/models/{model} | Одна модель и неизвестный ID | Не проверено |
| POST /v1/chat/completions | JSON, история, tools, SSE выбранного serving | Не проверено |
| POST /v1/responses | Native request/response и SSE | Не проверено |

Vision проверяется стандартными multimodal content parts у поддерживающей
текстовой модели. Это отдельный сценарий от OCR и image generation.

### 10.2. Изображения

| Endpoint | Что проверить | Статус |
|---|---|---|
| POST /v1/images/generations | Алиас/workflow и prompt → изображение | Работает: Qwen API export, прямой HTTP; LiteLLM ещё не проверен |
| POST /v1/images/edits | Исходная картинка + prompt → edit workflow | Работает: Qwen API-export, image + prompt, HTTP 200 и проверка результата; LiteLLM ещё не проверен |
| POST /v1/images/edits с mask | Выбор masked workflow и использование маски | Не проверено |
| POST /v1/images/variations | Variation workflow использует исходную картинку | Не проверено |

Стандартный JSON для generations, файловый multipart для edits/variations.
Обычный результат — created/data с b64_json либо URL в поддержанном режиме.
Проверить декодирование, отображение и скачивание результата.

Модель и defaults задаёт workflow. Стандартные параметры из запроса LiteLLM
передаются в запуск и переопределяют defaults в памяти. Подстановка этих
полей входит в реализацию простого адаптера.

| Параметр | Что проверить | Статус |
|---|---|---|
| size | Запрошенные ширина/высота попали в workflow и готовый файл | Работает: 768×768, 2026-10-27 |
| n | Запуск получил count/batch и вернул запрошенное число изображений | Работает частично: сквозной тест n=1; batch проверен моком |
| quality | Режим качества передан в соответствующий вход workflow | Не проверено |
| background | Поддержанный режим фона применён; transparent не подменён opaque | Не проверено |
| output_format | Кодек готового файла соответствует запросу | Не проверено |
| output_compression | Сжатие передано поддерживающему codec workflow | Не проверено |
| response_format | b64_json/URL корректно определяет способ возврата | Работает частично: URL и скачивание после restart; b64_json проверен моком |
| Параметры не переданы | Сохранены исходные defaults workflow | Не проверено |
| Следующий запрос | Подстановки прошлого запроса не изменили исходный файл | Не проверено |

Неподдержанное конкретным workflow значение даёт явный HTTP 400 с полем,
а не игнорируется. Несколько reference images и streaming/partial images
также проверяются при поддержке. Собственного batch scheduler не делаем.

Источники: [Images](https://docs.litellm.ai/docs/image_generation),
[Edits](https://docs.litellm.ai/docs/image_edits),
[Variations](https://docs.litellm.ai/docs/image_variations).

## 11. Минимальный harness встроенного чата (согласовано 2026-10-28)

Для просмотра добавлен read-only инструмент `get_image(image_id)`. Он доступен
без определения vision-возможностей модели. По вызову реальное изображение
передаётся LLM стандартным `image_url` с data URI после всех tool replies;
в SQLite остаётся ссылка на существующее вложение текущего диалога. Повторная
генерация и дублирование медиа в UI не выполняются. Модель получает инструкцию
запрашивать просмотр перед оценкой содержимого или качества картинки. URL
вместо ID и изображения другого диалога не принимаются. Автоматического
просмотра после каждой генерации нет: решение принимает LLM.

Проверка `get_image` 2026-10-28: 14 целевых backend-тестов проходят. В сквозном
тесте `main-llm-model` самостоятельно вызвала `get_image` по вопросу о ранее
созданной картинке и получила её для анализа; новая генерация не запускалась.

Текстовая LLM получает стандартные function tools `generate_image`, `edit_image`,
`generate_video`. Набор определяется настроенными media-алиасами и их workflow;
параметры и лимиты берутся из тех же алиасов. Выбранная LLM остаётся собеседником,
а изображения и видео создаются существующими сервисами ComfyUI. Прямой выбор
image/video-модели сохраняет существующий сценарий.

Описание каждого инструмента просит LLM перед вызовом уточнять краткий промпт
деталями композиции, освещения и стиля; для видео — движения и камеры. Замысел
и явные ограничения пользователя сохраняются, при редактировании уточняются
только запрошенные изменения. Просьба использовать точный промпт исключает
дополнения. Для вызова не нужно упоминать инструмент; просьба лишь написать
или обсудить промпт получает текстовый ответ без запуска генерации.

Для трёх инструментов используется небольшой прикладной цикл backend без нового
агентного фреймворка и зависимостей. До 50 обращений к LLM на пользовательский
запрос, до четырёх последовательных tool calls в одном ответе. Неполные вызовы из
оборванного потока не исполняются. Модель должна поддерживать OpenAI tool calling;
ошибки провайдера показываются явно, имитация вызовов текстовым парсингом не нужна.

Внутренние маршруты `/api/v1/chat/{conversation_id}` хранят текстовую историю,
реальные tool calls/results и вложения в отдельной SQLite `chats.sqlite3`. ID диалога находится
в URL `chat`; повтор POST с тем же ID сообщения идемпотентен. Медиа выводится
существующим компонентом рядом с текстовым ответом, краткий статус — в сообщении.
Новых режимов и технических панелей в UI нет. `/v1` и OPENAI_PORT не изменяются.

Вложения и результаты доступны инструментам только по ID из этого диалога.
LLM не получает URL/ключи подключений или произвольный HTTP-инструмент. Для
генерации используются сохранённые настройки размера/фона/длительности; явные
аргументы LLM проверяются по лимитам алиаса. Редактирование видео в этот набор
не входит: нужна отдельная поддерживаемая операция провайдера.

Выполнение backend продолжается при закрытии страницы. Повторное открытие URL
восстанавливает тот же диалог. После перезапуска backend ожидание видео с уже
сохранённым video ID продолжается без повторного POST генерации. Прерванная
отправка генерации с неизвестным результатом автоматически не повторяется.
Stop завершает цикл чата, но не прерывает общую очередь ComfyUI.

Проверено 2026-10-28: 11 целевых backend-тестов и 17 frontend-тестов, включая
прежние прямые сценарии чата. Сквозной тест в превью: `main-llm-model` вызвала
генерацию картинки через `qwen-image-turbo`, затем `edit_image` по ID предыдущего
результата без повторного вложения. Восстановление video job без повторного POST
проверено на управляемом тестовом сервисе; новая GPU-генерация видео для этого
этапа не запускалась.

## 12. Единый контракт reasoning (согласовано 2026-10-28)

`GET /v1/models` и `GET /v1/models/{model}` возвращают существующее расширение
Neural Deck `reasoning_capabilities`. Это дополнение к OpenAI model object,
а не утверждение о наличии стандартного OpenAI discovery-поля:

```json
{
  "efforts": ["low", "medium", "xhigh"],
  "effort_parameter": "chat_template_kwargs",
  "can_disable_thinking": true,
  "default_effort": "xhigh"
}
```

`efforts` содержит подтверждённые значения, `default_effort` — только известный
default. Универсальный набор значений: none/minimal/low/medium/high/xhigh/max;
каждая модель объявляет свой поднабор. `effort_parameter` — подсказка транспорта
к upstream для совместимости, клиенты Neural Deck используют стандартные поля:

- Chat Completions: `{"reasoning_effort":"low"}`.
- Responses: `{"reasoning":{"effort":"low"}}`.
- Авто: параметр отсутствует, defaults исполнителя не меняются.
- Выкл.: `none`, если поддержано; прокси при необходимости переводит его в
  `chat_template_kwargs.enable_thinking=false`.

Сохраняется приём native `chat_template_kwargs.reasoning_effort` и
`enable_thinking`. Противоречащие друг другу настройки и неподдержанный известной
моделью уровень дают HTTP 400 до отправки генерации. При переводе сохраняются
прочие kwargs и Responses reasoning-поля, включая summary. Никакой подмены
high на xhigh и ограничения мыслительных токенов вместо реального уровня нет.

Для локального managed-профиля используется команда конкретного работающего
экземпляра и выбранный ею chat template: явный `--chat-template` имеет приоритет
перед tokenizer_config.json. Поддержаны статические ограничения списком/кортежем
и переменная, присвоенная из reasoning_effort, как у текущего Qwen. Шаблон не
исполняется; неизвестные/недоступные шаблоны не дают вымышленных capabilities.
CLI defaults через `--default-chat-template-kwargs` учитываются. Кеш шаблона обновляется по
mtime/размеру; обновление метаданных не требует перезапуска модели.

Удалённое OpenAI-подключение сохраняет и нормализует тот же контракт, включая
default и max. Также принимаются явно опубликованные supported_reasoning_efforts,
default_reasoning_effort и supports_enable_thinking. Наличие параметра в SDK
или название модели не доказывают поддержку уровней. Без metadata запрос
передаётся в upstream без придумывания его возможностей. Для алиаса публикуется
metadata первого доступного кандидата; перевод выполняется по выбранному
исполнителю. Неизвестный клиенту дополнительный уровень не подменяется другим.

Встроенный чат показывает только объявленные варианты, включая Max, и отправляет
те же стандартные поля, что внешний клиент через OPENAI_PORT. Это одинаково
для локальных моделей и цепочки Neural Deck → Neural Deck.

### LiteLLM

OpenAI-compatible подключение использует стандартный reasoning_effort; обработка
Responses использует reasoning.effort. Для произвольного имени LiteLLM может
потребоваться указание его документированного флага в конфигурации LiteLLM:

```yaml
model_list:
  - model_name: my-qwen
    litellm_params:
      model: openai/qwen
      api_base: http://neural-deck:8080/v1
    model_info:
      supports_reasoning: true
```

Точный список уровней доступен в reasoning_capabilities нашего `/v1/models`.
`supports_reasoning` не означает поддержку всех уровней. LiteLLM и сторонние UI
могут использовать собственный каталог и не обязаны автоматически импортировать
это расширение; не заявляем автоматическую синхронизацию неизвестных клиентов.
Не включать drop_params для сокрытия отклонённого уровня.

Источники: [OpenAI reasoning](https://developers.openai.com/api/docs/guides/reasoning),
[vLLM reasoning](https://docs.vllm.ai/en/stable/features/reasoning_outputs/),
[LiteLLM reasoning](https://docs.litellm.ai/docs/reasoning_content).

Проверки реализации: 19 целевых backend-тестов reasoning, существующие проверки
provider forwarding/локальных и удалённых aliases и 12 frontend-тестов прошли.
Проверены список/детали модели через публичный API, параметры Chat Completions
и Responses, сохранение summary, HTTP 400 для неподдержанного уровня и
идемпотентный перевод при двух последовательных Neural Deck.
Живой прогон через установленный LiteLLM в эти проверки не входит.
По решению пользователя обновление основного сервера отложено до общего
релиза этой ветки; отдельный серверный патч не применяется.


## PDF во встроенном чате

PDF принимается общей кнопкой вложений в диалог с текстовой/Vision-моделью
или OCR-моделью. Backend преобразует страницы через Poppler в PNG по порядку
и передаёт изображения, а не PDF, в выбранную модель. Исходный PDF хранится
как вложение истории диалога; промежуточные PNG и временная копия PDF
удаляются после подготовки запроса, включая ошибки и остановку операции.
Страницы не сохраняются как самостоятельные вложения. Для продолжения
обычного диалога PDF из истории преобразуется заново.

Предельные значения: 25 МБ на PDF, 200 страниц, длинная сторона страницы
до 2560 пикселей, 8 МБ на PNG и 64 МБ на отрисованный документ. Превышение
возвращает явную ошибку без молчаливого усечения. Возможности зрения и
контекстное окно выбранной модели дополнительно ограничивают обработку.

Обычная Vision-модель получает пользовательский вопрос и страницы через
стандартные `image_url` в Chat Completions. Нативный `/v1/ocr` получает
страницы как `image_url` последовательно, результат объединяется по порядку.
Unlimited-OCR-2 на SGLang использует Chat Completions с документированным
шаблоном `<PAGE><image>…Multi page parsing.`, `temperature: 0`,
`skip_special_tokens: false` и `images_config.crop_mode`. Это специализированное
распознавание с фиксированной инструкцией модели, без инструментов агента.
Профиль модели `Unlimited-OCR-2` с `--chat-template unlimited-ocr` объявляет
`capabilities.document_adapter: unlimited_ocr_2`; метаданные проходят через
OpenAI-подключения и алиасы. Имя алиаса не используется для угадывания типа.
На удалённом Neural Deck объявление появляется после релиза этой ветки;
отдельный серверный патч не применяется.

Проверка: 54 backend-теста и 40 frontend-тестов прошли; проверены порядок
страниц, очистка временных файлов, ошибки, отмена и передача метаданных
через локальные и удалённые алиасы. Живой запрос через локальный API
с двухстраничным PDF и `main-llm-model` вернул `Page ONE`, `Page TWO`
в правильном порядке; временных каталогов после завершения нет.
Адаптер Unlimited-OCR-2 проверен на уровне запроса и маршрутизации; живой
прогон этой модели не выполнялся. Формат взят из
[карточки Unlimited-OCR-2](https://huggingface.co/baidu/Unlimited-OCR-2).


## Единый чат для UI и MCP

По решению пользователя `nd_chat_send`, `nd_chat_get`, `nd_chat_stop` — тонкие
обёртки над тем же
`ChatService` и `ChatTurnRequest`, что HTTP API frontend. Эти три MCP-инструмента
используют общую историю и сохраняемые задачи. PDF, OCR, агентные инструменты
и прямой выбор image/video-модели доступны по одному контракту. Выбор
операции по модели перенесён из выполнения на frontend в общий backend;
визуальный интерфейс и настройки сохраняются. Каталог MCP включает все
поддержанные чатовые типы. Отдельные специализированные MCP-инструменты
для каждой новой возможности не обязательны. Постоянные границы ответственности
описаны в `docs/development/chat-and-mcp.md`; формат и примеры — в `docs/mcp.md`.

Проверки общего пути: MCP и HTTP читают один диалог; повтор `nd_chat_send` с теми же
идентификаторами не запускает генерацию повторно. Проверены вызов генерации
LLM-инструментом, прямой image/video-алиас, edit/mask/variations, PDF для Vision
и нативного OCR, чтение и остановка долгой задачи, общий каталог с лимитами.
Frontend сохранил существующий выбор модели, reasoning, вложения и настройки
медиа; новые отправки всех типов используют `/api/v1/chat`. Старые сохранённые
в браузере задачи видео по-прежнему можно дочитать без повторной генерации.


## Отдельная тестовая база чатов (согласовано 2026-10-29)

Все данные `ChatStore` отделены от основной SQLite в `data/chats.sqlite3`.
Отсутствующий файл и таблицы создаются при запуске и следующем обращении
штатным подключением SQLite и DDL `CREATE TABLE IF NOT EXISTS`. Пул
соединений для чатов отключён стандартным `NullPool`. Удалённые диалоги
не восстанавливаются из кеша процесса. По уточнённому прямому решению
пользователя стандартная стартовая миграция `0011_drop_old_chat_tables`
удаляет старые чатовые таблицы из основной базы без переноса истории
и резервных копий.

## История чатов в правой панели (согласовано 2026-10-29)

Справа на странице чата доступна сворачиваемая панель со скруглением как
у поля ввода. На широком контейнере панель располагается рядом с диалогом,
на узком открывается поверх него и закрывается при выборе чата. Кнопка
«Чаты» возвращает скрытую панель. Список содержит все сохранённые диалоги,
новые сверху, с названием из первого сообщения, моделью и датой; отдельная
LLM для названий не вызывается.

Клик открывает соответствующий `chat` и последнюю модель в URL. Новый чат
начинается без сохранения пустой записи. Удаление после подтверждения
останавливает запрос выбранного диалога, удаляет его историю и загруженные
вложения из `chats.sqlite3`, очищает кеш процесса. Другие диалоги и файлы
ComfyUI не удаляются. Удаление текущего диалога открывает пустой чат.

HTTP: `GET /api/v1/chat` и `DELETE /api/v1/chat/{conversation_id}`. Внешние
MCP-обёртки `nd_chat_list` и `nd_chat_delete` используют тот же сервис.

## MCP-управление конфигурацией прокси (согласовано 2026-10-29)

Внешнему агенту доступны все действия трёх вкладок страницы «Прокси»:
OpenAI-подключения, обновление их каталогов, общий выбор локальных и удалённых
кандидатов, текстовые алиасы и порядок маршрутов, подключения ComfyUI,
каталог/проверка workflow, image/video алиасы и их лимиты.

Адаптер MCP вызывает общие прикладные методы HTTP API. Правила переименования
источников, проверки занятости, workflow, уникальности имён и сохранения
несвязанных настроек принадлежат backend; UI не переписывает весь конфиг
для изменения одного подключения или алиаса. Привязки node IDs не используются: workflow предоставляет именованные входы ND.v1.

Стандартный local нельзя изменить/удалить. Offline-каталог использует кэш;
сохранение настроек не скачивает и не анализирует workflow. API-ключи не возвращаются. Инструменты и все поля
имеют короткие предметные описания; контракты и примеры — в `docs/mcp.md`.

## Стандартные параметры изображений (согласовано 2026-10-29)

Универсальные правила подготовки последующих моделей и workflow, сохранения
пользовательского сценария и внешнего OpenAI-контракта описаны в
`docs/comfyui-workflow-contract.md`, разделы 1.1–1.2. Актуальное решение владельца: workflow — чёрный ящик, обратная совместимость
не требуется. Сравнение нового графа с прежним, проверки defaults/ветвей
и аудит результатов в NeuralDeck не выполняются; подробности — в контракте.

Для внешних клиентов, включая LiteLLM, генерация, edit, edit с маской и
вариации используют единый image-сервис с чатом. Добавлены посткодирование
PNG/JPEG/WebP, `output_compression` 0–100 (JPEG/WebP, default 100), `seed`
генератора шума и обработка `quality`. Qwen Turbo сохраняет штатные 8 шагов:
`auto`, `low`, `medium`, `high` принимаются как совместимые имена одного
сохранённого режима (`auto`), без изменения сэмплинга или разрешения.
Неизвестные значения возвращают HTTP 400. Различающиеся режимы требуют
содержательного определения и подтверждения тестами; число шагов не является
шкалой качества. Формат по умолчанию PNG; сочетание JPEG с прозрачным фоном
отклоняется. Настройки узлов и расширение чата/UI не добавляются.

Подробный контракт, ограничения воспроизводимости, пример запроса и хранение
преобразованных URL-результатов описаны в `docs/openai-endpoint.md`.
В уточнении пользователь отменил запуск тестов и генераций: ручную проверку
через существующий LiteLLM и ComfyUI он выполняет самостоятельно. Новые
профили, model instances и серверные workflow не создаются и не изменяются.

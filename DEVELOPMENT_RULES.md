# Инструкции разработки

Обязательный входной документ перед разработкой. `AGENTS.md` содержит контекст
проекта и ссылки на инструкции; подробные правила разработки хранятся здесь
и в тематических документах `docs/development/`.

## Общие правила

- Одноразовые изменения структуры существующих данных и конфигураций не
  хранить в коде приложения: не добавлять миграции, списки прежних полей,
  compatibility-преобразования или автоматическое переписывание при чтении.
  Такие изменения оформлять отдельным списком действий для пользователя либо,
  после его явного утверждения, выполнять вручную один раз. В приложении
  остаются актуальная модель данных и общая диагностика. Неизвестные поля
  конфигурации просто игнорируются, не блокируя загрузку; отдельных проверок,
  предупреждений и списков устаревших полей для них не добавлять.
- Полная видимость пользовательских настроек и действий в UI обязательна.
  Всё, что пользователь может задать через MCP/API или сохранить в конфигурации,
  должно быть доступно для просмотра и соответствующего изменения через UI.
  Унаследованные значения и defaults должны быть различимы от явных настроек.
  Скрытые подстановки и преобразования при открытии или сохранении формы
  запрещены: UI показывает сохранённое значение, а вычисленный результат —
  отдельно и явно. Команда запуска в редакторе всегда остаётся шаблоном;
  разрешение placeholders выполняется только для явного preview и запуска.
  Изменения UI/MCP/схем конфигурации проверять на полноту отображения и
  сохранение всех настроек при цикле открытия и сохранения формы.
- Типы задач, API-протокол, API URL и UI URL задаются только определением
  движка. Профиль не содержит и не переопределяет эти настройки. Draft-модель
  задаётся непосредственно аргументами команды запуска, без `draft_path`
  и `{{model_draft}}`. Отдельный явно видимый параметр `port` профиля сохранён.
  При удалении настройки из UI одновременно удалять её из схем API/MCP и
  backend; обработку существующих YAML согласовывать как отдельное одноразовое
  действие по правилу выше.
- Сначала обсудить и утвердить спецификацию, затем реализовать её этапами.
- Спецификации и документацию проекта писать на русском. Имена команд,
  переменных, путей API и идентификаторов сохранять в исходном виде.
- Секреты и постоянные данные не хранить в Git.
- Новый runtime-код можно сразу проверять и развёртывать из разрешённых
  исходных каталогов; правила состава deployment-архива и исключений указаны
  в `DEPLOYMENT_RULES.md`. Перед коммитом новый файл всё равно нужно добавить
  в Git, чтобы он вошёл в историю проекта.

## Как расширять инструкции

- Новое правило добавлять в подходящий тематический документ.
- Для новой области создавать документ в `docs/development/` и добавлять
  ссылку в таблицу выше. В `AGENTS.md` дополнительные подробности не переносить.
- Общие правила для всех областей добавлять в раздел «Общие правила».
- Не дублировать правила между документами. Спецификации описывают требования
  конкретных изменений, инструкции — постоянный порядок разработки.
